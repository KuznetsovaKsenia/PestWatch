# 1. Назначение документа

## 1.1 Общая информация

Настоящий документ описывает внутреннее устройство веб-приложения «Сезонный дозор» и определяет инженерные решения, необходимые для его реализации.

Документ является продолжением документа:

**«Техническое задание и пользовательские сценарии»**

и используется как рабочая основа разработки.

Если техническое задание отвечает на вопрос:

> **Что должна делать система?**

то настоящий документ отвечает:

> **Как система должна быть построена и на какие реалистичные задачи должна быть разложена разработка?**

---

## 1.2 Основание для проектирования

Архитектура приложения основана на результатах предварительного исследования сезонных биологических угроз в Центральной России.

Исследование установило, что для различных угроз значимы разные измеримые факторы:

- температура воздуха;
- влажность;
- температура почвы;
- осадки и сухость;
- ветер;
- сезон;
- накопленные температурные показатели.

При этом погодные данные позволяют выполнять индикативную оценку условий активности, но не позволяют достоверно определять фактическое присутствие конкретного вредителя. :contentReference[oaicite:0]{index=0}

Поэтому архитектура строится вокруг детерминированного **Risk Engine**, а не вокруг системы прогнозирования фактического появления вредителей.

## 1.4 Принцип декомпозиции

Декомпозиция разработки должна переводить архитектурные решения в конкретные задачи, по которым можно непосредственно реализовывать код.

Задачи не должны формулироваться слишком широко.

Например, задача:

```text
Реализовать Risk Engine
```

является недостаточно конкретной.

Она должна быть разложена на отдельные технические задачи:

```text
Создать модель WeatherData

Создать enum RiskLevel

Создать модель RiskResult

Создать модель RiskFactorResult

Определить общий контракт расчета риска

Реализовать расчет риска для иксодовых клещей

Реализовать расчет риска для колорадского жука

Реализовать расчет риска для капустной тли

Реализовать расчет риска для яблонной плодожорки

Реализовать обработку отсутствующих данных

Добавить unit-тесты для расчетной логики
```

Каждая задача должна иметь:

- понятную цель;
- определенный результат;
- минимально необходимый объем;
- проверяемый критерий завершения.

Декомпозиция должна позволять последовательно выполнять разработку без повторного проектирования архитектуры во время написания кода.

# 2. Общая архитектура системы

## 2.1 Архитектурный стиль

«Сезонный дозор» реализуется как локально запускаемое клиент-серверное веб-приложение.

Используется многослойная архитектура.

Основные уровни системы:

```text
Presentation Layer
        ↓
Application / Service Layer
        ↓
Domain / Risk Calculation Layer
        ↓
Data Access Layer
```

Интеграции с внешними погодными сервисами выделяются в отдельный:

```text
Integration Layer
```

Внутри расчетной части дополнительно различаются:

```text
provider observations
        ↓
derived domain calculations
        ↓
RiskContext
        ↓
threat-specific factor evaluation
        ↓
generic risk policy
        ↓
RiskResult
```

Основные архитектурные принципы:

- пользовательский интерфейс отделен от бизнес-логики;
- внешние Weather API изолированы от Domain / Risk Calculation Layer;
- текущие и исторические погодные данные имеют отдельные integration pipelines;
- provider-specific payload не передается непосредственно в расчетный слой;
- derived indicators рассчитываются после нормализации provider data;
- `RiskContext` является canonical input contract для Risk Calculators;
- Risk Calculators не зависят от Flask, SQLite и Weather API;
- `RiskPolicy` не содержит threat-specific biological thresholds;
- расчет должен быть детерминированным;
- результат должен быть объяснимым;
- отсутствующие данные не подменяются искусственными значениями;
- расчетная логика должна тестироваться отдельно от внешнего API, persistence и интерфейса.

---

## 2.3 Основные компоненты

### Frontend

Отвечает за взаимодействие с пользователем.

Основные функции:

- выбор территории;
- выбор профиля;
- запуск оценки;
- отображение погодных данных;
- отображение уровней риска;
- просмотр факторов;
- просмотр рекомендаций;
- просмотр истории.

Frontend не выполняет предметные расчеты риска.

Frontend не должен:

- применять biological thresholds;
- рассчитывать derived indicators;
- интерпретировать `RiskFactorResult`;
- обращаться напрямую к внешнему Weather API.

---

### Flask Backend

Является серверной частью приложения.

Отвечает за:

- прием HTTP-запросов;
- валидацию transport-level входных данных;
- вызов application services;
- формирование HTTP-ответов.

Backend не должен содержать правила конкретных биологических угроз непосредственно в HTTP-контроллерах.

HTTP layer не является владельцем:

```text
RiskContext
RiskPolicy
RiskLevel rules
derived calculations
```

---

### Current Weather Integration

Отвечает за получение и нормализацию текущих погодных наблюдений.

Canonical pipeline:

```text
Location
        ↓
WeatherService
        ↓
WeatherClient
        ↓
Current Weather API
        ↓
raw provider payload
        ↓
WeatherAdapter
        ↓
WeatherData
```

#### WeatherClient

Отвечает за:

- HTTP-запрос;
- параметры координат;
- timeout;
- network errors;
- HTTP errors;
- получение provider payload.

#### WeatherAdapter

Отвечает за:

```text
provider payload
        ↓
normalized WeatherData
```

Adapter не выполняет:

- T10 interpolation;
- Degree Days calculation;
- threat-specific risk interpretation.

#### WeatherService

Координирует:

```text
Location
→ WeatherClient
→ WeatherAdapter
→ WeatherData
```

После получения `WeatherData` ответственность `WeatherService` заканчивается.

---

### Historical Weather Integration

Отвечает за получение и нормализацию исторического температурного ряда.

Canonical pipeline:

```text
Location
+
period
        ↓
HistoricalWeatherService
        ↓
HistoricalWeatherClient
        ↓
Historical Weather API
        ↓
raw historical payload
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

Historical Weather Integration имеет отдельный domain output:

```text
DailyTemperature[]
```

и не возвращает `WeatherData`.

Historical integration не рассчитывает:

```text
DegreeDaysResult
RiskFactorResult
RiskResult
```

---

### Derived Calculations

Derived calculations преобразуют нормализованные observations в новые domain facts.

#### SoilTemperatureEstimator

Использует:

```text
WeatherData.soilTemperature6cm
+
WeatherData.soilTemperature18cm
```

и формирует:

```text
SoilTemperatureEstimate
```

Estimator не знает:

```text
COLORADO_BEETLE
13 °C threshold
RiskLevel
```

#### DegreeDaysCalculator

Использует:

```text
DailyTemperature[]
```

и формирует:

```text
DegreeDaysResult
```

Calculator использует собственный calculation contract, включая base temperature.

Он не знает biological threshold конкретной угрозы:

```text
130
```

Этот threshold принадлежит threat-specific Risk Calculator.

---

### RiskContext

`RiskContext` является canonical input aggregate Risk Calculators.

Он объединяет:

```text
WeatherData
+
SoilTemperatureEstimate | None
+
DegreeDaysResult | None
```

`RiskContext` не получает данные самостоятельно и не выполняет вычисления.

В него не входят:

```text
Location
UserProfile
Threat
RiskLevel
RiskResult
Recommendation
Source
```

---

### Risk Calculators

Каждая поддерживаемая угроза имеет отдельный specialized calculator:

```text
TICK
→ TickRiskCalculator

COLORADO_BEETLE
→ ColoradoBeetleRiskCalculator

CABBAGE_APHID
→ CabbageAphidRiskCalculator

CODLING_MOTH
→ CodlingMothRiskCalculator
```

Единый contract:

```python
evaluate(
    context: RiskContext,
) -> tuple[RiskFactorResult, ...]
```

Risk Calculator отвечает за:

- выбор необходимых inputs из `RiskContext`;
- применение threat-specific thresholds;
- формирование `RiskFactorResult[]`.

Risk Calculator не отвечает за:

- HTTP;
- получение WeatherData;
- получение historical data;
- формирование derived indicators;
- определение итогового `RiskStatus`;
- определение итогового `RiskLevel`;
- persistence.

---

### RiskPolicy

`RiskPolicy` отвечает за generic interpretation результатов факторов.

Вход:

```text
RiskFactorResult[]
```

Policy определяет:

```text
RiskStatus
RiskLevel
```

Status semantics:

```text
CALCULATED
→ отсутствующих факторов нет
```

```text
LIMITED
→ обязательные факторы доступны,
  но отсутствует optional factor
```

```text
INSUFFICIENT_DATA
→ отсутствует required factor
  либо factors отсутствуют
```

`RiskStatus.ERROR` не выводится `RiskPolicy` из состояний факторов.

`RiskPolicy` не содержит thresholds конкретных threats.

---

### RiskEngine

`RiskEngine` является общим компонентом формирования итогового результата.

Получает:

```text
threatCode
+
RiskFactorResult[]
```

Использует `RiskPolicy` для определения:

```text
status
riskLevel
```

и формирует:

```text
RiskResult
```

Canonical boundary:

```text
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult
```

RiskEngine не выполняет:

- HTTP-запросы;
- выбор территории;
- получение WeatherData;
- historical data acquisition;
- T10 interpolation;
- Degree Days calculation;
- threat-specific factor checks;
- прямое сохранение в SQLite;
- чтение пользовательского ввода.

---

### Threat Service

Отвечает за работу со справочной информацией об угрозах.

Предоставляет:

- название;
- описание;
- объект воздействия;
- возможный вред;
- сезон активности;
- принадлежность к профилю;
- профилактические рекомендации;
- официальные источники.

Threat Service не выполняет расчет уровня риска.

`activeSeason` является справочной характеристикой угрозы и не означает автоматически наличие runtime-factor `SEASON` в текущих Risk Calculators.

---

### Assessment / Application Orchestration

Пользовательский сценарий оценки требует orchestration нескольких существующих компонентов.

Концептуально:

```text
Location
+
UserProfile
        ↓
Threat[]
+
prepared calculation inputs
        ↓
RiskResult[]
        ↓
Assessment
```

Однако точный production contract orchestration пока не утвержден.

До отдельного Assessment Architecture Decision не фиксируются:

```text
AssessmentService как окончательный orchestration owner

RiskContextBuilder

RiskContextFactory

стратегия подготовки current/historical inputs

Assessment snapshot

ERROR isolation

transaction boundary
```

Следовательно, данный раздел не назначает преждевременно конкретный класс владельцем полного E2E flow.

---

### History Service

Концептуально отвечает за:

- получение списка выполненных оценок;
- получение конкретного исторического результата;
- подготовку сохраненных данных для отображения.

Обязательное product requirement:

```text
исторический результат
не пересчитывается при открытии
```

Точный persistence contract истории определяется вместе с Assessment.

---

### Repository Layer

Отвечает за операции с постоянным хранилищем.

Основные типы операций:

- чтение;
- создание;
- сохранение;
- поиск;
- получение исторических данных.

Repository не содержит:

- расчетной логики;
- biological thresholds;
- HTTP-логики;
- Weather API integration;
- derived calculations.

Точный Repository contract для Assessment определяется после утверждения persistence model.

---

### SQLAlchemy ORM

Используется для взаимодействия Python-приложения с реляционным хранилищем.

ORM-модели не должны:

- рассчитывать `RiskLevel`;
- формировать `RiskFactorResult`;
- выполнять provider integration;
- содержать threat-specific calculation logic.

Точный набор ORM-моделей Assessment определяется отдельно.

---

### SQLite

SQLite рассматривается как локальное постоянное хранилище приложения.

В нем могут храниться:

- справочные сведения об угрозах;
- рекомендации;
- источники;
- исторические результаты пользовательских оценок.

Точный состав persisted assessment input snapshot и derived data пока не фиксируется.

---

## 2.4 Основной поток выполнения оценки

Основной пользовательский сценарий начинается с:

```text
Location
+
UserProfile
```

После выбора профиля определяется:

```text
Threat[]
```

Параллельно или в необходимой последовательности application orchestration получает environmental inputs.

Canonical calculation flow:

```text
Location
        │
        ├──────────────→ Current Weather Integration
        │                         ↓
        │                    WeatherData
        │                         │
        │                         ▼
        │              SoilTemperatureEstimator
        │                         ↓
        │              SoilTemperatureEstimate
        │
        └──────────────→ Historical Weather Integration
                                  ↓
                          DailyTemperature[]
                                  ↓
                         DegreeDaysCalculator
                                  ↓
                          DegreeDaysResult
```

Далее:

```text
WeatherData
+
available derived indicators
        ↓
RiskContext
```

Одновременно:

```text
UserProfile
        ↓
Threat[]
        ↓
выбор calculator
```

После этого:

```text
RiskContext
+
selected RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult
```

Для нескольких threats:

```text
Threat A
→ Calculator A
→ RiskResult A

Threat B
→ Calculator B
→ RiskResult B
```

Итог:

```text
RiskResult[]
        ↓
ASSESSMENT BOUNDARY
```

Точная последовательность orchestration после этой точки определяется Assessment Architecture.

### Независимость threat evaluations

Каждая угроза оценивается независимо.

Например, для профиля:

```text
VEGETABLE_GARDEN
```

могут быть выбраны:

```text
COLORADO_BEETLE
CABBAGE_APHID
```

Для них используются разные inputs:

```text
COLORADO_BEETLE
→ soilTemperature10cmEstimate
```

```text
CABBAGE_APHID
→ current temperature + humidity
```

Недостаточность данных или высокий `RiskLevel` одной threat model не должны автоматически изменять результат другой.

---

## 2.5 Граница ответственности Weather Integration

Внешние погодные сервисы являются источниками environmental observations.

Они не должны:

- определять `RiskLevel`;
- выбирать угрозы;
- знать о `UserProfile`;
- формировать `Recommendation`;
- применять threat-specific thresholds;
- определять итог приложения.

Все provider-specific данные нормализуются до передачи в Domain / Risk Calculation Layer.

### Current Weather

```text
Current Weather API
        ↓
WeatherClient
        ↓
WeatherAdapter
        ↓
WeatherData
```

### Historical Weather

```text
Historical Weather API
        ↓
HistoricalWeatherClient
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

Следует различать:

```text
provider payload
```

и:

```text
normalized domain observations
```

После normalization остальная расчетная система не зависит от provider JSON.

### Integration validity

Integration layer определяет:

```text
можно ли корректно нормализовать provider response
```

Он не определяет:

```text
достаточно ли этих данных для конкретной threat model
```

Например:

```text
humidity = None
```

может быть допустимым normalized observation.

Решение о том, делает ли это конкретную оценку недостаточной, принимается Risk Calculator / Risk Policy.

---

## 2.6 Граница ответственности Risk Calculation Layer

Расчетный слой состоит из нескольких отдельных responsibilities.

### Derived calculation

```text
normalized observations
        ↓
SoilTemperatureEstimator
или
DegreeDaysCalculator
        ↓
derived domain result
```

### Threat-specific interpretation

```text
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
```

### Generic risk interpretation

```text
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskStatus + RiskLevel
```

### Result composition

```text
threatCode
+
RiskFactorResult[]
+
policy result
        ↓
RiskEngine
        ↓
RiskResult
```

Таким образом, термин:

```text
Risk Calculation Layer
```

не означает один монолитный `RiskEngine`.

Внутри calculation layer responsibilities разделены между:

```text
Derived Calculators
RiskContext
Risk Calculators
RiskPolicy
RiskEngine
```

Это позволяет каждый этап тестировать отдельно.

Для unit-тестирования Risk Calculator не требуется реальный Weather API:

```text
готовый RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
```

Для unit-тестирования RiskPolicy:

```text
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
status + level
```

## 2.7 Основной архитектурный принцип

Получение погодных данных само по себе не является основной ценностью проекта.

Внешние сервисы уже предоставляют environmental observations.

Собственная программная ценность «Сезонного дозора» возникает в последовательной интерпретации этих данных:

```text
External environmental data
        ↓
normalized observations
        ↓
derived environmental facts
        ↓
RiskContext
        ↓
threat-specific factor evidence
        ↓
generic RiskPolicy
        ↓
explainable RiskResult
```

Ключевым является не один отдельный класс, а **полная расчетная граница**:

```text
data normalization
→ derived calculation
→ RiskContext
→ RiskCalculator
→ RiskFactorResult[]
→ RiskPolicy
→ RiskEngine
→ RiskResult
```

Архитектура должна обеспечивать:

- отдельные правила для разных угроз;
- детерминированность;
- воспроизводимость;
- объяснимость;
- явную обработку отсутствующих данных;
- provenance derived indicators;
- трассируемость предметных правил до источников;
- независимость от конкретного Weather API;
- возможность изолированного тестирования каждого расчетного этапа;
- отсутствие преждевременной зависимости calculation core от будущего Assessment persistence.

# 3. Архитектурные принципы

## 3.1 Разделение ответственности

Каждый компонент приложения должен иметь одну основную область ответственности.

Архитектура должна разделять:

```text
transport
application orchestration
provider integration
domain normalization
derived calculations
threat-specific factor evaluation
generic risk policy
result composition
persistence
presentation
```

Смешение этих responsibilities в одном компоненте не допускается без отдельного архитектурного решения.

---

### Controller

Controller отвечает за:

- прием HTTP-запроса;
- получение transport-level параметров;
- валидацию структуры входного HTTP-запроса;
- вызов application layer;
- формирование HTTP-ответа.

Controller не должен:

- содержать правила оценки риска;
- применять biological thresholds;
- рассчитывать derived indicators;
- определять `RiskLevel`;
- обращаться к Weather API напрямую;
- выполнять SQL-запросы;
- содержать persistence logic.

---

### Application / Service Layer

Application / Service Layer отвечает за координацию пользовательских сценариев.

Service может:

- получить необходимые domain inputs через integration services;
- вызвать domain calculations;
- определить последовательность вызовов компонентов;
- координировать несколько независимых операций.

Service не должен содержать threat-specific biological thresholds.

Точный orchestration основного Assessment flow пока не фиксируется.

До отдельного Assessment Architecture Decision не утверждаются как canonical:

```text
AssessmentService
как окончательный владелец E2E flow

RiskContextBuilder

RiskContextFactory

конкретный порядок current/historical acquisition

конкретная persistence sequence
```

В документации термин:

```text
assessment/application orchestration
```

используется до утверждения окончательного контракта.

---

### Current Weather Integration

Current Weather Integration отвечает за:

```text
Location
        ↓
WeatherClient
        ↓
provider payload
        ↓
WeatherAdapter
        ↓
WeatherData
```

Integration layer выполняет:

- HTTP-взаимодействие;
- timeout handling;
- provider error handling;
- нормализацию provider-specific payload;
- сохранение отсутствующих optional observations как отсутствующих значений.

Integration layer не определяет:

```text
RiskStatus
RiskLevel
RiskFactorState
```

и не решает, достаточно ли конкретной модели угрозы имеющихся данных.

---

### Historical Weather Integration

Historical Weather Integration отвечает за:

```text
Location + period
        ↓
HistoricalWeatherClient
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

Он не рассчитывает:

```text
DegreeDaysResult
RiskFactorResult
RiskResult
```

---

### Derived Calculations

Derived calculations преобразуют нормализованные observations в новые domain facts.

Текущие компоненты:

```text
SoilTemperatureEstimator

DegreeDaysCalculator
```

Они отвечают за:

```text
normalized source data
        ↓
deterministic calculation
        ↓
derived domain result
```

Derived calculations не содержат threat-specific risk thresholds.

---

### RiskCalculator

`RiskCalculator` отвечает за применение правил конкретной threat model.

Вход:

```text
RiskContext
```

Выход:

```text
RiskFactorResult[]
```

Его ответственность:

- извлечь необходимые inputs;
- применить threshold конкретной угрозы;
- определить `MATCHED`, `NOT_MATCHED` или `MISSING`;
- сформировать объяснимый `RiskFactorResult`.

RiskCalculator не должен:

- обращаться к Weather API;
- вызывать WeatherService;
- получать historical data;
- рассчитывать derived indicators;
- определять итоговый `RiskStatus`;
- определять итоговый `RiskLevel`;
- сохранять результат.

---

### RiskPolicy

`RiskPolicy` отвечает за generic interpretation набора factor evidence.

Вход:

```text
RiskFactorResult[]
```

Он определяет:

```text
RiskStatus
RiskLevel
```

Policy учитывает:

```text
MATCHED
NOT_MATCHED
MISSING
required
```

RiskPolicy не содержит biological thresholds конкретных threats.

---

### RiskEngine

`RiskEngine` отвечает за композицию итогового `RiskResult`.

Он:

```text
получает threatCode
+
RiskFactorResult[]
        ↓
вызывает RiskPolicy
        ↓
получает status + level
        ↓
формирует RiskResult
```

RiskEngine не должен:

- получать WeatherData самостоятельно;
- обращаться к внешним API;
- рассчитывать T10;
- рассчитывать Degree Days;
- применять threat-specific thresholds;
- выбирать UserProfile;
- сохранять данные в persistence;
- зависеть от Flask;
- работать с HTML.

---

### Repository

Repository отвечает за постоянное хранение и чтение данных.

Repository выполняет:

- чтение;
- сохранение;
- поиск;
- получение исторических записей.

Repository не содержит:

- расчетной логики;
- threat-specific rules;
- HTTP-логики;
- integration logic;
- derived calculations.

Точный Repository contract для Assessment определяется вместе с Assessment persistence architecture.

---

## 3.2 Независимость слоев

Зависимости должны идти через явно определенные contracts и domain models.

Концептуальное направление:

```text
Controller
        ↓
Application / Service
        ↓
Domain / Risk Calculation
```

Integration Layer используется Application / Service Layer для получения внешних данных.

Persistence используется Application / Service Layer через Repository contracts.

Не допускаются прямые зависимости вида:

```text
Controller
        ↓
SQLAlchemy Model
```

или:

```text
RiskCalculator
        ↓
Weather API
```

или:

```text
RiskPolicy
        ↓
Threat Repository
```

или:

```text
Repository
        ↓
Weather API
```

или:

```text
RiskEngine
        ↓
Flask
```

Domain / Risk Calculation Layer должен оставаться независимым от transport и persistence frameworks.

---

## 3.3 Детерминированность расчетов

При одинаковых:

```text
RiskContext
+
выбранной threat model
+
версии calculation rules
+
RiskPolicy
```

система должна возвращать одинаковый расчетный результат.

На уровне отдельных stages:

```text
одинаковый RiskContext
        ↓
одинаковый RiskCalculator
        ↓
одинаковые RiskFactorResult[]
```

и:

```text
одинаковые RiskFactorResult[]
        ↓
одинаковый RiskPolicy
        ↓
одинаковые RiskStatus + RiskLevel
```

Следовательно:

```text
одинаковый threatCode
+
одинаковые RiskFactorResult[]
        ↓
RiskEngine
        ↓
одинаковый RiskResult
```

Для derived calculations действует тот же принцип:

```text
одинаковые source observations
+
одинаковый calculation method
        ↓
одинаковый derived result
```

Например:

```text
T6 + T18
        ↓
один и тот же interpolation method
        ↓
одинаковый SoilTemperatureEstimate
```

и:

```text
DailyTemperature[]
+
одинаковая base temperature
+
одинаковый calculation method
        ↓
одинаковый DegreeDaysResult
```

В расчетах не используются:

- случайные значения;
- генеративный AI;
- случайный выбор факторов;
- недокументированные поправочные коэффициенты;
- скрытые fallback-значения для отсутствующих данных.

---

## 3.4 Объяснимость

Система не должна возвращать только итоговый уровень риска.

Недостаточный результат:

```text
HIGH
```

Полноценный результат должен позволять понять:

```text
какая угроза оценивалась

какие факторы проверялись

какие значения были доступны

какие условия применялись

какие факторы совпали

какие факторы не совпали

каких данных не хватало

почему был определен итоговый статус и уровень
```

Основой объяснимости является:

```text
RiskFactorResult[]
```

Каждый `RiskFactorResult` должен содержать достаточную информацию о:

- проверяемом factor;
- фактическом значении;
- ожидаемом условии;
- состоянии `MATCHED / NOT_MATCHED / MISSING`;
- обязательности factor;
- explanation.

Итоговый `RiskResult` не должен скрывать factor evidence.

Derived indicators также должны быть объяснимыми на уровне собственного происхождения:

```text
SoilTemperatureEstimate
→ source depths
→ source temperatures
→ calculation method
```

```text
DegreeDaysResult
→ base temperature
→ period
→ observations
→ calculation method
```

При этом provenance derived calculation и risk explanation являются разными уровнями объяснимости.

---

## 3.5 Независимость моделей угроз

Каждая поддерживаемая угроза имеет собственную расчетную модель.

Не используется одна универсальная biological formula для всех угроз.

Текущие MVP models:

```text
Иксодовые клещи
        ↓
AIR_TEMPERATURE
        ↓
TickRiskCalculator
```

```text
Колорадский жук
        ↓
SOIL_TEMPERATURE_10CM
        ↓
ColoradoBeetleRiskCalculator
```

```text
Капустная тля
        ↓
AIR_TEMPERATURE
+
HUMIDITY
        ↓
CabbageAphidRiskCalculator
```

```text
Яблонная плодожорка
        ↓
DEGREE_DAYS_ABOVE_10C
        ↓
CodlingMothRiskCalculator
```

Справочное поле:

```text
Threat.activeSeason
```

не означает автоматически наличие runtime-factor:

```text
SEASON
```

В текущих реализованных Risk Calculators `SEASON` не используется как factor.

Добавление сезонного factor требует отдельного изменения calculation contract и тестового покрытия.

Общими для всех threats являются:

```text
RiskContext contract
RiskFactorResult model
RiskPolicy
RiskEngine
```

Но threat-specific thresholds остаются внутри соответствующих Risk Calculators.

---

## 3.6 Явная работа с отсутствующими данными

Отсутствие данных является самостоятельным состоянием и не должно маскироваться.

Например:

```text
humidity = None
```

не означает:

```text
humidity = 0
```

и не означает:

```text
humidity condition = NOT_MATCHED
```

Для factor evaluation используются минимум три состояния:

```text
MATCHED
NOT_MATCHED
MISSING
```

Семантика:

```text
MATCHED
→ данные доступны, условие выполнено
```

```text
NOT_MATCHED
→ данные доступны, условие не выполнено
```

```text
MISSING
→ данных для проверки нет
```

Дополнительно каждый factor имеет признак:

```text
required
```

RiskPolicy интерпретирует отсутствующие данные следующим образом:

```text
required factor = MISSING
        ↓
INSUFFICIENT_DATA
```

```text
optional factor = MISSING
+
required factors available
        ↓
LIMITED
```

При:

```text
INSUFFICIENT_DATA
```

обычный `RiskLevel` отсутствует.

При:

```text
LIMITED
```

`RiskLevel` может быть рассчитан по известным факторам.

В текущих четырех MVP calculators все реализованные factors являются required, но `LIMITED` остается поддерживаемой общей capability RiskPolicy.

---

## 3.7 Трассируемость правил

Каждое threat-specific предметное правило должно иметь источник либо явно зафиксированное основание происхождения.

Логическая цепочка:

```text
Official Source
        ↓
engineering interpretation
        ↓
threat-specific threshold / rule
        ↓
RiskCalculator
        ↓
RiskFactorResult
        ↓
RiskResult
```

При наличии conceptual `RiskRule` его роль следует понимать как описание предметного условия, а не обязательно как отдельную runtime entity.

Следует различать:

```text
официальный источник
```

```text
инженерную интерпретацию
```

```text
программный threshold
```

```text
фактический результат проверки
```

Это позволяет проверить, почему конкретное условие присутствует в calculation model.

Derived calculations имеют отдельную provenance chain:

```text
source observations
        ↓
calculation method
        ↓
derived domain result
```

Derived provenance не заменяет traceability biological risk rules.

---

## 3.8 Неизменность исторической оценки

Исторический Assessment должен представлять результат конкретного пользовательского запуска и не пересчитываться при последующем открытии.

Обязательный принцип:

```text
stored historical assessment
        ↓
open
        ↓
same historical result
```

Изменение:

- текущей погоды;
- historical provider data;
- текущего Risk Calculator;
- threshold;
- RiskPolicy;
- recommendation text

не должно автоматически изменять уже сохраненный исторический результат.

Для этого persistence должна сохранять достаточно данных, чтобы историческая запись была воспроизводимой и объяснимой.

Однако точный состав:

```text
assessment input snapshot
```

пока не фиксируется.

В частности, до Assessment Architecture Decision не утверждается автоматически, что достаточно хранить только:

```text
WeatherData
```

или что необходимо хранить целиком:

```text
RiskContext
DailyTemperature[]
SoilTemperatureEstimate
DegreeDaysResult
```

Это отдельное persistence decision.

---

## 3.9 Изоляция внешних интеграций

Конкретный поставщик погодных данных не должен влиять на Risk Calculators, RiskPolicy или RiskEngine.

Если внешний current-weather provider возвращает provider-specific JSON:

```json
{
  "temp": 18.4,
  "humidity": 67,
  "wind_speed": 3.2
}
```

integration layer преобразует его в:

```text
WeatherData
```

Если historical provider возвращает собственную структуру массивов дат и температур, integration layer преобразует ее в:

```text
DailyTemperature[]
```

После normalization provider-specific payload больше не используется расчетным слоем.

При замене поставщика изменяются:

```text
Client
Adapter
integration configuration
```

но не должны изменяться только по этой причине:

```text
RiskContext
RiskCalculator contracts
RiskPolicy
RiskEngine
```

Derived calculations также не должны зависеть от raw provider JSON.

---

## 3.10 Минимальная связанность

Компоненты должны взаимодействовать через четко определенные contracts и domain models.

Canonical boundaries:

```text
Current Weather Integration
        ↓
WeatherData
```

```text
Historical Weather Integration
        ↓
DailyTemperature[]
```

```text
WeatherData
        ↓
SoilTemperatureEstimator
        ↓
SoilTemperatureEstimate
```

```text
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult
```

```text
prepared domain inputs
        ↓
RiskContext
```

```text
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
```

```text
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult
```

Между слоями не передается необработанный provider JSON.

Также не должно существовать второго альтернативного calculation contract вида:

```text
WeatherData
        ↓
RiskCalculator
```

Canonical input Risk Calculator:

```text
RiskContext
```

До утверждения Assessment Architecture calculation core не должен зависеть от конкретной будущей snapshot или persistence model.

# 4. Контекстная диаграмма

## 4.1 Назначение

Контекстная диаграмма определяет:

- границы приложения;
- пользователей системы;
- внешние информационные источники;
- данные, поступающие извне;
- данные и решения, формируемые внутри приложения;
- границу между реализованным calculation core и будущей Assessment architecture.

Контекстная диаграмма не является детальной component diagram.

Она показывает, какие responsibilities принадлежат «Сезонному дозору», а какие находятся за его пределами.

```text
                         Пользователь
                              │
                              ▼
               +--------------------------------+
               |                                |
               |        СЕЗОННЫЙ ДОЗОР         |
               |                                |
               |  • выбор территории           |
               |  • выбор профиля              |
               |  • получение погодных данных  |
               |  • derived calculations       |
               |  • оценка факторов риска      |
               |  • формирование RiskResult    |
               |  • объяснение результата      |
               |  • рекомендации               |
               |  • история Assessment         |
               |                                |
               +--------------------------------+
                    │                     │
          ┌─────────┴─────────┐           │
          ▼                   ▼           ▼
 Current Weather      Historical Weather  Официальные
      API                    API          источники
                                       Роспотребнадзор /
                                       Россельхозцентр
```

---

## 4.2 Пользователь

Пользователь взаимодействует с приложением через браузер.

Он:

- выбирает территорию;
- выбирает пользовательский профиль;
- запускает оценку;
- просматривает текущие environmental data;
- просматривает результаты оценки угроз;
- изучает факторы результата;
- получает объяснение;
- изучает профилактические рекомендации;
- просматривает справочник;
- открывает историю выполненных оценок.

Пользователь не вводит вручную:

- значения погодных показателей;
- biological thresholds;
- расчетные коэффициенты;
- список факторов конкретной угрозы.

На вход основного пользовательского сценария поступают:

```text
Location
+
UserProfile
```

Эти значения имеют разные назначения:

```text
Location
→ получение environmental data
```

```text
UserProfile
→ определение Threat[]
```

---

## 4.3 Внешние погодные системы

Погодные API являются внешними информационными системами.

После развития MVP приложение использует две логически различные external capabilities:

```text
Current Weather
```

и:

```text
Historical Weather
```

Они могут предоставляться одним или разными внешними сервисами, но внутри приложения рассматриваются как разные integration flows.

### Current Weather API

Предоставляет текущие погодные наблюдения.

Используемые в текущей модели данные могут включать:

- температуру воздуха;
- относительную влажность;
- осадки;
- скорость ветра;
- температуру почвы на доступных глубинах;
- время наблюдения.

External provider response преобразуется во внутренний:

```text
WeatherData
```

### Historical Weather API

Предоставляет исторические суточные температурные данные за заданный период.

External provider response преобразуется во внутренний ряд:

```text
DailyTemperature[]
```

Historical Weather API не возвращает готовый:

```text
DegreeDaysResult
```

для расчетного ядра приложения.

Расчет accumulated temperature является responsibility «Сезонного дозора».

### Что Weather API не делает

Внешняя погодная система не должна:

- знать о пользовательских профилях;
- выбирать Threat;
- знать biological thresholds;
- рассчитывать `RiskFactorResult`;
- определять `RiskStatus`;
- определять `RiskLevel`;
- формировать `Recommendation`;
- создавать Assessment;
- определять итоговую пользовательскую интерпретацию.

Weather provider является источником observations, а не владельцем risk model.

---

## 4.4 Официальные источники

В качестве предметных источников используются:

- Роспотребнадзор;
- Россельхозцентр.

В MVP приложение не обязано автоматически читать или анализировать их сайты во время пользовательского расчета.

Сведения из предварительного исследования вручную преобразуются в:

- справочные сведения об угрозах;
- инженерные интерпретации biological conditions;
- thresholds расчетных моделей;
- профилактические рекомендации;
- ссылки на источники.

Логически:

```text
Official Source
        ↓
engineering interpretation
        ↓
threat-specific rule
        ↓
RiskCalculator
```

Следует различать:

```text
официальный источник
```

и:

```text
программное правило расчета
```

Официальный источник не выполняет вычисления внутри приложения.

---

    WeatherClient

    HistoricalWeatherClient

```text

History
Repository

```

в системной границе не означает, что их окончательный Assessment persistence contract уже утвержден.

Точный E2E orchestration после `RiskResult[]` определяется отдельным Assessment Architecture Decision.

## 4.6 Что находится за пределами системы

За пределами приложения находятся:

```text
Current Weather API

Historical Weather API

сайты Роспотребнадзора

сайты Россельхозцентра

реальный медицинский мониторинг

реальный фитосанитарный мониторинг

профессиональные агросистемы

полевые наблюдения
```

«Сезонный дозор» не является системой:

- диагностики;
- медицинского мониторинга;
- фитосанитарного учета;
- подтверждения фактического присутствия вредителя;
- профессионального агрономического прогнозирования.

Результат приложения представляет интерпретацию доступных environmental conditions в рамках зафиксированной расчетной модели.

---

## 4.7 Основной поток данных

На контекстном уровне основной поток выглядит следующим образом.

### Выбор угроз

```text
Пользователь
        ↓
UserProfile
        ↓
Threat[]
```

### Получение текущих observations

```text
Пользователь выбирает Location
        ↓
Current Weather API
        ↓
Current Weather Integration
        ↓
WeatherData
```

### Получение historical observations

Если выбранная расчетная модель требует исторических температур:

```text
Location
+
required period
        ↓
Historical Weather API
        ↓
Historical Weather Integration
        ↓
DailyTemperature[]
```

### Derived calculations

```text
WeatherData
        ↓
SoilTemperatureEstimator
        ↓
SoilTemperatureEstimate
```

и:

```text
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult
```

### Подготовка calculation input

```text
WeatherData
+
available derived indicators
        ↓
RiskContext
```

### Оценка угроз

```text
Threat[]
        ↓
выбор специализированных Risk Calculators

RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult[]
```

Две ветви сходятся на этапе calculator invocation:

```text
Threat[]
      \
       \
        → selected RiskCalculator
       /
RiskContext
```

`UserProfile` не преобразуется в `RiskContext`.

`Location` не является частью `RiskContext`.

---

### Assessment Boundary

Текущая полностью определенная calculation architecture заканчивается на:

```text
RiskResult[]
```

Дальнейший product flow:

```text
RiskResult[]
        ↓
Assessment
        ↓
Persistence
        ↓
History
        ↓
UI
```

является обязательным пользовательским сценарием, однако его точный technical contract пока определяется отдельно.

В частности, настоящая контекстная диаграмма не фиксирует:

```text
AssessmentService
как окончательный orchestration owner

WeatherSnapshot
как окончательный snapshot contract

хранение RiskContext

хранение DegreeDaysResult

хранение SoilTemperatureEstimate

хранение DailyTemperature[]

точную transaction boundary
```

## 4.8 Архитектурная ценность системы

Сам факт получения текущей или исторической погоды не является основной ценностью приложения.

Внешние сервисы предоставляют observations.

Собственная логика «Сезонного дозора» начинается после их получения и нормализации:

```text
External Weather Data
        ↓
normalized observations
        ↓
derived environmental facts
        ↓
RiskContext
        ↓
threat-specific interpretation
        ↓
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskResult
        ↓
объяснимая пользовательская оценка
```

Пример разделения knowledge layers:

```text
T6 = 16 °C
T18 = 10 °C
        ↓
SoilTemperatureEstimator
        ↓
T10 = 14 °C
```

На этом этапе существует только derived environmental fact.

Далее:

```text
T10 = 14 °C
        ↓
ColoradoBeetleRiskCalculator
        ↓
14 °C >= 13 °C
        ↓
MATCHED
```

И только после этого:

```text
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskLevel
```

Аналогично:

```text
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult.total
```

не является само по себе результатом риска яблонной плодожорки.

Risk interpretation появляется только после применения:

```text
CodlingMothRiskCalculator
```

Таким образом, собственная архитектурная ценность проекта состоит не в одном монолитном `RiskEngine`, а в системе разделенных и проверяемых stages:

```text
provider isolation

normalization

derived calculations

RiskContext

threat-specific calculators

factor evidence

RiskPolicy

RiskResult
```

Эти stages должны оставаться независимо тестируемыми и не должны смешиваться с будущими решениями о persistence Assessment.

# 5. Логическая модель предметной области (Domain Model)

## 5.1 Назначение

Логическая модель предметной области определяет основные сущности системы, value objects, расчетные входные данные и связи между ними.

Она не зависит напрямую от:

- Flask;
- SQLite;
- SQLAlchemy;
- конкретного Weather API.

Domain Model описывает предметную структуру приложения и отделяет:

- исходные погодные наблюдения;
- производные расчетные показатели;
- входной контекст оценки риска;
- результаты проверки факторов;
- итоговые результаты оценки угроз;
- данные, необходимые для пользовательской истории.

---

## 5.2 Общая модель

Domain Model состоит из нескольких связанных областей.

### Справочная модель

```text
UserProfile
     │
     └────── * Threat
                  │
                  ├────── * RiskRule
                  │
                  ├────── * Recommendation
                  │
                  └────── * Source
```

### Модель погодных и производных данных

```text
Location
     │
     │ используется для получения
     ▼
WeatherData
     │
     │ исходные погодные наблюдения
     │
     ├──────────────→ SoilTemperatureEstimate
     │
     │
     │
DailyTemperature[]
     │
     ▼
DegreeDaysResult
```

`WeatherData` содержит нормализованные текущие погодные наблюдения.

`SoilTemperatureEstimate` и `DegreeDaysResult` являются производными domain-моделями и не являются частью `WeatherData`.

### Расчетная модель

```text
WeatherData
        +
SoilTemperatureEstimate | None
        +
DegreeDaysResult | None
        ↓
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskResult
```

`RiskContext` является canonical input aggregate для Risk Calculators.

`RiskCalculator` является расчетным компонентом, а не отдельной хранимой бизнес-сущностью.

### Модель пользовательской оценки

```text
Assessment
     │
     ├────── 1 Location
     │
     ├────── 1 WeatherDataSnapshot
     │
     └────── * RiskResult
                    │
                    └────── * RiskFactorResult
```

Точный runtime- и persistence-контракт `Assessment`, включая вопрос хранения производных показателей, определяется отдельно на этапе проектирования Assessment.

---

## 5.3 Сущность UserProfile

### Назначение

Определяет группу угроз, интересующую пользователя.

Поддерживаемые значения:

```text
HUMAN
GARDEN
VEGETABLE_GARDEN
```

Пользовательские названия:

```text
Человек
Сад
Огород
```

---

## 5.4 Сущность Threat

### Назначение

Представляет конкретную биологическую угрозу.

В MVP:

```text
Иксодовые клещи

Колорадский жук

Капустная тля

Яблонная плодожорка
```

### Основные атрибуты

| Поле | Описание |
|---|---|
| id | идентификатор |
| code | внутренний код |
| name | название |
| profile | пользовательский профиль |
| description | краткое описание |
| affectedObject | объект воздействия |
| damageDescription | возможный вред |
| activeSeason | описание сезона активности |

---

## 5.5 Сущность Location

### Назначение

Представляет территорию, для которой выполняется оценка.

### Основные атрибуты

| Поле | Описание |
|---|---|
| name | населенный пункт |
| region | регион |
| country | страна |
| latitude | широта |
| longitude | долгота |

Координаты используются upstream-компонентами для получения погодных данных.

`Location` не является частью `RiskContext`.

После получения нормализованных данных Risk Calculators не должны зависеть от координат территории.

---

## 5.6 Сущность WeatherData

### Назначение

Внутренняя нормализованная модель текущих погодных наблюдений.

`WeatherData` отделяет Domain Model от структуры ответа конкретного Weather API.

### Основные атрибуты

| Поле | Описание |
|---|---|
| observedAt | дата и время наблюдения |
| temperature | температура воздуха |
| humidity | относительная влажность |
| precipitation | осадки |
| windSpeed | скорость ветра |
| soilTemperature | температура почвы на поверхности, если доступна |
| soilTemperature6cm | температура почвы на глубине 6 см, если доступна |
| soilTemperature18cm | температура почвы на глубине 18 см, если доступна |

### Архитектурная граница

`WeatherData` содержит только нормализованные погодные наблюдения.

В `WeatherData` не должны храниться:

```text
SoilTemperatureEstimate
DegreeDaysResult
RiskResult
RiskLevel
```

В частности, следующие производные значения не принадлежат `WeatherData`:

```text
soilTemperature10cmEstimate
degreeDays10c
```

Они представлены отдельными domain-моделями и передаются Risk Calculators через `RiskContext`.

---

## 5.7 Модель SoilTemperatureEstimate

### Назначение

`SoilTemperatureEstimate` представляет вычисленную оценку температуры почвы на целевой глубине.

Для текущей модели колорадского жука используется оценка температуры на глубине 10 см.

### Основные атрибуты

| Поле | Описание |
|---|---|
| depthCm | целевая глубина |
| temperature | вычисленная температура |
| sourceDepthsCm | глубины исходных наблюдений |
| sourceTemperatures | исходные температуры |
| method | метод получения оценки |

### Текущая модель

Оценка T10 формируется на основе доступных наблюдений:

```text
T6
+
T18
        ↓
SoilTemperatureEstimator
        ↓
SoilTemperatureEstimate(T10)
```

Текущий метод:

```text
LINEAR_INTERPOLATION
```

### Provenance

`SoilTemperatureEstimate` хранит не только вычисленное значение, но и сведения, позволяющие установить:

- из каких глубин оно получено;
- какие исходные температуры использовались;
- каким методом выполнен расчет.

Risk Calculator не должен самостоятельно выполнять интерполяцию.

---

## 5.8 Модель DailyTemperature

### Назначение

`DailyTemperature` представляет одно нормализованное историческое суточное температурное наблюдение.

Модель используется как вход для расчета накопленных температур.

### Основные атрибуты

| Поле | Описание |
|---|---|
| date | календарная дата |
| meanTemperature | средняя суточная температура |

Значение `meanTemperature` может отсутствовать, если достоверное наблюдение за соответствующий день недоступно.

Последовательность:

```text
DailyTemperature[]
```

представляет нормализованный исторический температурный ряд и не зависит от структуры ответа конкретного Historical Weather API.

---

## 5.9 Модель DegreeDaysResult

### Назначение

`DegreeDaysResult` представляет результат расчета суммы эффективных температур за определенный период.

Для текущей модели яблонной плодожорки используется базовая температура:

```text
10 °C
```

### Основные атрибуты

| Поле | Описание |
|---|---|
| baseTemperature | базовая температура расчета |
| total | накопленная сумма эффективных температур |
| periodStart | начало расчетного периода |
| periodEnd | конец расчетного периода |
| observations | исходные суточные наблюдения |
| method | метод расчета |

### Текущий метод

```text
DAILY_MEAN_ABOVE_BASE
```

Для каждого полного суточного наблюдения учитывается превышение средней температуры над базовой температурой.

Если температура не превышает базовое значение, вклад соответствующего дня равен нулю.

### Provenance

`DegreeDaysResult` сохраняет:

- базовую температуру;
- расчетный период;
- использованные наблюдения;
- метод расчета;
- итоговое значение.

Благодаря этому итоговый derived indicator остается воспроизводимым и объяснимым.

Risk Calculator яблонной плодожорки получает готовый `DegreeDaysResult` и не должен самостоятельно:

- обращаться к Historical Weather API;
- формировать исторический температурный ряд;
- рассчитывать сумму эффективных температур.

---

## 5.10 Модель RiskContext

### Назначение

`RiskContext` представляет canonical набор уже подготовленных данных, доступных Risk Calculators в рамках одного расчета.

Минимальная структура:

```text
RiskContext
    │
    ├── WeatherData
    │
    ├── SoilTemperatureEstimate | None
    │
    └── DegreeDaysResult | None
```

### Основные атрибуты

| Поле | Описание |
|---|---|
| weather | нормализованные текущие погодные наблюдения |
| soilTemperature10cmEstimate | производная оценка T10, если доступна |
| degreeDays10c | результат расчета накопленных температур, если доступен |

`WeatherData` является обязательной частью текущего `RiskContext`.

Производные показатели являются optional, поскольку они необходимы не всем Risk Calculators.

### Назначение границы

`RiskContext` отделяет:

```text
получение данных
+
подготовку derived indicators
```

от:

```text
применения правил конкретной угрозы
```

Таким образом:

```text
upstream preparation
        ↓
RiskContext
        ↓
RiskCalculator
```

### Что не входит в RiskContext

В текущий `RiskContext` не входят:

```text
Location
UserProfile
Threat
RiskLevel
RiskResult
Recommendation
Source
```

`Location` требуется upstream для получения погодных данных.

`Threat` определяет, какой Calculator должен быть использован, но не является расчетным входным показателем самого Calculator.

`RiskLevel` и `RiskResult` являются результатами вычисления и поэтому также не принадлежат входному контексту.

### Missing-data semantics

Отсутствие optional derived indicator не делает весь `RiskContext` невалидным.

Например:

```python
RiskContext(
    weather=weather,
    soil_temperature_10cm_estimate=None,
    degree_days_10c=None,
)
```

является допустимым состоянием.

Каждый Risk Calculator определяет достаточность только тех входных данных, которые необходимы его собственной модели.

Поэтому отсутствие `DegreeDaysResult` не должно блокировать расчет клещей или капустной тли, а отсутствие `SoilTemperatureEstimate` не должно блокировать угрозы, которым температура почвы на глубине 10 см не требуется.

## 5.11 Сущность Assessment

### Назначение

`Assessment` представляет одну выполненную пользовательскую оценку.

На концептуальном уровне Assessment объединяет:

```text
когда
+
где
+
какой профиль
+
какие исходные условия использовались
+
какие результаты получены
```

### Основные атрибуты

На текущем уровне системной модели:

| Поле | Описание |
|---|---|
| id | идентификатор |
| createdAt | дата расчета |
| profile | выбранный профиль |
| location | территория |
| weatherSnapshot | погодный снимок |
| results | результаты оценки угроз |

### Архитектурная оговорка

`Assessment` является пользовательской и исторической сущностью, тогда как `RiskContext` является runtime input aggregate для Risk Calculators.

Эти понятия не следует отождествлять:

```text
RiskContext
→ вход в расчет

Assessment
→ результат пользовательского запуска оценки
  и основа его истории
```

Точный контракт `Assessment`, включая:

- способ формирования;
- runtime orchestration;
- состав сохраняемого snapshot;
- необходимость сохранения derived indicators;
- связь с `RiskContext`;
- persistence model;

определяется отдельным архитектурным решением перед реализацией Assessment.

До принятия такого решения системная документация не предполагает, что `Assessment` обязан хранить `RiskContext` целиком.

---

## 5.12 Сущность RiskResult

### Назначение

`RiskResult` представляет итог расчета одной угрозы.

Один `RiskResult` относится к одной конкретной угрозе и формируется на основании результатов проверки ее факторов.

### Основные атрибуты

| Поле | Описание |
|---|---|
| threat | оцениваемая угроза |
| riskLevel | итоговый уровень риска |
| explanation | краткое объяснение |
| status | статус расчета |
| factors | результаты проверки отдельных факторов |

### Возможные статусы

```text
CALCULATED
LIMITED
INSUFFICIENT_DATA
ERROR
```

`RiskResult` является результатом расчетного процесса и не входит в `RiskContext`.

---

## 5.13 Сущность RiskLevel

Используются четыре значения:

```text
LOW
MODERATE
ELEVATED
HIGH
```

Пользовательские значения:

```text
Низкий
Умеренный
Повышенный
Высокий
```

`RiskLevel` является качественной категорией, а не математической вероятностью фактического присутствия угрозы.

`RiskLevel` формируется только после оценки необходимых факторов и не является входным параметром Risk Calculator.

---

## 5.14 Сущность RiskFactorResult

### Назначение

`RiskFactorResult` представляет результат проверки одного фактора конкретной расчетной модели.

Пример:

```text
factor = AIR_TEMPERATURE

state = MATCHED

actualValue = 12.0

expectedCondition = >= 10 °C
```

### Возможные состояния

```text
MATCHED

NOT_MATCHED

MISSING
```

### Основные атрибуты

| Поле | Описание |
|---|---|
| factor | идентификатор проверенного фактора |
| state | результат проверки |
| actualValue | фактическое значение |
| expectedCondition | описание ожидаемого условия |
| explanation | объяснение результата проверки |
| required | является ли фактор обязательным |

`RiskFactorResult` должен сохранять достаточную информацию, чтобы пользовательский результат оставался объяснимым.

Несколько `RiskFactorResult` используются для формирования итогового `RiskResult`.

---

## 5.15 Сущность RiskRule

### Назначение

`RiskRule` концептуально описывает предметное условие, используемое при оценке конкретной угрозы.

Примеры типов условий:

```text
SEASON

TEMPERATURE

HUMIDITY

SOIL_TEMPERATURE

DEGREE_DAYS

PRECIPITATION

WIND
```

Предметное правило должно иметь источник либо явно зафиксированное основание его происхождения.

### Текущий архитектурный статус

В runtime-архитектуре правила конкретных поддерживаемых угроз реализуются специализированными Risk Calculators.

Поэтому необходимо различать:

```text
RiskRule
→ предметное описание условия

RiskCalculator
→ программная реализация расчетной модели угрозы
```

`RiskRule` не следует автоматически считать отдельной runtime- или persistence-сущностью только на основании его присутствия в логической Domain Model.

Окончательная роль `RiskRule` в canonical модели подлежит отдельному alignment review с фактической реализацией Risk Calculators.

---

## 5.16 Сущность Recommendation

### Назначение

`Recommendation` хранит профилактическую рекомендацию для конкретной угрозы.

### Основные атрибуты

| Поле | Описание |
|---|---|
| id | идентификатор |
| threat | угроза |
| title | краткий заголовок |
| text | содержание |
| source | официальный источник |

Рекомендация относится к справочной части предметной модели и не участвует непосредственно в вычислении `RiskContext` или `RiskFactorResult`.

---

## 5.17 Сущность Source

### Назначение

`Source` представляет источник предметных сведений, использованных при формировании:

- описания угрозы;
- условий активности;
- расчетных правил;
- профилактических рекомендаций.

### Основные атрибуты

| Поле | Описание |
|---|---|
| id | идентификатор |
| organization | организация |
| title | название материала |
| url | ссылка |
| publishedAt | дата публикации, если известна |

Основные организации MVP:

```text
Роспотребнадзор

Россельхозцентр
```

### Traceability

Предметное правило или рекомендация должны иметь источник либо явно зафиксированное основание происхождения.

`Source` не является расчетным входом `RiskContext`.

Его назначение — обеспечивать предметную проверяемость и трассируемость знаний, на основании которых построена расчетная модель.

## 5.18 Основные связи

### Справочная часть

```text
UserProfile

1 -------- *

Threat
```

Один пользовательский профиль объединяет несколько поддерживаемых угроз.

```text
Threat

1 -------- *

Recommendation
```

Одна угроза может иметь несколько профилактических рекомендаций.

```text
Threat

* -------- *

Source
```

Предметные сведения об угрозе могут опираться на несколько источников, а один источник может использоваться для нескольких угроз.

Концептуальная связь предметных правил:

```text
Threat
        │
        └────── RiskRule
                    │
                    └────── Source
```

`RiskRule` описывает предметное условие.

Программная реализация условий поддерживаемой угрозы находится в соответствующем `RiskCalculator`.

---

### Погодные и производные данные

`Location` используется upstream-компонентами для получения погодных данных:

```text
Location
        ↓
получение погодных данных
        ↓
WeatherData
```

После формирования `WeatherData` координаты территории не требуются Risk Calculators непосредственно.

Для расчетных моделей, которым требуется температура почвы на глубине 10 см:

```text
WeatherData
        │
        ├── soilTemperature6cm
        │
        └── soilTemperature18cm
                    ↓
        SoilTemperatureEstimator
                    ↓
        SoilTemperatureEstimate
```

Для моделей, которым требуется накопленная температура:

```text
Historical Weather Data
        ↓
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult
```

`SoilTemperatureEstimate` и `DegreeDaysResult` являются отдельными derived domain objects и не входят в `WeatherData`.

---

### RiskContext

Подготовленные данные объединяются в расчетный контекст:

```text
WeatherData
        +
SoilTemperatureEstimate | None
        +
DegreeDaysResult | None
        ↓
RiskContext
```

Связи имеют следующую семантику:

```text
RiskContext

1 -------- 1

WeatherData
```

и:

```text
RiskContext

0..1 -------- 1

SoilTemperatureEstimate
```

```text
RiskContext

0..1 -------- 1

DegreeDaysResult
```

`WeatherData` является обязательным элементом текущего `RiskContext`.

Derived indicators являются optional.

---

### Расчет риска

Canonical calculation boundary:

```text
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskEngine / RiskPolicy
        ↓
RiskResult
```

Каждый специализированный Risk Calculator получает единый тип входных данных — `RiskContext`.

Calculator использует только необходимые ему части context.

Примеры:

```text
TickRiskCalculator
→ RiskContext.weather.temperature
```

```text
CabbageAphidRiskCalculator
→ RiskContext.weather.temperature
→ RiskContext.weather.humidity
```

```text
ColoradoBeetleRiskCalculator
→ RiskContext.soilTemperature10cmEstimate
```

```text
CodlingMothRiskCalculator
→ RiskContext.degreeDays10c
```

`RiskCalculator` не должен самостоятельно получать или вычислять отсутствующие входные данные.

---

### Результаты расчета

```text
RiskResult

1 -------- *

RiskFactorResult
```

Один результат угрозы содержит результаты проверенных факторов.

На концептуальном уровне:

```text
Assessment

1 -------- *

RiskResult
```

Одна пользовательская оценка может содержать результаты нескольких угроз.

Точный persistence contract этой связи определяется при проектировании `Assessment`.

---

## 5.19 Основные бизнес-правила Domain Model

### BR-001

Каждый `Threat` принадлежит одному пользовательскому профилю MVP.

---

### BR-002

Каждый `RiskResult` относится ровно к одной угрозе.

---

### BR-003

Одна пользовательская оценка может содержать несколько `RiskResult`.

---

### BR-004

Исторический `Assessment` должен сохранять достаточный snapshot исходных данных, чтобы изменение текущих погодных условий не изменяло уже сохраненный результат.

Точный состав snapshot определяется контрактом Assessment.

---

### BR-005

Изменение текущих погодных данных не должно изменять уже сохраненный исторический Assessment.

---

### BR-006

`RiskLevel` не является вероятностью фактического присутствия вредителя или иного биологического объекта.

Он характеризует соответствие доступных условий принятой расчетной модели риска.

---

### BR-007

При отсутствии обязательных данных система не должна подменять отсутствующий показатель произвольным значением только для получения обычного `RiskLevel`.

Если данных недостаточно для конкретной модели, результат должен отражать состояние недостаточности данных в соответствии с Risk Policy.

---

### BR-008

Каждое предметное правило должно иметь источник либо явно зафиксированное основание его происхождения.

---

### BR-009

`WeatherData` содержит нормализованные погодные наблюдения и не является владельцем derived indicators.

Следующие модели существуют отдельно:

```text
SoilTemperatureEstimate
DegreeDaysResult
```

---

### BR-010

Derived indicator должен сохранять provenance, достаточный для объяснения и воспроизведения способа получения результата.

Для `SoilTemperatureEstimate` provenance включает как минимум:

```text
sourceDepthsCm
sourceTemperatures
method
```

Для `DegreeDaysResult`:

```text
baseTemperature
periodStart
periodEnd
observations
method
```

---

### BR-011

`RiskContext` является canonical input aggregate для Risk Calculators.

Risk Calculators не должны использовать `WeatherData` как альтернативный самостоятельный входной контракт.

---

### BR-012

Отсутствие одного optional derived indicator в `RiskContext` не делает весь context невалидным.

Достаточность данных определяется отдельно для расчетной модели каждой угрозы.

Например:

```text
degreeDays10c = None
```

не препятствует расчету угрозы, которая использует только текущую температуру воздуха.

---

### BR-013

Risk Calculator не должен:

- обращаться к Weather API;
- обращаться к Historical Weather API;
- выполнять инфраструктурный поиск данных;
- самостоятельно формировать отсутствующие derived indicators.

Calculator отвечает только за интерпретацию уже подготовленного `RiskContext` в рамках модели конкретной угрозы.

---

### BR-014

Одинаковые входные domain-данные и одинаковая версия расчетных правил должны приводить к воспроизводимому результату.

---

### BR-015

Derived indicator представляет вычисленный environmental/domain fact и не содержит интерпретацию риска конкретной угрозы.

---

### BR-016

Предметный threshold конкретной угрозы применяется Risk Calculator и не должен переноситься в универсальную derived domain model.

---

### BR-017

Derived indicator должен сохранять provenance, необходимый для воспроизведения собственного вычисления, но не обязан хранить полный integration или Assessment audit trail.

---

### BR-018

Если исходных данных недостаточно для корректного вычисления derived indicator, система не должна создавать приблизительное или искусственное значение без отдельно утвержденного правила.

---

### BR-019

`RiskCalculator` отвечает за формирование threat-specific `RiskFactorResult[]`.

`RiskCalculator` не определяет итоговый `RiskStatus` и `RiskLevel`.

Итоговая интерпретация factor evidence является ответственностью `RiskPolicy`.

---

### BR-020

`RiskStatus.ERROR` не выводится из состояний `MATCHED`, `NOT_MATCHED` и `MISSING`.

`ERROR` представляет техническую невозможность выполнить расчет и должен формироваться orchestration/application layer в соответствии с контрактом Assessment.

---

## 5.20 Граница жизненного цикла Assessment

Полный жизненный цикл `Assessment` еще не является утвержденным runtime-контрактом.

На текущем этапе достоверно определена следующая часть pipeline:

```text
Location
        ↓
получение текущих погодных данных
        ↓
WeatherData

Historical Weather Data
        ↓
DailyTemperature[]
        ↓
DegreeDaysResult

WeatherData
        ↓
SoilTemperatureEstimate

WeatherData
        +
доступные derived indicators
        ↓
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskEngine / RiskPolicy
        ↓
RiskResult
```

Следующая часть пользовательского сценария концептуально выглядит как:

```text
RiskResult[]
        ↓
Assessment
        ↓
Persistence
        ↓
History
```

но ее точный контракт должен быть определен отдельно.

До утверждения Assessment Architecture настоящая модель не фиксирует:

```text
RiskContextBuilder

RiskContextFactory

AssessmentService implementation

Assessment → RiskContext ownership

хранение RiskContext целиком

хранение SoilTemperatureEstimate в Assessment

хранение DegreeDaysResult в Assessment

точную persistence-схему derived indicators
```

Таким образом, настоящий раздел фиксирует существующую calculation boundary, но не предрешает архитектуру следующего этапа.

---

## 5.21 Итог Domain Model

После разделения responsibilities центральная расчетная модель PestWatch выглядит следующим образом:

```text
                    Location
                       │
                       ▼
                  WeatherData
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   │
SoilTemperatureEstimate          │
                                 │
DailyTemperature[]               │
        │                        │
        ▼                        │
 DegreeDaysResult                │
        │                        │
        └────────────┬───────────┘
                     ▼
                RiskContext
                     │
                     ▼
               RiskCalculator
                     │
                     ▼
            RiskFactorResult[]
                     │
                     ▼
             RiskEngine / Policy
                     │
                     ▼
                 RiskResult
```

Справочная часть определяет:

```text
UserProfile
→ какие угрозы относятся к пользовательскому сценарию

Threat
→ что оцениваем

RiskRule
→ какое предметное условие лежит в основе проверки

Recommendation
→ какие профилактические действия могут быть предложены

Source
→ на каком основании сформированы предметные сведения
```

Расчетная часть определяет:

```text
WeatherData
→ какие текущие погодные наблюдения доступны

DailyTemperature
→ какие исторические суточные наблюдения доступны

SoilTemperatureEstimate
→ какой derived soil indicator рассчитан и откуда он получен

DegreeDaysResult
→ какой accumulated indicator рассчитан и на основании каких данных

RiskContext
→ какие подготовленные данные доступны конкретному расчету

RiskFactorResult
→ какой результат дала отдельная проверка

RiskResult
→ каков итог оценки конкретной угрозы
```

`WeatherData` больше не является универсальным контейнером всех данных, необходимых Risk Engine.

Canonical calculation input:

```text
RiskContext
```

При этом `RiskContext` не является:

- пользовательской оценкой;
- исторической записью;
- persistence entity;
- источником данных;
- владельцем бизнес-правил;
- результатом расчета.

Его ответственность ограничена передачей уже подготовленных domain inputs через стабильную границу:

```text
data preparation
        ↓
RiskContext
        ↓
risk interpretation
```

Пользовательская оценка остается отдельным понятием:

```text
RiskResult[]
        ↓
Assessment
```

и ее окончательная runtime- и persistence-модель определяется следующим архитектурным этапом.

Таким образом, Domain Model после EPIC-09 устанавливает четыре явные границы:

```text
1. Provider observations
   → WeatherData / DailyTemperature

2. Derived calculations
   → SoilTemperatureEstimate / DegreeDaysResult

3. Risk calculation input
   → RiskContext

4. Risk calculation output
   → RiskFactorResult / RiskResult
```

Эта модель является основой для дальнейшего проектирования:

- Assessment;
- orchestration получения необходимых данных;
- persistence snapshot;
- REST-контракта оценки;
- истории пользовательских расчетов;
- последующих расширений Risk Calculators.

# 6. Алгоритмы работы системы

## 6.1 Назначение раздела

Настоящий раздел определяет внутреннюю последовательность обработки данных приложением.

Алгоритмы описывают:

- получение погодных данных;
- запуск оценки;
- выбор расчетной модели;
- проверку факторов;
- определение уровня риска;
- работу с отсутствующими данными;
- формирование объяснения;
- сохранение результата.

Алгоритмы Risk Engine должны быть:

- детерминированными;
- объяснимыми;
- воспроизводимыми;
- независимыми от пользовательского интерфейса.

---

## 6.2 Общий алгоритм подготовки и оценки риска

Расчетная часть системы состоит из нескольких последовательных стадий:

```text
получить Location
        ↓
получить текущие погодные данные
        ↓
WeatherData
        ↓
при необходимости получить исторические данные
        ↓
DailyTemperature[]
        ↓
при необходимости рассчитать derived indicators
        ↓
SoilTemperatureEstimate
DegreeDaysResult
        ↓
сформировать RiskContext
        ↓
получить UserProfile
        ↓
определить Threat[]
        ↓
для каждой Threat
        ↓
выбрать соответствующий RiskCalculator
        ↓
передать RiskContext
        ↓
получить RiskFactorResult[]
        ↓
RiskEngine / RiskPolicy
        ↓
сформировать RiskResult
        ↓
объединить результаты
```

До этапа:

```text
RiskResult[]
```

данный алгоритм описывает реализованную calculation boundary.

Следующая часть пользовательского сценария:

```text
RiskResult[]
        ↓
Assessment
        ↓
Persistence
        ↓
History
```

является концептуальной и уточняется отдельным архитектурным контрактом Assessment.

### Основной принцип

Получение погодных данных, расчет derived indicators и интерпретация риска являются разными ответственностями:

```text
provider integration
        ↓
normalized domain observations
        ↓
derived calculations
        ↓
RiskContext
        ↓
risk interpretation
```

Risk Calculator не должен самостоятельно получать внешние данные или вычислять отсутствующие derived indicators.

---

## 6.3 Алгоритм получения текущих погодных данных

### Входные данные

`Location`.

Для обращения к внешнему погодному сервису используются:

```text
latitude
longitude
```

### Последовательность

```text
Location
        ↓
WeatherService
        ↓
WeatherClient
        ↓
Current Weather API
        ↓
raw provider payload
        ↓
WeatherAdapter
        ↓
WeatherData
```

### Ответственность WeatherClient

`WeatherClient` отвечает за HTTP-взаимодействие с внешним provider:

- формирование параметров запроса;
- выполнение HTTP-запроса;
- применение настроенного timeout;
- обработку транспортных ошибок;
- обработку неуспешного HTTP-ответа.

`WeatherClient` не должен:

- рассчитывать риск;
- выполнять интерполяцию температуры почвы;
- рассчитывать накопленные температуры;
- создавать `RiskContext`.

### Ответственность WeatherAdapter

`WeatherAdapter` преобразует внешний provider payload во внутреннюю domain-модель:

```text
provider payload
        ↓
WeatherAdapter
        ↓
WeatherData
```

Adapter изолирует остальную систему от структуры внешнего API.

### Ответственность WeatherService

`WeatherService` координирует:

```text
Location
        ↓
WeatherClient
        ↓
WeatherAdapter
        ↓
WeatherData
```

После получения нормализованного `WeatherData` его ответственность заканчивается.

`WeatherService` не должен:

- рассчитывать `SoilTemperatureEstimate`;
- получать historical weather;
- рассчитывать `DegreeDaysResult`;
- создавать `RiskContext`;
- запускать Risk Calculators;
- определять `RiskLevel`.

### Результат

```text
WeatherData
```

Внутренний объект не зависит от структуры конкретного Weather API.

---

## 6.4 Валидация и нормализация текущих погодных данных

Integration layer должен гарантировать, что во внутреннюю систему передаются структурно корректные нормализованные наблюдения.

При обработке provider response необходимо различать:

```text
транспортную ошибку
структурно некорректный payload
отсутствующее наблюдение
недостаточность данных для конкретной risk model
```

Это разные состояния.

### Транспортные ошибки

К транспортным ошибкам относятся, например:

```text
timeout
HTTP 4xx
HTTP 5xx
network failure
```

Они обрабатываются integration layer и не преобразуются в значения `WeatherData`.

### Некорректный payload

Ошибкой integration layer являются, например:

- отсутствие обязательной структуры ответа;
- отсутствие времени наблюдения, если оно обязательно для нормализации;
- некорректный формат времени;
- значение неожиданного типа;
- payload, который невозможно однозначно преобразовать во внутреннюю модель.

Некорректные данные не должны представляться системе как достоверные погодные наблюдения.

### Отсутствующие optional observations

Отсутствие отдельного погодного показателя само по себе не обязательно означает ошибку provider response.

Например:

```text
humidity = None

soilTemperature6cm = None

soilTemperature18cm = None
```

могут быть корректным состоянием нормализованного `WeatherData`.

Integration layer должен сохранить факт отсутствия значения:

```text
missing provider observation
        ↓
None
```

и не подменять его:

```text
0
средним значением
предыдущим значением
произвольным fallback
```

только для возможности продолжить расчет.

### Integration validity и Risk sufficiency

Следует различать:

```text
integration validity
```

и:

```text
risk sufficiency
```

Например:

```text
WeatherData(
    temperature=18.0,
    humidity=None
)
```

может быть корректным результатом Weather Integration.

При этом:

```text
TickRiskCalculator
```

может иметь достаточно данных для своей модели, а:

```text
CabbageAphidRiskCalculator
```

может сформировать для humidity:

```text
RiskFactorState.MISSING
```

Решение о достаточности данных для конкретной угрозы принимает risk layer, а не `WeatherAdapter` и не `WeatherService`.

## 6.5 Алгоритм получения исторических погодных данных

### Назначение

Historical Weather pipeline используется для расчетных моделей, которым недостаточно текущего погодного snapshot.

Текущий пример:

```text
яблонная плодожорка
        ↓
накопленная сумма эффективных температур
```

### Входные данные

Для historical request используются:

```text
Location
+
startDate
+
endDate
```

Из `Location` используются координаты территории.

### Последовательность

```text
Location
+
period
        ↓
HistoricalWeatherService
        ↓
HistoricalWeatherClient
        ↓
Historical Weather API
        ↓
raw historical payload
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

### Ответственность HistoricalWeatherClient

`HistoricalWeatherClient` отвечает за:

- формирование запроса по координатам;
- передачу периода;
- HTTP-взаимодействие с historical provider;
- применение отдельного timeout;
- обработку transport/provider errors.

Он не рассчитывает Degree Days.

### Ответственность HistoricalWeatherAdapter

`HistoricalWeatherAdapter` преобразует provider-specific historical payload в:

```text
DailyTemperature[]
```

Adapter отвечает за нормализацию исторических суточных наблюдений.

Он не должен:

- рассчитывать сумму эффективных температур;
- применять threshold конкретной угрозы;
- формировать `RiskFactorResult`;
- создавать `RiskResult`.

### Ответственность HistoricalWeatherService

`HistoricalWeatherService` координирует:

```text
Location + period
        ↓
HistoricalWeatherClient
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

### Результат

```text
DailyTemperature[]
```

Historical Weather pipeline не возвращает `WeatherData`.

Текущие погодные наблюдения и исторический суточный ряд являются различными domain representations:

```text
Current Weather
→ WeatherData

Historical Weather
→ DailyTemperature[]
```

## 6.6 Алгоритм расчета производных погодных показателей

После завершения provider integration нормализованные domain observations могут использоваться для расчета derived indicators.

Derived calculation не является обязанностью Weather Adapter или Weather Client.

### 6.6.1 Оценка температуры почвы на глубине 10 см

Для модели колорадского жука используется вычисленная температура почвы на глубине 10 см.

Исходные данные:

```text
WeatherData.soilTemperature6cm
WeatherData.soilTemperature18cm
```

Последовательность:

```text
T6
+
T18
        ↓
SoilTemperatureEstimator
        ↓
SoilTemperatureEstimate
```

`SoilTemperatureEstimator` выполняет domain calculation после завершения provider normalization.

Текущий метод:

```text
LINEAR_INTERPOLATION
```

Результат:

```text
SoilTemperatureEstimate
```

содержит:

- целевую глубину;
- вычисленное значение;
- исходные глубины;
- исходные температуры;
- метод расчета.

Если исходных данных недостаточно для корректной оценки, estimator не должен создавать вымышленное значение.

### Архитектурная граница

```text
WeatherAdapter
→ наблюдения

SoilTemperatureEstimator
→ derived indicator
```

`WeatherAdapter` не должен выполнять интерполяцию.

`ColoradoBeetleRiskCalculator` не должен выполнять интерполяцию.

---

### 6.6.2 Расчет суммы эффективных температур

Для модели яблонной плодожорки используется сумма эффективных температур относительно базовой температуры:

```text
10 °C
```

Исходные данные:

```text
DailyTemperature[]
```

Последовательность:

```text
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult
```

Текущий метод:

```text
DAILY_MEAN_ABOVE_BASE
```

Для каждого доступного суточного наблюдения вычисляется вклад относительно базовой температуры.

Если средняя температура не превышает base temperature:

```text
daily contribution = 0
```

Результат:

```text
DegreeDaysResult
```

сохраняет:

- base temperature;
- total;
- начало периода;
- конец периода;
- исходные observations;
- method.

### Недостаток исторических данных

Если историческая последовательность не содержит данных, необходимых для достоверного расчета, система не должна подменять отсутствующие наблюдения произвольными значениями.

Невозможность сформировать корректный `DegreeDaysResult` должна сохраняться как отсутствие соответствующего derived indicator на следующем этапе.

### Архитектурная граница

```text
HistoricalWeatherAdapter
→ DailyTemperature[]

DegreeDaysCalculator
→ DegreeDaysResult
```

`HistoricalWeatherAdapter` не рассчитывает Degree Days.

`CodlingMothRiskCalculator` не рассчитывает Degree Days и не обращается к Historical Weather API.

Derived calculation преобразует нормализованные наблюдения в новый domain fact:

```text
normalized observations
        ↓
deterministic calculation
        ↓
derived domain result

## 6.7 Формирование расчетного контекста

После получения доступных observations и derived indicators система формирует расчетный input aggregate:

```text
WeatherData
        +
SoilTemperatureEstimate | None
        +
DegreeDaysResult | None
        ↓
RiskContext
```

`RiskContext` содержит только уже подготовленные domain inputs.

### Минимальная структура

```text
RiskContext
    │
    ├── weather
    │
    ├── soilTemperature10cmEstimate | None
    │
    └── degreeDays10c | None
```

`WeatherData` является обязательным элементом текущего contract.

Derived indicators являются optional.

### Принцип независимости угроз

Система не должна требовать наличия всех возможных derived indicators перед запуском любого calculator.

Например:

```text
RiskContext
    weather = available
    soilTemperature10cmEstimate = None
    degreeDays10c = None
```

может быть достаточен для:

```text
TickRiskCalculator
```

или части других моделей.

Каждый calculator оценивает достаточность только собственных inputs.

### Граница ответственности

Формирование `RiskContext` отделяет:

```text
data acquisition
+
data normalization
+
derived calculation
```

от:

```text
risk interpretation
```

После формирования context:

```text
RiskContext
        ↓
RiskCalculator
```

Risk Calculator не должен обращаться обратно к provider integration для получения отсутствующих данных.

### Orchestration

Точный production-компонент, который будет координировать получение всех необходимых данных и собирать `RiskContext`, пока не фиксируется.

В частности, настоящий раздел не вводит:

```text
RiskContextBuilder
RiskContextFactory
AssessmentService implementation
```

Это является deferred architecture decision следующего этапа — Assessment.

После выбора `UserProfile` система определяет набор угроз, относящихся к выбранному пользовательскому сценарию.

```text
HUMAN
        ↓
TICK
```

```text
GARDEN
        ↓
CODLING_MOTH
```

```text
VEGETABLE_GARDEN
        ↓
COLORADO_BEETLE
CABBAGE_APHID
```

Список угроз определяется системой и не вводится пользователем вручную.

`UserProfile` используется для определения:

```text
какие Threat должны быть оценены
```

но не является частью `RiskContext`.

После определения угрозы система выбирает соответствующую расчетную модель.

## 6.9 Выбор расчетной модели

Для каждой поддерживаемой угрозы существует отдельный специализированный `RiskCalculator`.

Соответствие:

```text
TICK
→ TickRiskCalculator

COLORADO_BEETLE
→ ColoradoBeetleRiskCalculator

CABBAGE_APHID
→ CabbageAphidRiskCalculator

CODLING_MOTH
→ CodlingMothRiskCalculator
```

Все calculators используют единый входной contract:

```python
evaluate(
    context: RiskContext,
) -> tuple[RiskFactorResult, ...]
```

Таким образом:

```text
Threat
        ↓
выбор calculator
        ↓
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
```

`Threat` определяет, какой calculator необходимо вызвать.

При этом сам `Threat` не передается calculator как часть расчетного input aggregate.

Если calculator для угрозы отсутствует, система не должна:

- использовать calculator другой угрозы;
- подменять расчет универсальной fallback-моделью;
- создавать вымышленный `RiskResult`.

### Архитектурная граница

`RiskCalculator` не отвечает за:

```text
выбор Threat

получение WeatherData

получение historical weather

формирование derived indicators

формирование RiskContext

определение общего RiskStatus

создание итогового RiskResult
```

Его ответственность ограничена проверкой факторов конкретной угрозы.

## 6.10 Общий алгоритм Risk Calculator

Несмотря на различие предметных правил, все Risk Calculators работают через единый тип входа:

```text
RiskContext
```

Общий алгоритм:

```text
получить RiskContext
        ↓
извлечь только необходимые
для данной угрозы inputs
        ↓
для каждого фактора
        ↓
проверить наличие значения
        ↓
сравнить значение
с предметным условием
        ↓
сформировать RiskFactorResult
        ↓
вернуть RiskFactorResult[]
```

Результатом работы calculator является:

```text
RiskFactorResult[]
```

а не готовый `RiskResult`.

### Пример

Для клещей:

```text
RiskContext
        ↓
context.weather.temperature
        ↓
TickRiskCalculator
        ↓
AIR_TEMPERATURE RiskFactorResult
```

Для капустной тли:

```text
RiskContext
        ↓
context.weather.temperature
+
context.weather.humidity
        ↓
CabbageAphidRiskCalculator
        ↓
RiskFactorResult[]
```

Для колорадского жука:

```text
RiskContext
        ↓
context.soilTemperature10cmEstimate
        ↓
ColoradoBeetleRiskCalculator
        ↓
SOIL_TEMPERATURE_10CM RiskFactorResult
```

Для яблонной плодожорки:

```text
RiskContext
        ↓
context.degreeDays10c
        ↓
CodlingMothRiskCalculator
        ↓
DEGREE_DAYS_ABOVE_10C RiskFactorResult
```

### Calculator не должен получать данные

Calculator не должен:

- обращаться к Weather API;
- обращаться к Historical Weather API;
- вызывать `WeatherService`;
- вызывать `HistoricalWeatherService`;
- выполнять interpolation T10;
- рассчитывать Degree Days.

Если необходимый indicator отсутствует в `RiskContext`, calculator фиксирует это через:

```text
RiskFactorState.MISSING
```

а не пытается получить или восстановить данные самостоятельно.

## 6.11 Проверка отдельного фактора

Каждая предметная проверка возвращает не `true/false`, а полноценный `RiskFactorResult`.

Пример:

```text
RiskFactorResult

factor = AIR_TEMPERATURE

state = MATCHED

actualValue = 25.4

expected = "25–26 °C"

required = true

explanation =
"Температура находится в диапазоне,
благоприятном для активности."
```

### Назначение RiskFactorResult

`RiskFactorResult` фиксирует:

```text
что проверялось
+
какие данные использовались
+
какое условие ожидалось
+
какой результат получен
+
почему получен такой результат
+
является ли фактор обязательным
```

Это позволяет:

- отделить проверку фактора от итоговой оценки риска;
- объяснить пользователю результат;
- корректно обрабатывать отсутствующие данные;
- передать структурированные evidence в `RiskEngine`.

### Фактическое значение

Если показатель доступен:

```text
actualValue = фактическое значение
```

Например:

```text
12.3
65.0
14.2
137.4
```

Если показатель отсутствует:

```text
actualValue = None
```

Не допускается подставлять искусственное значение только для выполнения правила.

---

## 6.12 Состояния факторов

Поддерживаются три состояния:

```text
MATCHED
NOT_MATCHED
MISSING
```

### MATCHED

Данные существуют и предметное условие выполняется.

Пример:

```text
actual:
25.4 °C

condition:
25–26 °C

result:
MATCHED
```

---

### NOT_MATCHED

Данные существуют, но предметное условие не выполняется.

Пример:

```text
actual:
15 °C

condition:
25–26 °C

result:
NOT_MATCHED
```

---

### MISSING

Необходимое значение отсутствует.

Пример:

```text
humidity:
None

result:
MISSING
```

или:

```text
soilTemperature10cmEstimate:
None

result:
MISSING
```

или:

```text
degreeDays10c:
None

result:
MISSING
```

`MISSING` принципиально отличается от `NOT_MATCHED`.

```text
NOT_MATCHED
→ данные есть, условие не выполнено

MISSING
→ данных для проверки нет
```

Отсутствующий фактор не должен автоматически трактоваться как неблагоприятное условие.

### Required factors

`RiskFactorResult.required` указывает, требуется ли соответствующий фактор для корректного вычисления конкретной модели.

Наличие:

```text
required = true
state = MISSING
```

является evidence недостаточности данных для последующего `RiskEngine / RiskPolicy`.

Сам calculator при этом не должен создавать фиктивный итоговый уровень риска.

---

## 6.13 Формирование итогового результата риска

После завершения calculator stage система получает:

```text
RiskFactorResult[]
```

Далее calculator больше не участвует в orchestration итогового результата.

Последовательность:

```text
RiskFactorResult[]
        ↓
RiskEngine
        ↓
RiskPolicy
        ↓
RiskResult
```

### Ответственность RiskEngine

`RiskEngine` координирует формирование результата оценки угрозы на основании уже рассчитанных факторов.

Он получает:

```text
threatCode
+
RiskFactorResult[]
```

и формирует итоговый `RiskResult`.

### Ответственность RiskPolicy

`RiskPolicy` интерпретирует комбинацию состояний факторов и определяет итоговое состояние оценки.

В частности, policy учитывает:

```text
MATCHED
NOT_MATCHED
MISSING
required
```

### Недостаточность данных

Если обязательный factor находится в состоянии:

```text
MISSING
```

итоговая оценка не должна притворяться обычным рассчитанным risk level.

Результат должен отражать:

```text
RiskStatus.INSUFFICIENT_DATA
```

и отсутствие обычного `RiskLevel`, если данных действительно недостаточно.

### Расчет при достаточных данных

Если обязательные данные присутствуют:

```text
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskStatus.CALCULATED
+
RiskLevel
```

Используемые уровни:

```text
LOW
MODERATE
ELEVATED
HIGH
```

`RiskLevel` является качественной категорией расчетной модели.

Процентная вероятность фактического присутствия вредителя не рассчитывается.

### Разделение ответственности

Итоговая граница:

```text
RiskCalculator
→ проверяет факторы

RiskEngine / RiskPolicy
→ интерпретирует факторы
  и формирует итог оценки
```

Следовательно:

```text
RiskCalculator
≠ RiskEngine

RiskFactorResult
≠ RiskResult
```

Это разделение позволяет независимо тестировать:

- предметные thresholds конкретного calculator;
- missing semantics;
- общую policy формирования результата;
- итоговую интеграцию calculator → engine.
---

## 6.14 Алгоритм оценки риска иксодовых клещей

### Назначение

Оценить соответствие текущей температуры воздуха условию расчетной модели активности иксодовых клещей.

Текущая MVP-модель использует один обязательный фактор:

```text
AIR_TEMPERATURE
```

### Входные данные

Calculator получает:

```text
RiskContext.weather.temperature
```

`Location`, `AssessmentDate` и `UserProfile` не являются входными факторами `TickRiskCalculator`.

### Порог

Используемое условие:

```text
temperature >= 10 °C
```

### Алгоритм

```text
RiskContext
        ↓
weather.temperature
        ↓
значение отсутствует?
        │
   ┌────┴────┐
   ▼         ▼
  Да         Нет
   │          │
   ▼          ▼
MISSING    temperature >= 10?
                │
           ┌────┴────┐
           ▼         ▼
          Да         Нет
           │          │
           ▼          ▼
        MATCHED   NOT_MATCHED
```

Calculator формирует один:

```text
RiskFactorResult(
    factor = AIR_TEMPERATURE,
    required = true
)
```

### Итоговая интерпретация

При достаточных данных:

```text
MATCHED
        ↓
HIGH
```

```text
NOT_MATCHED
        ↓
LOW
```

При:

```text
MISSING
```

итоговый результат имеет:

```text
RiskStatus = INSUFFICIENT_DATA
RiskLevel = None
```

### Граница текущего MVP

Сезон активности и территориальный контекст могут иметь предметное значение, однако в текущей реализованной модели они не являются факторами `TickRiskCalculator`.

Поэтому документация не должна представлять:

```text
SEASON
Location
AssessmentDate
```

как уже реализованные calculator inputs.

Добавление таких факторов требует отдельного изменения расчетного контракта, предметного обоснования и тестов.

## 6.18 Обработка недостаточных данных

Недостаточность данных определяется не integration layer и не самим `RiskContext`, а на уровне конкретной risk model и последующей Risk Policy.

### Общий принцип

Каждый `RiskFactorResult` содержит:

```text
state
required
```

Ключевое различие:

```text
NOT_MATCHED
→ данные доступны,
  но предметное условие не выполнено

MISSING
→ данных для проверки фактора нет
```

`MISSING` не должен автоматически преобразовываться в:

```text
NOT_MATCHED
LOW
0
false
```

### Required factor

Если calculator сформировал:

```text
RiskFactorResult(
    required = true,
    state = MISSING
)
```

это является evidence того, что данных для полной оценки конкретной угрозы недостаточно.

Для реализованных текущих сценариев такой результат приводит к:

```text
RiskStatus = INSUFFICIENT_DATA
RiskLevel = None
```

### Независимость угроз

Недостаточность данных для одной угрозы не означает недостаточность всего `RiskContext`.

Например:

```text
weather.temperature = available
weather.humidity = available

soilTemperature10cmEstimate = None
degreeDays10c = None
```

такой context может позволять выполнить:

```text
TickRiskCalculator
CabbageAphidRiskCalculator
```

и одновременно давать недостаточность данных для:

```text
ColoradoBeetleRiskCalculator
CodlingMothRiskCalculator
```

Следовательно:

```text
data sufficiency
```

определяется отдельно для каждой threat model.

### LIMITED

`RiskStatus.LIMITED` остается частью общей предметной модели, однако его точная runtime-semantics должна быть зафиксирована отдельно в `RiskPolicy`.

Настоящий раздел не вводит новое правило, автоматически преобразующее любую комбинацию отсутствующих optional factors в `LIMITED`.

До утверждения такого policy-rule используются только явно определенные calculator/policy semantics.

---

## 6.19 Формирование объяснения результата

Объяснимость строится на структурированных результатах факторов.

Основой являются:

```text
RiskFactorResult[]
```

Каждый factor result уже содержит:

```text
factor
state
actualValue
expected
required
explanation
```

Поэтому объяснение не должно формироваться из случайно выбранного текста, не связанного с фактически выполненной проверкой.

### Пример

```text
factor = HUMIDITY
state = NOT_MATCHED
actualValue = 50.0
expected = "60–70 %"
explanation =
"Влажность не находится в благоприятном диапазоне."
```

Пользовательское представление может быть построено на этих данных:

```text
RiskFactorResult[]
        ↓
presentation formatting
        ↓
объяснение для пользователя
```

### Архитектурная граница

Настоящая архитектура не требует обязательного отдельного runtime-компонента:

```text
ExplanationBuilder
```

только потому, что такое понятие присутствовало в первоначальном алгоритме.

Canonical source объяснения на текущем этапе:

```text
RiskFactorResult.explanation
+
итоговый RiskResult
```

Если в дальнейшем потребуется отдельный механизм композиции объяснений, он должен быть введен отдельным архитектурным решением.

---

## 6.20 Формирование рекомендаций

Рекомендации не рассчитываются Risk Engine заново.

После определения угрозы система получает заранее подготовленные рекомендации:

```text
Threat
        ↓
Recommendation[]
```

Например:

```text
TICK
        ↓
профилактика контакта
```

```text
CABBAGE_APHID
        ↓
рекомендация провести осмотр растений
```

Каждая рекомендация должна иметь предметное основание и источник.

### Разделение ответственности

```text
Risk Calculator / Risk Engine
→ определяют результат оценки

Recommendation
→ справочная профилактическая информация
```

`Recommendation` не входит в `RiskContext` и не является входным фактором Risk Calculator.

---

## 6.21 Граница формирования и сохранения Assessment

После завершения расчетной части система имеет:

```text
Location
UserProfile
RiskResult[]
```

а также набор входных данных, использованных для расчета.

На концептуальном уровне следующий шаг:

```text
результаты расчета
+
assessment input snapshot
        ↓
Assessment
        ↓
Persistence
        ↓
History
```

Однако точный состав:

```text
assessment input snapshot
```

настоящим разделом не фиксируется.

### Почему старого WeatherData snapshot недостаточно для утвержденного контракта

После развития модели расчет может использовать не только:

```text
WeatherData
```

но также:

```text
SoilTemperatureEstimate
DegreeDaysResult
historical observations
```

Поэтому прежняя схема:

```text
Location
+
WeatherData
+
UserProfile
+
RiskResult[]
        ↓
Assessment
```

не должна считаться окончательным persistence contract.

### Deferred decisions

До проектирования Assessment не фиксируются:

```text
Assessment → RiskContext

Assessment хранит RiskContext целиком

Assessment хранит DegreeDaysResult

Assessment хранит SoilTemperatureEstimate

Assessment хранит DailyTemperature[]

точный WeatherSnapshot contract

точная схема persistence derived indicators
```

При этом сохраняется обязательный системный принцип:

> Исторический результат должен быть воспроизводим из сохраненных данных и не должен изменяться вслед за изменением текущей погоды.

Точный способ выполнения этого требования определяется Assessment Architecture.

---

## 6.22 Обработка ошибки отдельной расчетной модели

Расчет разных угроз должен оставаться независимым.

Если техническая ошибка возникает при обработке одной угрозы, она не должна автоматически превращать корректные результаты остальных угроз в ошибочные.

Концептуально допустимо:

```text
Threat A
→ CALCULATED

Threat B
→ ERROR
```

при выполнении следующих условий:

- корректные результаты других угроз не повреждены;
- ошибочная угроза явно помечена;
- пользователь не получает вымышленный `RiskLevel`;
- техническая ошибка не маскируется под `LOW`, `NOT_MATCHED` или `MISSING`.

### Различие domain- и technical-state

Следует различать:

```text
MISSING
→ необходимое domain-значение отсутствует
```

и:

```text
ERROR
→ расчет не выполнен из-за технической ошибки
```

Эти состояния не взаимозаменяемы.

Точный orchestration partial assessment определяется вместе с Assessment contract.

---

## 6.23 Итог алгоритмов

Актуальный расчетный pipeline после развития MVP выглядит следующим образом:

```text
Location
        ↓
Current Weather Integration
        ↓
WeatherData
        │
        ├───────────────┐
        │               │
        ▼               │
SoilTemperatureEstimator
        │               │
        ▼               │
SoilTemperatureEstimate │
                        │
Historical Weather Integration
        ↓               │
DailyTemperature[]      │
        ↓               │
DegreeDaysCalculator    │
        ↓               │
DegreeDaysResult        │
        │               │
        └───────┬───────┘
                ▼
          UserProfile
                ↓
            Threat[]
                ↓
         выбор RiskCalculator
             ▲
             │
         RiskContext
                │
                ▼
   соответствующий RiskCalculator
                │
                ▼
       RiskFactorResult[]
                │
                ▼
      RiskEngine / RiskPolicy
                │
                ▼
            RiskResult[]
                │
                ├──────→ Recommendation[]
                │
                ▼
        Assessment boundary
                │
                ▼
             History
```

### Основные границы

```text
External provider
→ raw data

Adapter
→ normalized domain observations

Estimator / Calculator
→ derived domain indicators

RiskContext
→ prepared calculation inputs

RiskCalculator
→ factor interpretation

RiskEngine / RiskPolicy
→ final risk interpretation

Assessment
→ пользовательский и исторический контекст запуска
```

### Главные архитектурные правила

```text
WA-001
Integration layer нормализует provider data,
но не принимает решения о risk sufficiency.
```

```text
WA-002
Current Weather и Historical Weather имеют
раздельные integration pipelines и разные domain outputs.
```

```text
WA-003
Derived calculations выполняются после provider normalization
и не являются обязанностью Adapter или Client.
```

```text
WA-004
Risk Calculator не получает внешние данные
и не рассчитывает derived weather indicators.
```

```text
WA-005
RiskContext является единой границей передачи
подготовленных domain inputs в Risk Calculators.
```

```text
WA-006
Отсутствующие данные сохраняются как отсутствующие
и не подменяются искусственными значениями.
```

```text
WA-007
Недостаточность данных определяется отдельно
для каждой расчетной модели угрозы.
```

### Главный принцип

> Каждый итоговый результат должен быть восстановим из конкретных входных данных, конкретных derived indicators и конкретных результатов проверки факторов.

При этом расчетная архитектура не должна смешивать:

```text
получение данных
расчет derived indicators
интерпретацию риска
историческое хранение результата
```

в одну ответственность.

# 7. Проектирование модели данных

## 7.1 Назначение

Настоящий раздел определяет принципы постоянного хранения данных приложения и границы persistence architecture.

После развития расчетной модели persistence разделяется на две области:

```text
Reference Persistence
```

и:

```text
Assessment Persistence
```

Reference Persistence хранит справочные сведения, не зависящие от конкретного пользовательского запуска.

Assessment Persistence должна обеспечивать сохранение исторического результата пользовательской оценки.

При этом точный persistence contract `Assessment` пока не утвержден и определяется отдельным Assessment Architecture Decision.

SQLite остается целевой локальной СУБД MVP.

Работа с реляционным хранилищем выполняется через SQLAlchemy ORM.

Persistence layer не является владельцем:

- calculation rules;
- derived calculations;
- RiskPolicy;
- provider integration;
- формирования RiskContext.

---

## 7.2 Категории сохраняемых данных

### Справочные данные

К справочной части относятся:

```text
Threat
Source
Recommendation
Threat ↔ Source relationship
```

Эти данные описывают предметную область и не являются snapshot конкретного расчета.

### Исторические данные оценки

Концептуально история должна содержать:

```text
Assessment
        │
        ├── идентификацию пользовательского запуска
        │
        ├── assessment input snapshot
        │
        └── RiskResult[]
                    │
                    └── RiskFactorResult[]
```

Однако:

```text
assessment input snapshot
```

является пока архитектурным понятием, а не утвержденной таблицей или ORM entity.

После появления:

```text
WeatherData
DailyTemperature[]
SoilTemperatureEstimate
DegreeDaysResult
RiskContext
```

нельзя автоматически считать, что старой модели:

```text
Assessment
1 -------- 1
WeatherSnapshot
```

достаточно для воспроизводимости всех расчетных сценариев.

Точный состав Assessment Persistence определяется следующим Architecture Decision.

---

SEASON

## 7.6 Таблица recommendations

### Назначение

Хранит профилактические рекомендации.

| Поле | Тип | Ограничения |

Она не:

- участвует в расчете `RiskFactorResult`;
- входит в `RiskContext`;
- определяет `RiskLevel`.

---

## 7.7 Хранение Risk Rules

Для MVP не требуется универсальный редактируемый rule engine в базе данных.

Threat-specific calculation rules реализуются в specialized Risk Calculators:

```text
TickRiskCalculator

ColoradoBeetleRiskCalculator

CabbageAphidRiskCalculator

CodlingMothRiskCalculator
```

Предметные thresholds и условия находятся в программной calculation model.

Причины:

- поддерживается ограниченный набор угроз;
- правила содержат программную логику;
- отсутствует пользовательский интерфейс администрирования rules;
- универсальная DB-driven rule model существенно усложнила бы MVP;
- Risk Calculators должны оставаться явно тестируемыми.

При этом каждое предметное правило должно иметь источник либо явно зафиксированное основание происхождения.

Следует различать:

```text
Source
→ откуда получено предметное знание

RiskRule
→ conceptual representation условия

RiskCalculator
→ runtime implementation этого условия
```

---

## 7.8 Assessment Persistence Boundary

`Assessment` концептуально представляет один пользовательский запуск оценки.

На текущем уровне подтверждены требования:

```text
Assessment
→ идентифицирует один запуск

Assessment
→ относится к выбранному UserProfile

Assessment
→ относится к Location

Assessment
→ содержит результаты выбранных Threat[]

Assessment
→ может быть открыт из History

Assessment
→ при открытии не пересчитывается
```

Однако физическая схема таблицы `assessments` и ее relationships пока не считается окончательно утвержденной.

До Assessment Architecture Decision не фиксируются окончательно:

```text
точный набор колонок assessments

состав assessment input snapshot

relationship Assessment → WeatherData

relationship Assessment → RiskContext

relationship Assessment → historical observations

relationship Assessment → derived indicators
```

Такие поля, как:

```text
created_at
profile
location_name
region
country
latitude
longitude
```

являются естественными кандидатами для Assessment metadata, но окончательный persistence contract утверждается вместе с полной моделью Assessment.

---

## 7.9 Assessment Input Snapshot

Первоначальная архитектура использовала отдельную модель:

```text
WeatherSnapshot
```

с relationship:

```text
Assessment
1 -------- 1
WeatherSnapshot
```

После развития calculation architecture этого предположения недостаточно для автоматического утверждения persistence contract.

Современный расчет потенциально использует:

```text
WeatherData
```

и дополнительно:

```text
SoilTemperatureEstimate
DegreeDaysResult
DailyTemperature[]
```

в зависимости от выбранной threat model.

Поэтому в canonical architecture до Assessment Decision используется нейтральный термин:

```text
assessment input snapshot
```

### Требование к snapshot

Snapshot должен содержать достаточно информации, чтобы:

- исторический результат не зависел от текущего Weather API;
- пользователь мог открыть сохраненный Assessment без повторного расчета;
- использованные calculation inputs оставались объяснимыми;
- сохраненный результат не изменялся при изменении текущих algorithms или provider data.

### Что пока не решено

Не фиксируется, должен ли snapshot хранить:

```text
WeatherData целиком

отдельные WeatherData fields

DailyTemperature[] целиком

DegreeDaysResult

SoilTemperatureEstimate

RiskContext целиком

только inputs, фактически использованные выбранными threats

provider metadata
```

Это является центральным вопросом будущего Assessment Architecture.

Следовательно, таблица:

```text
weather_snapshots
```

в ее первоначальной форме больше не является утвержденной canonical persistence model.

---

## 7.10 Persistence RiskResult

`RiskResult` является частью исторического результата Assessment.

Концептуальная связь:

```text
Assessment
1 -------- *
RiskResult
```

Для сохраненного `RiskResult` необходимо обеспечить возможность восстановить как минимум:

```text
threat identity

RiskStatus

RiskLevel | None

explanation

RiskFactorResult[]
```

Поддерживаемые status semantics:

```text
CALCULATED
LIMITED
INSUFFICIENT_DATA
ERROR
```

При:

```text
INSUFFICIENT_DATA
ERROR
```

`RiskLevel` отсутствует.

При:

```text
LIMITED
```

`RiskLevel` может присутствовать.

### Physical schema

Конкретная таблица может быть реализована как:

```text
risk_results
```

однако ее окончательные FK, constraints и ownership утверждаются вместе с Assessment Persistence Contract.

Важно сохранить domain invariant:

```text
RiskResult
→ относится ровно к одной threat evaluation
```

и историческую неизменность сохраненного результата.

---

## 7.11 Persistence RiskFactorResult

Исторический `RiskResult` должен сохранять factor evidence, достаточный для объяснения результата.

Концептуальная связь:

```text
RiskResult
1 -------- *
RiskFactorResult
```

Для factor evidence необходимо сохранять смысл следующих domain fields:

```text
factor

state

actualValue

expected

explanation

required
```

Поддерживаемые значения `state`:

```text
MATCHED

NOT_MATCHED

MISSING
```

Persistence representation не должна терять различие:

```text
MISSING
≠
NOT_MATCHED
```

Также должна сохраняться семантика:

```text
required = true / false
```

поскольку она влияет на:

```text
LIMITED
```

и:

```text
INSUFFICIENT_DATA
```

---

## 7.12 Представление actualValue

Первоначальная схема предлагала хранить:

```text
actual_value
```

как универсальный `String`, поскольку факторы могли иметь разные формы отображения.

После уточнения Domain Model следует различать:

```text
domain value
```

и:

```text
presentation value
```

Например:

```text
12.3
```

является фактическим domain value температуры, а:

```text
"12.3 °C"
```

является ее пользовательским представлением.

Поэтому persistence contract не должен автоматически считать форматированный UI-text единственным canonical representation исходного factor value.

Точный способ хранения polymorphic `actualValue` определяется Assessment Persistence Decision.

Возможные требования, которые необходимо учесть:

- числовые значения не должны терять numeric semantics;
- `None` должен оставаться отличимым от `0`;
- единица измерения не должна изменять смысл исходного значения;
- сохраненный фактор должен оставаться пригодным для исторического объяснения.

Не следует проектировать тип поля только из прежнего примера:

```text
SEASON → "август"
```

поскольку `SEASON` не является factor текущих четырех Risk Calculators.

---

## 7.13 Связи

### Справочные связи

```text
Threat

1 -------- *

Recommendation
```

```text
Threat

* -------- *

Source
```

### Исторические conceptual relationships

```text
Assessment

1 -------- *

RiskResult
```

```text
RiskResult

1 -------- *

RiskFactorResult
```

Relationship между:

```text
Assessment
```

и:

```text
assessment input snapshot
```

должен быть определен отдельным Assessment Persistence Contract.

До этого не фиксируется cardinality:

```text
1 → 1 WeatherSnapshot
```

как обязательная canonical relationship.

---

## 7.14 Правила удаления

Для справочных объектов должны сохраняться referential integrity rules.

```text
Threat
Source
Recommendation
```

не должны автоматически удаляться вслед за удалением пользовательской истории только потому, что участвовали в историческом Assessment.

Для Assessment-related data действует общий принцип:

```text
удаление Assessment
        ↓
не должно оставлять orphaned
assessment-owned historical records
```

Однако точный cascade contract для:

```text
Assessment

assessment input snapshot

RiskResult

RiskFactorResult

derived indicator snapshot

historical observations
```

утверждается после определения ownership этих persistence entities.

Поэтому прежнее конкретное правило:

```text
delete Assessment
→ cascade WeatherSnapshot
→ cascade RiskResult
→ cascade RiskFactorResult
```

пока не является окончательным canonical contract.

---

## 7.15 Индексы

Индексы должны следовать из реально утвержденной physical schema и фактических query patterns.

Для справочной части очевидным кандидатом остается:

```text
threats.code
```

Для будущей Assessment Persistence ожидаются query patterns типа:

```text
получить историю по времени

получить RiskResult конкретного Assessment

получить factors конкретного RiskResult
```

но конкретные индексы:

```text
assessments.created_at

risk_results.assessment_id

risk_results.threat_id

risk_factor_results.risk_result_id
```

утверждаются после фиксации соответствующих таблиц и relationships.

Documentation Alignment не должен преждевременно превращать предполагаемые query patterns в окончательный physical design.

---

## 7.16 Неизменность истории

После успешного сохранения Assessment его исторический результат не должен автоматически пересчитываться.

В частности, сохраненные:

```text
RiskStatus

RiskLevel

RiskFactorResult[]

explanations
```

не должны изменяться при:

- изменении текущей погоды;
- изменении Historical Weather provider data;
- изменении текущих thresholds;
- изменении Risk Calculators;
- изменении RiskPolicy;
- изменении calculation method;
- обновлении справочных рекомендаций.

Историческая запись должна отражать именно результат того запуска, который был выполнен ранее.

Это означает:

```text
open historical Assessment
        ↓
read stored historical state
```

а не:

```text
open historical Assessment
        ↓
request current weather
        ↓
recalculate
```

### Reproducibility

Неизменность и воспроизводимость связаны, но не тождественны.

```text
immutability
→ сохраненный результат не меняется
```

```text
reproducibility
→ можно понять, из каких данных и evidence он был получен
```

Assessment Persistence должна поддерживать оба свойства.

Точный объем сохраняемого provenance определяется Assessment Architecture.

---

## 7.17 Итог модели данных

Persistence architecture разделяется на две области.

### Справочная модель

```text
Threat
Source
Recommendation
ThreatSource
```

Эта часть может развиваться независимо от Assessment history.

### Историческая модель

На концептуальном уровне:

```text
Assessment
        │
        ├── assessment input snapshot
        │
        └── RiskResult[]
                    │
                    └── RiskFactorResult[]
```

При этом:

```text
assessment input snapshot
```

пока является архитектурной границей, а не утвержденной физической таблицей.

До следующего Architecture Decision не считается окончательно утвержденным наличие отдельных persistence entities:

```text
WeatherSnapshot

DailyTemperatureSnapshot

SoilTemperatureEstimateSnapshot

DegreeDaysSnapshot

RiskContextSnapshot
```

Главное обязательное требование:

> Исторический Assessment должен сохранять достаточно данных и evidence для неизменного, объяснимого и воспроизводимого представления результата без обращения к текущему Weather API и без повторного расчета.

Следующий Architecture Decision должен ответить:

```text
что именно сохраняет Assessment

какова snapshot boundary

что является owned historical data

какие relationships используются

какие данные сохраняются как raw inputs

какие derived results сохраняются

какая provenance необходима

как хранится RiskFactorResult.actualValue

какие cascade rules требуются

какие индексы необходимы
```

До принятия этих решений persistence architecture не должна диктовать структуру calculation core.

# 8. Интеграция с Weather API и REST-взаимодействие

## 8.1 Назначение

Настоящий раздел определяет:

- взаимодействие приложения с внешними погодными API;
- разделение Current Weather и Historical Weather Integration;
- normalization external provider data;
- правила обработки integration errors;
- границу REST-контрактов, уже определенных архитектурой;
- REST-контракты, которые остаются deferred до проектирования Assessment.

Weather APIs используются только как источники environmental observations.

Расчет:

```text
derived indicators
RiskFactorResult
RiskStatus
RiskLevel
RiskResult
```

выполняется внутри приложения.

---

## 8.2 Общая схема взаимодействия

На текущем этапе следует разделять два типа flow.

### Current Weather

```text
Application / Service Layer
        ↓
WeatherService
        ↓
WeatherClient
        ↓
Current Weather API
        ↓
raw provider payload
        ↓
WeatherAdapter
        ↓
WeatherData
```

### Historical Weather

```text
Application / Service Layer
        ↓
HistoricalWeatherService
        ↓
HistoricalWeatherClient
        ↓
Historical Weather API
        ↓
raw provider payload
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

После integration layer начинаются domain calculations:

```text
WeatherData
        ↓
SoilTemperatureEstimator
        ↓
SoilTemperatureEstimate
```

и:

```text
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult
```

После подготовки необходимых inputs:

```text
WeatherData
+
available derived indicators
        ↓
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult
```

Persistence и Assessment REST flow начинаются за отдельной:

```text
ASSESSMENT BOUNDARY
```

---

## 8.3 Принцип изоляции Weather API

Frontend, Risk Calculators, RiskPolicy и RiskEngine не должны знать структуру ответа конкретного погодного сервиса.

Например, внешний current-weather provider может вернуть:

```json
{
  "current": {
    "temperature_2m": 18.4,
    "relative_humidity_2m": 67,
    "precipitation": 0,
    "wind_speed_10m": 3.2,
    "soil_temperature_6cm": 16.0,
    "soil_temperature_18cm": 10.0
  }
}
```

Integration layer преобразует provider payload во внутренний:

```text
WeatherData
```

Например:

```text
temperature = 18.4
humidity = 67
precipitation = 0
windSpeed = 3.2
soilTemperature6cm = 16.0
soilTemperature18cm = 10.0
```

Historical provider может возвращать собственную структуру дат и температур.

Она преобразуется в:

```text
DailyTemperature[]
```

После normalization расчетная система не использует raw provider JSON.

Следует различать:

```text
Current provider output
→ WeatherData
```

```text
Historical provider output
→ DailyTemperature[]
```

Формулировка:

```text
"в дальнейшем система работает только с WeatherData"
```

не является корректной для всей Weather Architecture.

---

## 8.4 Current Weather Client

`WeatherClient` отвечает только за transport interaction с current-weather provider.

Он:

- принимает координаты;
- формирует provider request;
- выполняет HTTP-вызов;
- применяет configured timeout;
- проверяет HTTP response;
- получает JSON payload;
- преобразует transport failures в integration exceptions.

Он не должен:

- создавать RiskContext;
- выполнять T10 interpolation;
- рассчитывать Degree Days;
- определять RiskFactorState;
- рассчитывать RiskLevel.

### Timeout

Current Weather Integration использует отдельную настройку:

```text
WEATHER_API_TIMEOUT_SECONDS
```

Текущее значение конфигурации MVP:

```text
5 seconds
```

Timeout является integration configuration, а не domain rule.

---

## 8.5 Historical Weather Client

`HistoricalWeatherClient` отвечает за transport interaction с historical-weather provider.

Он получает:

```text
latitude
longitude
startDate
endDate
```

и возвращает provider payload.

Он не рассчитывает:

```text
DailyTemperature domain semantics beyond transport
DegreeDaysResult
risk factors
risk levels
```

### Timeout

Historical Weather Integration использует отдельную настройку:

```text
WEATHER_ARCHIVE_API_TIMEOUT_SECONDS
```

Текущее значение конфигурации MVP:

```text
20 seconds
```

Current и Historical Weather имеют независимые timeout settings.

Это позволяет не связывать latency profile historical requests с current-weather requests.

---

## 8.6 Weather Adapter

`WeatherAdapter` преобразует current-weather provider payload в:

```text
WeatherData
```

Adapter отвечает за:

- проверку обязательной структуры;
- parsing observation time;
- mapping provider fields;
- сохранение optional missing observations как `None`;
- сохранение нулевых значений как реальных значений.

Например:

```text
0.0
≠
None
```

Adapter не должен:

- выполнять interpolation;
- применять biological thresholds;
- решать, достаточно ли данных для конкретной угрозы;
- создавать `RiskFactorResult`.

---

## 8.7 Historical Weather Adapter

`HistoricalWeatherAdapter` преобразует historical provider payload в:

```text
DailyTemperature[]
```

Он отвечает за:

- проверку структуры historical response;
- сопоставление дат и средних температур;
- parsing дат;
- сохранение отсутствующих температур как missing observations;
- формирование нормализованной последовательности.

Adapter не рассчитывает:

```text
DegreeDaysResult
```

и не знает:

```text
CODLING_MOTH
130 Degree Days
RiskStatus
```

---

## 8.8 Integration validity

Integration layer отвечает на вопрос:

```text
можно ли корректно получить и нормализовать provider data?
```

Он не отвечает на вопрос:

```text
достаточно ли этих данных для конкретной risk model?
```

Пример:

```text
WeatherData(
    temperature=18.4,
    humidity=None
)
```

может быть корректным integration result.

Далее:

```text
TickRiskCalculator
```

может выполнить расчет,

а:

```text
CabbageAphidRiskCalculator
```

может сформировать:

```text
HUMIDITY
state = MISSING
```

Следовательно:

```text
integration invalidity
≠
risk insufficiency
```

---

## 8.9 Ошибки Weather Integration

Integration layer должен явно различать:

```text
timeout
connection error
HTTP error
invalid JSON
invalid provider structure
invalid observation data
```

Общие integration exceptions могут включать:

```text
WeatherTimeoutError

WeatherConnectionError

WeatherResponseError

WeatherDataError
```

Эти ошибки не должны автоматически преобразовываться в:

```text
RiskFactorState.MISSING
```

Технический failure provider interaction отличается от отсутствующего domain observation.

## 8.11 Поиск территории

включающий:

    }

## 8.14 Assessment REST Boundary

Endpoint:

```http
POST /api/assessments
```

является целевым пользовательским контрактом MVP, но его окончательная request/response semantics должна быть утверждена после Assessment Architecture Decision.

На концептуальном уровне request содержит:

```text
Location
+
UserProfile
```

Например:

```json
{
  "location": {
    "name": "Тула",
    "region": "Тульская область",
    "country": "Россия",
    "latitude": 54.1961,
    "longitude": 37.6182
  },
  "profile": "VEGETABLE_GARDEN"
}
```

Frontend не должен отправлять:

```text
RiskLevel
RiskStatus
RiskFactorResult
derived indicator values
```

как самостоятельно рассчитанные результаты.

Однако до Assessment Contract не фиксируются:

- exact orchestration;
- exact snapshot content;
- exact success response;
- partial-success behavior;
- technical-error mapping;
- persistence timing;
- transaction behavior.

## 8.15 Что не является canonical flow POST /api/assessments

WeatherData
        ↓
Threat[]
        ↓
RiskEngine
        ↓
RiskResult[]
        ↓
save Assessment

больше не считается окончательным contract.

Она не учитывает:

```text
Historical Weather Integration
SoilTemperatureEstimate
DegreeDaysResult
RiskContext
RiskCalculator
RiskPolicy
```

Актуальная pre-Assessment calculation boundary выглядит так:

```text

        ↓

+

        ↓

        ↓
RiskFactorResult[]
        ↓

Кто именно orchestrates этот pipeline — предмет следующего Architecture Decision.

## 8.16 Assessment response model — DEFERRED

Прежний пример успешного Assessment response содержал:

```text
WeatherData
+
RiskResult[]
```

и одновременно использовал устаревшие factors:

```text
SEASON
SOIL_TEMPERATURE
```

Такой response не является canonical.

После Assessment Architecture необходимо определить:

```text
assessmentId

metadata

location representation

profile representation

snapshot / inputs representation

RiskResult[]

RiskFactorResult[]

derived indicator presentation

partial technical failures
```

До принятия этого контракта в системной документации не следует публиковать конкретный JSON `POST /api/assessments` как утвержденный API.

## 8.17 History REST Boundary

Целевые endpoints:

```http
GET /api/assessments
```

и:

```http
GET /api/assessments/{id}
```

остаются частью product requirements.

Их ключевая semantics:

```text
GET historical Assessment
        ↓
read stored state
```

а не:

```text
GET historical Assessment
        ↓
request Weather API
        ↓
recalculate
```

Точная response schema определяется после фиксации Assessment Persistence Contract.

Концептуально history list должна позволять идентифицировать:

- Assessment;
- время создания;
- Location;
- UserProfile.

History details должна возвращать сохраненный исторический результат без нового risk calculation.

---

## 8.18 Общий формат успешного ответа

Если REST API использует envelope format, единая структура:

```json
{
  "success": true,
  "data": {}
}
```

может использоваться для application endpoints.

Envelope format является transport concern и не влияет на Domain Model.

---

## 8.19 Общий формат ошибки

Единый формат:

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Понятное описание ошибки."
  }
}
```

Error response не должен раскрывать:

- stack trace;
- внутренние provider payload;
- SQL details;
- секреты конфигурации.

---

## 8.20 Error taxonomy

Ошибки следует разделять минимум на следующие группы.

### Input / resource errors

```text
LOCATION_NOT_FOUND

INVALID_PROFILE

THREAT_NOT_FOUND

ASSESSMENT_NOT_FOUND
```

### Weather integration errors

```text
WEATHER_SERVICE_UNAVAILABLE

WEATHER_DATA_INVALID
```

При необходимости Current и Historical Weather failures могут получить более точные application error codes после утверждения E2E orchestration.

### Calculation technical errors

```text
RISK_CALCULATION_ERROR
```

Этот error означает technical failure calculation path и не является:

```text
RiskFactorState.MISSING
```

### Internal errors

```text
INTERNAL_ERROR
```

### Важное различие

Не следует автоматически использовать:

```text
WEATHER_DATA_INCOMPLETE
```

для любого missing optional observation.

Например:

```text
humidity=None
```

может быть допустимым WeatherData.

Недостаточность для конкретной threat model выражается через:

```text
RiskFactorState.MISSING
        ↓
RiskPolicy
```

а не обязательно через HTTP integration error.

---

## 8.21 HTTP status semantics

Общий transport mapping:

| HTTP | Назначение |
|---|---|
| 200 | успешный запрос |
| 201 | ресурс успешно создан, если create contract это предусматривает |
| 400 | структурно некорректный или недопустимый запрос |
| 404 | запрошенный ресурс не найден |
| 502 | failure внешнего integration provider |
| 500 | необработанная внутренняя ошибка |

Использование:

```text
422
```

для domain-level insufficient risk data не должно фиксироваться автоматически.

Например:

```text
RiskStatus.INSUFFICIENT_DATA
```

может являться корректным бизнес-результатом успешного Assessment, а не ошибкой HTTP-запроса.

Точная REST semantics Assessment определяется его контрактом.

---

## 8.22 Обработка Current Weather timeout

Current Weather Client использует configurable timeout.

Conceptual flow:

```text
WeatherClient
        ↓
timeout
        ↓
WeatherTimeoutError
        ↓
application orchestration
        ↓
Controller
        ↓
integration HTTP error
```

Для отдельного current-weather endpoint допустим response вида:

```json
{
  "success": false,
  "error": {
    "code": "WEATHER_SERVICE_UNAVAILABLE",
    "message": "Не удалось получить актуальные погодные данные."
  }
}
```

с HTTP:

```text
502
```

При этом конкретный Assessment behavior при failure Current Weather определяется Assessment Architecture.

## 8.23 Обработка Historical Weather timeout

Historical integration использует собственный timeout и собственный client.

Conceptual flow:

```text
HistoricalWeatherClient
        ↓
timeout
        ↓
WeatherTimeoutError
        ↓
application orchestration
```

Важный принцип:

```text
Historical Weather failure
```

не должен автоматически ломать threat evaluation, которой historical data не требуется.

Например, failure Archive API не должен сам по себе мешать расчету:

```text
TICK
```

если все его необходимые current inputs доступны.

Точная partial-failure orchestration определяется Assessment Contract.

## 8.24 Принцип REST-взаимодействия

Frontend отвечает за:

- получение пользовательского ввода;
- отправку HTTP-запросов;
- отображение нормализованных данных;
- отображение результатов и ошибок.

Frontend не должен:

- рассчитывать RiskLevel;
- применять thresholds;
- формировать Degree Days;
- интерполировать T10;
- решать, является ли `MISSING` критичным.

Backend отвечает за:

```text
integration

domain preparation

risk calculation

application orchestration

persistence
```

через соответствующие отдельные components.

Фраза:

```text

выбирает угрозы,
выполняет расчет,
сохраняет Assessment
```

является слишком агрегированной и не должна использоваться как component responsibility одного сервиса.

> ## Статус разделов §10–§11
>
> Разделы §10 и §11 сохраняются как **исторический план реализации проекта**.

> Они отражают первоначальную декомпозицию и последовательность разработки, сформированные до появления и уточнения следующих архитектурных решений:

> ```
>
> ```text
> Assessment
> → WeatherSnapshot
> ```
>
> ```text
> AssessmentService
> → заранее определенный владелец полного E2E orchestration

### Расчет

Для модели используется базовая температура, зафиксированная в исследовании:

```text
10 °C
```

Упрощенная расчетная логика:

```text
если averageTemperature > 10 °C

effectiveTemperature =
averageTemperature - 10 °C

иначе

effectiveTemperature = 0
```

После этого:

```text
DegreeDays =
сумма effectiveTemperature
за расчетный период
```

### Недостаток исторических данных

Если необходимые данные получить невозможно:

```text
DEGREE_DAYS = MISSING
        ↓
INSUFFICIENT_DATA
```

Система не должна рассчитывать накопленную температуру по одному текущему значению.

Отдельно проверить:

- день ниже базовой температуры;
- день выше базовой температуры;
- последовательность нескольких дней;
- правильность накопления;
- граничные значения;
- отсутствие исторических данных.

Команда должна полностью пройти защиту от начала до конца.

### Результат дня

Проект находится в состоянии Release Candidate и готов к демонстрации.

# 12. Стратегия тестирования

## 12.1 Назначение

Стратегия тестирования должна подтверждать не только корректность отдельных функций, но и соблюдение архитектурных границ приложения.

Основные цели тестирования:

- проверить correctness Domain Model;
- проверить Current Weather Integration;
- проверить Historical Weather Integration;
- проверить derived calculations;
- проверить RiskContext contract;
- проверить четыре независимых Risk Calculators;
- проверить RiskPolicy;
- проверить RiskEngine;
- проверить REST-контракты уже реализованных endpoints;
- предотвратить смешение `MISSING`, `NOT_MATCHED` и technical errors;
- подтвердить детерминированность расчетов;
- обеспечить regression safety при дальнейшем развитии Assessment.

Стратегия разделяется на:

```text
Unit Tests
Integration Tests
API Tests
Regression Tests
```

Assessment / History testing расширяется после утверждения соответствующего архитектурного контракта.

---

## 12.2 Общий принцип

Каждый architectural responsibility должен тестироваться на своем уровне.

```text
Domain invariant
→ unit test
```

```text
Adapter mapping
→ unit test
```

```text
Derived calculation
→ unit test
```

```text
Threat-specific rule
→ unit test calculator
```

```text
Generic risk semantics
→ RiskPolicy unit test
```

```text
composition
→ RiskEngine unit test
```

```text
несколько компонентов вместе
→ integration test
```

```text
HTTP contract
→ API test
```

Не следует использовать end-to-end тест как замену unit-тестам calculation rules.

## 12.21 Regression Gate

Перед merge каждого архитектурного EPIC должен выполняться полный regression suite:

```text
python -m pytest
```

Regression Gate считается пройденным только если:

```text
0 failed
```

Уменьшение количества тестов само по себе не считается проблемой, если оно является осознанным следствием удаления устаревшего contract и функциональное покрытие сохранено.

При архитектурном refactoring особенно проверяются:

```text
старый API случайно не остается параллельно новому

не возникает второй source of truth

не появляется direct WeatherData → RiskCalculator path

derived indicators не возвращаются в WeatherData

calculator не получает provider dependencies
```

```

## 12.23 Definition of Test Completeness для текущего calculation core

Текущий расчетный слой считается достаточно покрытым, если:

- Domain Model имеет unit coverage основных invariants;
- Current Weather Client/Adapter/Service покрыты unit tests;
- Historical Weather Client/Adapter/Service покрыты unit tests;
- SoilTemperatureEstimator покрыт boundary tests;
- DegreeDaysCalculator покрыт boundary tests;
- все четыре Risk Calculators покрыты boundary и missing-data tests;
- RiskPolicy покрывает status и level boundaries;
- RiskEngine покрывает composition scenarios;
- существуют integration tests для threat calculation pipelines;
- существует полный regression suite;
- отсутствуют flaky dependencies на реальный Weather API в unit tests.

Assessment/History не входит в данный completeness gate до утверждения следующего архитектурного контракта.

## 12.24 Главный принцип стратегии тестирования

Тесты должны подтверждать не только:

```text
"получили правильное число"
```

но и:

```text
"это число было получено правильным компонентом
из правильных входных данных
через правильную архитектурную границу"
```

Поэтому calculation correctness и architectural correctness рассматриваются совместно.

Главная цепочка тестируемости:

```text
Provider Payload
        ↓
Adapter
        ↓
Normalized Domain Data
        ↓
Derived Calculation
        ↓
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult
```

Каждая стрелка должна иметь собственное проверяемое основание.

# 13. Контрольный сценарий защиты

## 13.1 Назначение

Контрольный сценарий определяет рекомендуемую последовательность демонстрации приложения.

Его задача — показать не максимальное количество экранов, а главную причинно-следственную связь проекта:

```text
исследование
        ↓
выявленная проблема
        ↓
инженерная модель
        ↓
архитектурное решение
        ↓
работающий результат
```

Демонстрация должна показывать не только пользовательский интерфейс, но и главное инженерное свойство системы:

```text
разные угрозы
→ используют разные environmental inputs
→ применяют разные calculation rules
→ дают независимые объяснимые результаты
```

---

## 13.2 Начало демонстрации

Сначала кратко объясняется исследовательская проблема.

Рекомендуемый смысл вступления:

> Весной и летом активизируются клещи и различные вредители растений. Во время исследования мы выяснили, что для разных угроз важны разные условия: температура воздуха, влажность, температура почвы или накопленное тепло.

Затем необходимо обозначить принципиальное ограничение модели:

> По погодным данным нельзя достоверно определить фактическое присутствие вредителя. Поэтому приложение не предсказывает появление вредителя, а оценивает соответствие доступных environmental conditions условиям выбранной расчетной модели.

Важно не использовать формулировки:

```text
вероятность появления = X %

вредитель точно появится

прогноз заражения

официальный эпидемиологический прогноз
```

если приложение фактически этого не рассчитывает.

---

## 13.3 Демонстрация выбора территории

1. Открыть главную страницу.
2. Найти заранее выбранную территорию.
3. Показать найденный `Location`.
4. Выбрать территорию.

После выбора можно показать текущие погодные observations:

```text
температура воздуха

влажность

осадки

ветер

доступные температуры почвы
```

Объяснить:

> Эти наблюдения приложение получает автоматически через внешний погодный сервис, но дальше работает уже с собственной нормализованной domain-моделью, а не с provider JSON.

При необходимости коротко показать цепочку:

```text
Weather API
        ↓
Weather Adapter
        ↓
WeatherData
```

Не требуется показывать полный raw JSON provider.

---

## 13.4 Демонстрация профиля «Огород»

Выбрать:

```text
Огород
```

и запустить оценку.

Для этого профиля система должна независимо оценить:

```text
Колорадский жук

Капустная тля
```

Важно показать, что эти угрозы используют **разные calculation inputs**.

### Колорадский жук

Используется:

```text
температура почвы на глубине 10 см
```

При этом значение T10 является derived indicator:

```text

+
T18
        ↓
SoilTemperatureEstimator
        ↓
T10
```

После этого:

```text
T10
        ↓
ColoradoBeetleRiskCalculator
```

### Капустная тля

Используются:

```text
температура воздуха
+
влажность
```

После этого:

```text
RiskContext
        ↓
CabbageAphidRiskCalculator
```

Рекомендуемое объяснение:

> Для обеих угроз используется одна и та же территория, но их модели требуют разных environmental indicators. Поэтому результаты рассчитываются независимо и могут различаться.

Это точнее, чем формулировка:

```text
«погода одна и та же,
но правила разные»
```

поскольку часть threat models использует derived или historical inputs.

## 13.10 LIMITED — только если есть подходящий сценарий

Общая RiskPolicy поддерживает:

```text
RiskStatus.LIMITED
```

если:

```text
required factors доступны

optional factor отсутствует
```

При этом:

```text
RiskLevel
```

может быть рассчитан по известным factors.

Однако в текущих четырех MVP Risk Calculators все реализованные factors являются required.

Поэтому искусственно создавать демонстрационный `LIMITED` только ради показа статуса не требуется.

Если к моменту защиты появится реальная threat model с optional factor, `LIMITED` можно включить в дополнительный демонстрационный сценарий.

## 13.11 Демонстрация истории

Раздел истории показывается после реализации и утверждения Assessment Architecture.

Открыть:

```text
История
```

и выбрать ранее сохраненный Assessment.

Минимально необходимо показать:

- идентификацию исторического запуска;
- территорию;
- дату и время;
- выбранный профиль;
- сохраненные `RiskResult`;
- сохраненные factor evidence.

Ключевой принцип:

```text
open historical Assessment
        ↓
read stored historical state
```

а не:

```text
open historical Assessment
        ↓
request current weather
        ↓
recalculate
```

Поэтому при открытии истории:

- не должен запускаться новый calculation pipeline;
- текущая погода не должна изменять старый результат;
- изменение текущих thresholds не должно менять сохраненный `RiskResult`.

### Что говорить о сохраненных inputs

До утверждения Assessment Persistence Contract не следует обещать, что история обязательно хранит только:

```text
«погодные данные»
```

или конкретный `WeatherSnapshot`.

Корректная формулировка:

> Историческая запись сохраняет результат конкретного запуска и тот объем calculation evidence и input snapshot, который необходим для его объяснимости и воспроизводимости.

После утверждения Assessment Architecture эту часть сценария необходимо конкретизировать по фактической persistence model.

```text

при этом:

```text

# 14. Технические риски проекта

## 14.1 Назначение

Настоящий раздел фиксирует актуальные технические риски PestWatch после формирования текущего calculation core.

Следует различать:

```text
исходный риск
```

```text
архитектурное решение,
которое уже снижает риск
```

и:

```text
остаточный риск
```

Часть рисков первоначального проекта уже не является неизвестностью, поскольку соответствующие architecture decisions реализованы.

Основное внимание по-прежнему уделяется:

- внешним environmental data;
- корректности derived calculations;
- threat-specific calculation rules;
- отсутствующим данным;
- external-provider availability;
- дальнейшему Assessment architecture;
- недопущению scope creep.

---

## 14.2 Current Weather data availability

### Исходный риск

Погодный provider может:

- не вернуть отдельное observation;
- изменить структуру ответа;
- вернуть некорректный payload;
- быть временно недоступен;
- превысить timeout.

### Реализованное снижение риска

Current Weather Integration изолирован через:

```text
WeatherClient
        ↓
WeatherAdapter
        ↓
WeatherData
```

Provider-specific payload не передается напрямую в Risk Calculation Layer.

Integration layer различает:

```text
transport failure

invalid provider data

valid missing optional observation
```

### Остаточный риск

Даже при корректной integration architecture внешний provider остается внешней зависимостью.

Возможны:

```text
timeout

connection failure

HTTP error

provider contract change

отсутствующее observation
```

### Меры

- использовать configurable timeout;
- обрабатывать provider errors отдельными exceptions;
- покрывать Client и Adapter unit-тестами;
- не подменять отсутствующее значение нулем;
- не превращать technical failure автоматически в `RiskFactorState.MISSING`;
- не позволять Risk Calculators зависеть от provider API.

---

## 14.3 Soil Temperature — RESOLVED ARCHITECTURE, RESIDUAL DATA RISK

### Исходный риск

Модель колорадского жука требует температуры почвы на глубине 10 см, тогда как внешний provider может не предоставлять именно эту глубину.

Первоначальный риск:

```text
T10 unavailable
        ↓
Colorado calculation unavailable
```

### Принятое архитектурное решение

Текущая модель использует observations:

```text
T6
+
T18
```

и отдельно рассчитывает:

```text
SoilTemperatureEstimate
```

через:

```text
SoilTemperatureEstimator
```

Текущий метод:

```text
LINEAR_INTERPOLATION
```

Calculation pipeline:

```text
WeatherData.soilTemperature6cm
+
WeatherData.soilTemperature18cm
        ↓
SoilTemperatureEstimator
        ↓
SoilTemperatureEstimate
        ↓
RiskContext
        ↓
ColoradoBeetleRiskCalculator
```

Таким образом, отсутствие provider field ровно на глубине 10 см больше не является нерешенной архитектурной проблемой.

### Остаточный риск

Для interpolation всё равно необходимы source observations.

Если:

```text
T6 = None
```

или:

```text
T18 = None
```

корректный estimate может быть недоступен.

### Меры

Система не должна:

- заменять температуру почвы температурой воздуха;
- экстраполировать значение без утвержденного правила;
- создавать synthetic T10 только ради продолжения расчета.

Если корректный estimate отсутствует:

```text
RiskContext
→ soilTemperature10cmEstimate unavailable
        ↓
ColoradoBeetleRiskCalculator
        ↓
MISSING
        ↓
INSUFFICIENT_DATA
```

### Статус

```text
ARCHITECTURE RISK
→ RESOLVED

SOURCE DATA AVAILABILITY
→ RESIDUAL RISK
```

---

## 14.4 Historical Weather availability — RESOLVED ARCHITECTURE, RESIDUAL PROVIDER RISK

### Исходный риск

Для яблонной плодожорки недостаточно current weather.

Требуется historical temperature series за период.

### Принятое архитектурное решение

Создан отдельный pipeline:

```text
HistoricalWeatherClient
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

после чего:

```text
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult
        ↓
RiskContext
        ↓
CodlingMothRiskCalculator
```

Historical Weather больше не пытается использовать тот же contract, что Current Weather.

### Остаточные риски

Внешний archive provider может:

- быть недоступен;
- иметь ограничения периода;
- менять API;
- возвращать неполный временной ряд;
- содержать отсутствующие daily observations;
- отвечать медленнее current-weather provider.

### Меры

Использовать отдельные:

```text
HistoricalWeatherClient

HistoricalWeatherAdapter

HistoricalWeatherService
```

и отдельный timeout:

```text
WEATHER_ARCHIVE_API_TIMEOUT_SECONDS
```

Historical failure не должен автоматически ломать threat models, которым historical data не требуется.

Например:

```text
Archive API unavailable
```

не должно само по себе делать невозможным:

```text
TickRiskCalculator
```

### Статус

```text
ARCHITECTURE RISK
→ RESOLVED

EXTERNAL PROVIDER AVAILABILITY
→ RESIDUAL RISK
```

---

## 14.5 Риск некорректного Degree Days calculation

### Проблема

Даже при наличии historical data ошибка в расчете accumulated temperature может привести к систематически неверному результату Codling Moth model.

Возможные ошибки:

- неправильная base temperature;
- неправильный daily contribution;
- неверное суммирование;
- неправильный период;
- некорректная обработка missing observation.

### Архитектурная защита

Расчет выделен в отдельный:

```text
DegreeDaysCalculator
```

и отделен от:

```text
CodlingMothRiskCalculator
```

Следует различать:

```text
10 °C
→ base temperature calculation
```

и:

```text
130 Degree Days
→ threat-specific risk threshold
```

### Меры

Unit-тестами покрываются:

```text
temperature < base

temperature = base

temperature > base

multiple days

missing observation

period boundaries

total
```

Threshold:

```text
130
```

тестируется отдельно в:

```text
CodlingMothRiskCalculator
```

---

## 14.6 Риск ошибки Soil Temperature interpolation

### Проблема

Ошибка в calculation formula или использовании source depths приведет к некорректному `SoilTemperatureEstimate`.

### Архитектурная защита

Interpolation находится в отдельном:

```text
SoilTemperatureEstimator
```

и не смешивается с Colorado risk threshold.

Derived model сохраняет provenance:

```text
target depth

source depths

source temperatures

method
```

### Меры

Проверять unit-тестами:

- known interpolation examples;
- boundary values;
- zero values;
- negative values;
- missing source observations;
- сохранение calculation method и provenance.

---

## 14.7 Риск чрезмерного усложнения Risk Calculation Layer

### Проблема

По мере роста проекта может возникнуть желание создать:

- универсальный rule engine;
- DSL правил;
- сложную систему весов;
- generic biological formula;
- динамический graph rules;
- универсальный configuration-driven calculator.

### Последствие

Calculation layer станет значительно сложнее реальных требований MVP.

### Меры

Текущая архитектура сохраняет явное разделение:

```text
RiskCalculator
→ threat-specific rules
```

```text
RiskPolicy
→ generic factor interpretation
```

```text
RiskEngine
→ RiskResult composition
```

Поддерживаются четыре explicit calculators:

```text
TickRiskCalculator

ColoradoBeetleRiskCalculator

CabbageAphidRiskCalculator

CodlingMothRiskCalculator
```

Не требуется создавать универсальный язык biological rules без отдельного доказанного product need.

Первоначальный риск чрезмерного усложнения Risk Engine сохраняет смысл, но теперь относится ко всему Risk Calculation Layer, а не к одному классу `RiskEngine`. Исходный документ именно universal rule engine считал угрозой срокам MVP. :contentReference[oaicite:2]{index=2}

---

## 14.8 Риск нарушения архитектурных границ

### Проблема

При дальнейшем развитии может появиться shortcut:

```text
RiskCalculator
→ WeatherService
```

или:

```text
RiskCalculator
→ HistoricalWeatherClient
```

или:

```text
WeatherData
→ снова хранит derived indicators
```

или:

```text
RiskEngine
→ начинает применять threat thresholds
```

### Последствие

Возникают:

- второй calculation contract;
- скрытая связанность;
- усложнение unit testing;
- provider leakage;
- regression risk;
- нарушение EPIC-09 architecture.

### Меры

Сохранять canonical boundary:

```text
Normalized Observations
        ↓
Derived Calculations
        ↓
RiskContext
        ↓
RiskCalculator
        ↓
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult
```

На каждом architecture EPIC выполнять boundary checks и полный regression suite.

---

## 14.9 Риск смешения MISSING и technical failure

### Проблема

Два разных состояния могут быть ошибочно объединены:

```text
provider request failed
```

и:

```text
provider ответил успешно,
но конкретное observation отсутствует
```

Первое является technical integration failure.

Второе может быть корректным domain state.

### Последствие

Система может:

- показать `INSUFFICIENT_DATA` вместо реальной technical error;
- скрыть provider outage;
- либо, наоборот, считать обычный missing value HTTP error.

### Меры

Сохранять разделение:

```text
integration exception
≠
RiskFactorState.MISSING
```

```text
MISSING
→ нет domain input
```

```text
ERROR
→ technical inability to perform calculation
```

Точная orchestration `ERROR` определяется Assessment Architecture.

---

## 14.10 Риск ложной научной точности

### Проблема

Интерфейс или презентация могут создать впечатление, что приложение рассчитывает научную вероятность фактического появления вредителя.

Например:

```text
«Вероятность появления клеща — 87 %»
```

не соответствует текущей calculation model.

### Последствие

Пользовательский вывод становится сильнее предметного основания проекта.

### Меры

Использовать качественные уровни:

```text
LOW

MODERATE

ELEVATED

HIGH
```

и явно объяснять:

> Система оценивает соответствие environmental conditions условиям инженерной модели, а не вероятность фактического присутствия вредителя.

Исходный риск остаётся полностью актуальным. :contentReference[oaicite:3]{index=3}

---

## 14.11 Риск ошибки в threat-specific rules

### Проблема

Неправильный threshold или неверно перенесенная предметная интерпретация приводят к воспроизводимо неправильному результату.

Например:

```text
10 °C

13 °C

25–26 °C

60–70 %

130 Degree Days
```

являются критичными параметрами calculation models.

### Меры

Для каждого правила должна существовать traceability:

```text
Official Source
        ↓
engineering interpretation
        ↓
calculator rule
        ↓
unit test
```

Следует разделять:

```text
derived-calculation parameters
```

и:

```text
risk thresholds
```

Например:

```text
10 °C
→ Degree Days base
```

не является тем же правилом, что:

```text
130 Degree Days
→ Codling Moth threshold
```

Первоначальная документация уже правильно требовала сверять каждое правило с исследованием и после реализации добавлять unit-тест. :contentReference[oaicite:4]{index=4}

---

## 14.12 Риск threshold drift

### Проблема

Один и тот же threshold может случайно оказаться продублирован в нескольких слоях:

```text
Calculator

Service

Controller

Documentation

Test helper
```

После изменения одного значения система станет противоречивой.

### Меры

Threat-specific threshold должен иметь одного runtime owner.

Текущие owners:

```text
Tick 10 °C
→ TickRiskCalculator

Colorado 13 °C
→ ColoradoBeetleRiskCalculator

Cabbage Aphid 25–26 °C / 60–70 %
→ CabbageAphidRiskCalculator

Codling Moth 130 Degree Days
→ CodlingMothRiskCalculator
```

Derived calculation settings принадлежат своим calculation components.

Tests должны проверять contract, но не создавать альтернативный source of truth.

---

## 14.13 Риск зависимости от внешнего сервиса во время демонстрации

### Проблема

Во время защиты может отсутствовать Интернет либо один из Weather providers может быть недоступен.

Теперь существуют как минимум две внешние capabilities:

```text
Current Weather

Historical Weather
```

### Последствие

Часть live calculation scenario может быть невозможно показать.

### Меры

Перед демонстрацией:

- проверить current provider;
- проверить archive provider;
- подготовить стабильный основной сценарий;
- после реализации Assessment подготовить сохраненный исторический результат;
- убедиться, что reference data открывается без внешних Weather API.

Важно:

```text
stored historical result
```

может использоваться как демонстрационный резерв, но не должен выдаваться за новый live calculation.

Это сохраняет смысл исходного риска external dependency во время защиты. :contentReference[oaicite:5]{index=5}

---

## 14.14 Риск premature Assessment design

### Проблема

До проектирования Assessment существует соблазн автоматически реализовать первоначальную модель:

```text
AssessmentService

WeatherSnapshot

AssessmentRepository

WeatherData-only snapshot
```

### Последствие

Persistence architecture может оказаться несовместимой с уже существующими:

```text
Historical Weather

SoilTemperatureEstimate

DegreeDaysResult

RiskContext
```

и потребовать повторного refactoring.

### Меры

До Assessment Architecture Decision не фиксировать:

```text
snapshot structure

orchestration owner

transaction boundary

ERROR isolation

derived persistence

historical-observation persistence
```

Следующая архитектурная задача должна сначала определить contract, а затем физическую persistence model.

---

## 14.15 Риск недостаточной воспроизводимости Assessment

### Проблема

Если исторический Assessment сохранит только итоговый:

```text
RiskLevel
```

или слишком узкий weather snapshot, позже невозможно будет понять, почему был получен конкретный результат.

### Последствие

Нарушаются:

```text
explainability

auditability

historical reproducibility
```

### Меры

Assessment Architecture должна определить minimum reproducibility boundary:

```text
historical result
+
factor evidence
+
required input snapshot / provenance
```

При этом нельзя заранее считать, что:

```text
WeatherData alone
```

достаточен для всех threat models.

---

## 14.16 Риск чрезмерного объема UI

### Проблема

Сложные:

- карты;
- графики;
- animation;
- advanced dashboards;
- deep historical visualization

могут отвлечь от calculation correctness.

### Меры

Приоритет:

```text
корректная Domain Model
        >
корректные integrations
        >
derived calculations
        >
Risk Calculation Layer
        >
целостный пользовательский сценарий
        >
понятный UI
        >
декоративные улучшения
```

В исходной версии приоритет начинался с `Risk Engine`. :contentReference[oaicite:6]{index=6} После архитектурного развития проекта правильнее говорить о calculation core в целом, а не об одном классе.

---

## 14.17 Риск scope creep по угрозам

### Проблема

После реализации четырех threats можно начать добавлять:

- новые виды вредителей;
- болезни растений;
- дополнительные медицинские угрозы;
- дополнительные biological models.

### Последствие

Каждая новая threat требует:

```text
research

sources

engineering interpretation

inputs

possibly new derived indicators

RiskCalculator

tests

recommendations
```

### Меры

До завершения MVP поддерживаемый набор остается:

```text
TICK

COLORADO_BEETLE

CABBAGE_APHID

CODLING_MOTH
```

Новые threat models добавляются только после завершения текущего MVP и оценки их влияния на Domain Model и `RiskContext`.

Исходное ограничение четырьмя угрозами остаётся актуальным. :contentReference[oaicite:7]{index=7}

---

## 14.18 Риск разрастания RiskContext

### Проблема

При добавлении новых threats существует риск превращения:

```text
RiskContext
```

в универсальный контейнер любых данных системы.

### Последствие

Он может начать содержать:

```text
Location

UserProfile

Threat

Recommendations

Repositories

provider data

application metadata
```

и потерять роль clean calculation boundary.

### Меры

Каждое новое поле RiskContext должно проходить отдельную проверку:

```text
является ли это подготовленным domain input,
необходимым calculator?
```

Если нет — поле не должно добавляться.

---

## 14.19 Риск over-persistence

### Проблема

Стремление обеспечить полную воспроизводимость может привести к сохранению всего:

```text
raw provider JSON

всех HTTP requests

всех external responses

полного RiskContext

всех historical observations

всей integration metadata
```

даже если это не требуется MVP.

### Последствие

- усложнение schema;
- duplication;
- migration burden;
- ненужный storage coupling.

### Меры

Assessment Persistence должна хранить **достаточный**, а не максимальный snapshot.

Правило:

```text
minimum data required
for immutable + explainable + reproducible history
```

определяется отдельным Assessment Decision.

---

## 14.20 Риск under-persistence

### Проблема

Обратная ошибка — сохранить слишком мало:

```text
Assessment id

RiskLevel
```

без factor evidence или необходимых calculation inputs.

### Последствие

Исторический результат перестает быть объяснимым.

### Меры

Persistence Decision должен проверяться по вопросу:

> Можно ли после отключения Weather API понять, какие данные и какие factor results сформировали сохраненный результат?

Если нет — snapshot недостаточен.

---

## 14.21 Риск изменения algorithms после сохранения истории

### Проблема

После MVP могут измениться:

```text
thresholds

RiskPolicy

Degree Days method

interpolation method
```

Новый расчет тех же observations потенциально даст другой результат.

### Требование

Исторический Assessment не должен автоматически меняться.

Необходимо различать:

```text
historical stored result
```

и:

```text
recalculation using current algorithm
```

Если в будущем появится функция recalculation, она должна быть отдельной явной operation, а не side effect открытия истории.

---

## 14.22 Риск недостаточного regression coverage

### Проблема

Архитектурные refactoring могут сохранять локально корректный код, но случайно возвращать старые boundaries.

Например:

```text
WeatherData → Calculator

derived indicator снова внутри WeatherData

RiskLevel внутри Calculator

provider dependency внутри RiskContext
```

### Меры

Перед merge:

```text
python -m pytest
```

должен завершаться:

```text
0 failed
```

Дополнительно выполняются architecture-oriented searches/checks на запрещенные зависимости и legacy contracts.

---

## 14.23 Риск некорректного отображения explanation

### Проблема

Даже при корректном domain result UI может показать поврежденный или неправильно декодированный текст explanation.

Это особенно важно для русскоязычных сообщений.

### Последствие

Calculation остается корректным, но пользовательская explainability фактически ломается.

### Меры

Перед пользовательской демонстрацией необходимо проверить:

```text
source encoding

runtime encoding

JSON serialization

browser rendering
```

и не полагаться только на отображение текста через конкретную PowerShell console.

После EPIC-07/08/09 исходный risk profile изменился.

### Существенно снижены архитектурой

```text

missing/error semantics

scope creep

scientific overclaiming
```

```text
premature snapshot design

under-persistence

over-persistence

partial failure semantics

ERROR ownership

reproducibility contract
```

## 14.25 Итог технических рисков

На текущем этапе наиболее критичны уже не те же три риска, что до начала разработки.

Актуальная группа:

```text
корректность external + derived data
                +
корректность threat-specific rules
                +
сохранение архитектурных boundaries
                +
правильный Assessment persistence contract
```

Главный принцип управления рисками:

```text
external uncertainty
→ isolate

derived uncertainty
→ make calculation explicit and tested

biological uncertainty
→ trace to source

missing data
→ preserve explicitly

architecture uncertainty
→ decide before implementation

historical persistence
→ design for reproducibility
```

Новый функционал не должен добавляться ценой нарушения уже утвержденных calculation boundaries.

# 15. Definition of Done проекта

## 15.1 Назначение

Definition of Done определяет условия, при которых MVP «Сезонного дозора» считается технически завершенным.

Факт наличия исходного кода, отдельных работающих endpoints или зеленого unit test suite сам по себе не означает завершение всего проекта.

Для контроля готовности необходимо различать два уровня:

```text
Calculation Core DoD
```

и:

```text
Full MVP DoD
```

### Calculation Core DoD

Подтверждает готовность:

```text
environmental data acquisition
+
derived calculations
+
RiskContext
+
risk calculation
```

до границы:

```text
RiskResult[]
```

### Full MVP DoD

Дополнительно требует:

```text
Assessment orchestration
+
persistence
+
history
+
user-facing flow
```

Следовательно:

```text
Calculation Core DONE
```

не означает автоматически:

```text
MVP DONE
```

---

## 15.2 Готовность Domain Model

Для Calculation Core должны быть определены и реализованы domain models:

```text
Location

WeatherData

DailyTemperature

SoilTemperatureEstimate

DegreeDaysResult

DegreeDaysCalculationMethod

RiskContext

RiskFactorResult

RiskResult

RiskFactorState

RiskStatus

RiskLevel
```

### WeatherData

Должен представлять только normalized current-weather observations.

Не должен содержать:

```text
SoilTemperatureEstimate

DegreeDaysResult
```

### RiskContext

Должен быть canonical input aggregate Risk Calculators.

Он содержит только подготовленные calculation inputs и не должен включать:

```text
Location

UserProfile

Threat

Recommendation

RiskResult

Repository

provider dependencies
```

### Derived models

```text
SoilTemperatureEstimate

DegreeDaysResult
```

должны представлять derived domain facts и не содержать threat-specific risk interpretation.

---

## 15.3 Готовность Current Weather Integration

Current Weather Integration считается готовой, если реализована цепочка:

```text
Location
        ↓
WeatherClient
        ↓
WeatherAdapter
        ↓
WeatherData
```

Необходимо обеспечить:

- получение реальных provider data;
- передачу координат;
- configurable timeout;
- обработку timeout;
- обработку connection errors;
- обработку HTTP errors;
- обработку invalid JSON;
- validation provider structure;
- parsing observation time;
- сохранение optional missing values как `None`;
- различие `None` и `0.0`.

Integration layer не должен:

```text
определять RiskStatus

определять RiskLevel

рассчитывать T10

рассчитывать Degree Days
```

---

## 15.4 Готовность Historical Weather Integration

Historical Weather Integration считается готовой, если реализована цепочка:

```text
Location
+
period
        ↓
HistoricalWeatherClient
        ↓
HistoricalWeatherAdapter
        ↓
DailyTemperature[]
```

Необходимо обеспечить:

- запрос historical provider;
- передачу периода;
- отдельный archive timeout;
- обработку transport errors;
- validation historical response;
- mapping dates;
- mapping mean temperatures;
- корректную работу с missing daily values.

Historical integration не должна:

```text
рассчитывать DegreeDaysResult

применять Codling Moth threshold

создавать RiskFactorResult
```

---

## 15.5 Готовность derived calculations

### SoilTemperatureEstimator

Должен быть реализован отдельный расчет:

```text
T6
+
T18
        ↓
SoilTemperatureEstimate(T10)
```

Для результата должны сохраняться:

```text
target depth

calculated temperature

source depths

source temperatures

method
```

Если необходимых observations недостаточно, synthetic estimate не создается.

---

### DegreeDaysCalculator

Должен быть реализован отдельный расчет:

```text
DailyTemperature[]
        ↓
DegreeDaysResult
```

Текущий calculation method должен явно фиксировать:

```text
base temperature

period

observations

total

method
```

Расчет Degree Days не должен содержать threshold:

```text
130
```

для Codling Moth risk.

---

## 15.6 Готовность Risk Calculator contract

Все threat-specific calculators должны реализовывать единый contract:

```python
evaluate(
    context: RiskContext,
) -> tuple[RiskFactorResult, ...]
```

Не должно существовать параллельного legacy contract:

```text
WeatherData
→ RiskCalculator
```

или:

```text
AssessmentDate + WeatherData
→ RiskCalculator
```

Каждый calculator:

- получает только `RiskContext`;
- применяет только правила своей threat model;
- возвращает `RiskFactorResult[]`;
- не определяет итоговый `RiskStatus`;
- не определяет итоговый `RiskLevel`.

---

## 15.7 Готовность четырех threat models

Поддерживаются четыре calculators.

### TickRiskCalculator

Factor:

```text
AIR_TEMPERATURE
```

Rule:

```text
temperature >= 10 °C
```

---

### CabbageAphidRiskCalculator

Factors:

```text
AIR_TEMPERATURE

HUMIDITY
```

Rules:

```text
25 °C <= temperature <= 26 °C
```

```text
60 % <= humidity <= 70 %
```

---

### ColoradoBeetleRiskCalculator

Factor:

```text
SOIL_TEMPERATURE_10CM
```

Rule:

```text
T10 >= 13 °C
```

Calculator получает готовый:

```text
SoilTemperatureEstimate
```

через `RiskContext`.

---

### CodlingMothRiskCalculator

Factor:

```text
DEGREE_DAYS_ABOVE_10C
```

Rule:

```text
Degree Days >= 130
```

Calculator получает готовый:

```text
DegreeDaysResult
```

через `RiskContext`.

---

### Общие требования

Для каждой threat model:

- factor names определены явно;
- thresholds определены явно;
- `required` semantics определена;
- `MISSING` обрабатывается корректно;
- `actualValue` сохраняется;
- `expected` формируется;
- explanation присутствует;
- boundary cases покрыты unit tests.

`SEASON` не должен появляться как реализованный factor текущих четырех calculators.

---

## 15.8 Готовность RiskPolicy

`RiskPolicy` считается готовой, если определена и протестирована generic semantics:

```text
нет factors
→ INSUFFICIENT_DATA
```

```text
required MISSING
→ INSUFFICIENT_DATA
```

```text
optional MISSING
→ LIMITED
```

```text
нет missing factors
→ CALCULATED
```

RiskLevel рассчитывается по известным factors.

Boundary semantics:

```text
ratio < 0.25
→ LOW

0.25 <= ratio < 0.50
→ MODERATE

0.50 <= ratio < 0.75
→ ELEVATED

ratio >= 0.75
→ HIGH
```

Для:

```text
INSUFFICIENT_DATA

ERROR
```

должно выполняться:

```text
RiskLevel = None
```

`RiskPolicy` не должна содержать threat-specific thresholds.

---

## 15.9 Готовность RiskEngine

`RiskEngine` считается готовым, если:

```text
threatCode
+
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskResult
```

работает как единый composition flow.

RiskEngine должен:

- сохранять `threatCode`;
- сохранять factor results;
- использовать `RiskPolicy`;
- формировать `RiskStatus`;
- формировать `RiskLevel`;
- формировать итоговый `RiskResult`.

При этом RiskEngine не должен:

- получать WeatherData;
- обращаться к Weather API;
- выполнять interpolation;
- рассчитывать Degree Days;
- применять biological thresholds;
- выполнять persistence.

---

## 15.10 Готовность missing-data semantics

В Calculation Core должны быть выполнены invariants:

```text
None
≠
0
```

```text
MISSING
≠
NOT_MATCHED
```

```text
INSUFFICIENT_DATA
≠
LOW
```

```text
technical error
≠
MISSING
```

Если required input отсутствует:

```text
RiskFactorState.MISSING
        ↓
RiskPolicy
        ↓
INSUFFICIENT_DATA
        ↓
RiskLevel = None
```

Система не должна подставлять synthetic fallback без отдельно утвержденного правила.

---

```

```

```text

```

```

Full regression:

```text

```

должен завершаться:

```text

```

## 15.14 Assessment Architecture Gate

До реализации Assessment должен быть утвержден отдельный contract, отвечающий минимум на вопросы:

```text
кто orchestrates E2E assessment flow

как выбираются Threat[]

когда запрашивается Current Weather

когда требуется Historical Weather

как формируются derived indicators

как формируется RiskContext

один ли RiskContext используется для нескольких threats

как изолируются failures отдельных threats

кто формирует ERROR

что является transaction boundary
```

Без этого нельзя считать допустимым автоматическое возвращение к первоначальному:

```text
AssessmentService
→ WeatherData
→ RiskEngine
```

flow.

---

## 15.15 Assessment Persistence Gate

До завершения Full MVP должна быть утверждена и реализована persistence model, обеспечивающая:

```text
Assessment

RiskResult[]

RiskFactorResult[]

assessment input snapshot
```

Точный snapshot определяется Assessment Architecture.

Не является обязательным заранее:

```text
WeatherSnapshot
```

как конкретная физическая entity.

Persistence должна гарантировать:

```text
historical result immutability

factor evidence preservation

MISSING semantics preservation

required semantics preservation

sufficient reproducibility
```

---

## 15.16 Готовность истории

History считается готовой, если пользователь может:

```text
открыть список Assessment
```

и:

```text
открыть конкретный Assessment
```

без нового calculation request.

При просмотре history:

```text
Current Weather API
```

и:

```text
Historical Weather API
```

не должны использоваться для автоматического пересчета сохраненного результата.

Изменение текущей погоды или текущих thresholds не должно изменять сохраненный `RiskResult`.

---

## 15.17 Готовность Assessment REST

После утверждения Assessment Contract должны работать целевые capabilities:

```text
POST /api/assessments
```

```text
GET /api/assessments
```

```text
GET /api/assessments/{id}
```

При этом:

```text
INSUFFICIENT_DATA
```

может быть корректным domain result успешной оценки, а не автоматически HTTP error.

Technical failures должны быть отделены от domain missing-data semantics.

Точная REST response model определяется Assessment REST Contract.

Пользователь не должен использовать для основного сценария:

```text

Python console

SQL client

ручной запуск внутренних функций
```

## 15.19 Готовность explainability

Пользовательский результат должен позволять увидеть:

```text

```

Для каждого factor:

```text

actualValue

required

```

Если использовался derived indicator, архитектура должна позволять объяснить его происхождение на уровне соответствующей domain model.

Например:

```text
T10

```

или:

```text

## 15.20 Готовность reference data

Для каждой поддерживаемой threat должны быть доступны:

- название;
- описание;
- объект воздействия;
- возможный вред;
- справочный active season;
- рекомендации;
- официальные sources.

Reference data не должна смешиваться с runtime factor model.

В частности:

```text

```

не означает автоматически:

```text

```

Например, запрещено иметь canonical sections:

```text

```text

как два одновременно действующих варианта.

## 15.24 Что не входит в Definition of Done MVP

Эти capabilities могут рассматриваться после завершения основного MVP.

## 15.25 Full MVP DoD

MVP считается завершенным, когда можно пройти полную цепочку:

```text
Исследование
        ↓
обоснованные предметные rules
        ↓
Location + UserProfile
        ↓
environmental data acquisition
        ↓
normalized observations
        ↓
derived indicators
        ↓
RiskContext
        ↓
threat-specific RiskCalculators
        ↓
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult[]
        ↓
Assessment
        ↓
Persistence
        ↓
History
        ↓
объяснимый UI result
```

При этом должны одновременно выполняться четыре свойства.

### Correctness

```text
расчет соответствует утвержденным rules
```

### Explainability

```text
пользователь понимает,
какие factors сформировали результат
```

### Reproducibility

```text
historical Assessment содержит достаточно
данных и evidence для объяснения результата
```

### Immutability

```text
открытие истории
не приводит к автоматическому пересчету
```

## 15.26 Текущий pre-Assessment статус

На этапе перед проектированием Assessment допускается отдельно зафиксировать:

```text

→ DONE
```

если:

- Domain Model alignment завершен;
- Current Weather pipeline завершен;
- Historical Weather pipeline завершен;
- derived calculations завершены;
- RiskContext завершен;
- четыре Risk Calculators завершены;
- RiskPolicy завершена;
- RiskEngine завершен;
- regression suite зеленый;
- architecture gates пройдены.

При этом:

```text
Full MVP
→ NOT DONE
```

до завершения:

```text
Assessment
+
Persistence
+
History
+
E2E user flow
```

Это не является незавершенностью calculation architecture.

Это означает, что проект перешел от этапа:

```text
Calculation Core
```

к следующей явно определенной архитектурной задаче:

```text
Assessment
```

## 15.27 Главный критерий завершенности

«Сезонный дозор» считается завершенным MVP не тогда, когда реализован один `RiskEngine` или получена погода из API, а когда вся цепочка от предметного исследования до сохраненного объяснимого пользовательского результата является целостной и проверяемой.

Итоговый критерий:

> **«Сезонный дозор» должен быть работающим программным продолжением проведенного исследования: получать и подготавливать реальные environmental data, применять проверяемые модели риска и сохранять объяснимый результат конкретного пользовательского запуска без подмены отсутствующих данных и без необоснованных утверждений о фактическом присутствии угрозы.**

# 16. Возможности дальнейшего развития

## 16.1 Назначение

Первая версия PestWatch сознательно ограничивается:

```text
4 threat models
+
rule-based calculation core
+
минимальным пользовательским Assessment flow
```

После завершения MVP система может развиваться без отказа от основных архитектурных принципов:

```text
provider isolation

normalized domain data

derived calculations

RiskContext

threat-specific RiskCalculators

RiskPolicy

RiskResult

reproducible Assessment
```

Любое расширение должно сначала проверяться на совместимость с этой архитектурой.

Не следует добавлять новую capability только потому, что технически ее возможно реализовать.

---

## 16.2 Расширение списка угроз

В дальнейшем можно добавить новые biological threats.

Например:

### Для человека

- комары;
- другие виды клещей;
- сезонные кровососущие насекомые.

### Для сада

- тля плодовых культур;
- долгоносики;
- листовертки;
- другие распространенные вредители.

### Для огорода

- капустная моль;
- крестоцветные блошки;
- луковая муха;
- морковная муха;
- другие сезонные вредители.

Добавление каждой новой угрозы должно начинаться не с программирования, а с предметного исследования:

```text
Новая Threat
        ↓
Исследование
        ↓
Official Sources
        ↓
определение environmental inputs
        ↓
проверка существующей Domain Model
        ↓
при необходимости новый derived indicator
        ↓
RiskContext impact review
        ↓
RiskCalculator
        ↓
unit + integration tests
```

### Главное ограничение

Новая threat не должна автоматически приводить к добавлению произвольных данных в `RiskContext`.

Для каждого нового input необходимо ответить:

> Является ли это подготовленным domain input, действительно необходимым Risk Calculator?

Если нет — он не должен добавляться в `RiskContext`.

---

## 16.3 Расширение RiskContext

`RiskContext` может развиваться по мере появления новых calculation requirements.

Например, в будущем могут понадобиться:

```text
precipitation history

soil moisture

forecast indicators

vegetation-related observations

additional accumulated indicators
```

Но `RiskContext` не должен превращаться в общий application container.

В него по-прежнему не должны попадать только ради удобства:

```text
Location

UserProfile

Threat

Recommendation

Repository

HTTP objects

provider clients

UI metadata
```

Расширение `RiskContext` должно проходить отдельный architecture review.

---

## 16.4 Новые derived indicators

Появление новой threat может потребовать нового environmental indicator, которого нет непосредственно в provider data.

Правильный flow:

```text
normalized source observations
        ↓
new derived calculator / estimator
        ↓
new derived domain model
        ↓
RiskContext
        ↓
RiskCalculator
```

Не следует переносить generic derived calculation внутрь threat-specific calculator.

Например, если в будущем потребуется:

```text
rolling precipitation total
```

или:

```text
soil moisture estimate
```

его следует рассматривать как самостоятельный derived domain fact.

Canonical principle сохраняется:

```text
derived environmental fact
≠
risk evidence
```

---

## 16.5 Расширение географии

MVP ориентирован на ограниченную географическую область.

В дальнейшем возможно добавление других регионов.

При этом нельзя автоматически считать, что:

```text
thresholds
seasonality
biological behavior
recommendations
```

одинаковы для всей страны.

Перед расширением необходимо проверить:

- климатические особенности;
- распространение threat;
- региональную сезонность;
- региональные источники;
- применимость существующих thresholds;
- доступность environmental data.

Возможный результат исследования:

```text
одна Threat
+
разные regional rules
```

должен рассматриваться как отдельное архитектурное изменение, а не скрытый `if region == ...` внутри существующего calculator.

---

## 16.6 Оценка условий на несколько дней

В будущей версии можно добавить forecast-based assessment.

Например:

```text
Сегодня       ELEVATED

Завтра        HIGH

Через 2 дня   HIGH

Через 3 дня   MODERATE
```

Для этого потребуется отдельный forecast integration contract.

Conceptual flow:

```text
Forecast Weather API
        ↓
normalized forecast observations
        ↓
forecast calculation inputs
        ↓
RiskContext per forecast point / period
        ↓
RiskCalculator
        ↓
RiskResult
```

Важно не смешивать:

```text
current observation
```

и:

```text
forecast observation
```

как будто это один и тот же temporal contract.

Forecast-based result по-прежнему должен называться:

```text
оценка условий
```

а не точным прогнозом фактического появления вредителя.

---

## 16.7 Multi-day derived indicators

Forecast mode может потребовать derived calculations на периоде.

Например:

```text
forecast DailyTemperature[]
        ↓
future Degree Days
```

или:

```text
forecast soil observations
        ↓
future SoilTemperatureEstimate
```

Такие calculations должны иметь явную temporal semantics.

Нельзя молча смешивать:

```text
historical DegreeDays
```

и:

```text
forecast DegreeDays
```

в одном поле без явного contract.

---

## 16.8 График изменения риска

После появления устойчивой истории Assessment можно строить временные графики:

```text
Assessment Date
        ↓
RiskLevel
```

например:

```text
LOW
↓
MODERATE
↓
ELEVATED
↓
HIGH
```

Это presentation capability над уже сохраненными результатами.

Она не должна автоматически пересчитывать исторические Assessment.

График должен использовать:

```text
stored RiskResult
```

а не текущую версию calculation model.

---

## 16.9 Пользовательские наблюдения

В будущей версии пользователь может сообщать о фактическом наблюдении threat.

Например:

```text
Date

Threat

Observation

Comment
```

Это создаст отдельный тип domain evidence:

```text
calculated environmental risk
```

и:

```text
actual user observation
```

Эти данные нельзя смешивать.

User observation не должен автоматически изменять существующий:

```text
RiskFactorResult
```

если соответствующее правило специально не будет утверждено.

## 16.10 Карта наблюдений

После накопления пользовательских observations можно добавить map view.

Например:

```text
● обнаружен клещ

● обнаружен колорадский жук

● обнаружена тля
```

При этом карта должна явно показывать тип данных.

Следует различать:

```text
calculated assessment
```

```text
user-reported observation
```

```text
professional / official observation
```

Пользовательское сообщение не должно автоматически считаться подтвержденным профессиональным наблюдением.

---

## 16.11 Фотография объекта

Пользовательское observation можно расширить фотографией.

Первоначально фотография может использоваться только как вложение к observation.

Более сложный вариант:

```text
Image
        ↓
Computer Vision
        ↓
classification result
```

потребует:

- dataset;
- labeling;
- модели либо внешнего CV service;
- validation accuracy;
- confidence semantics;
- false-positive / false-negative analysis;
- отдельной UI semantics.

Такой результат не должен автоматически подменять biological risk calculation.

---

## 16.12 Персональные уведомления

После появления user accounts можно добавить subscriptions.

Например:

```text
Location:
Тульская область

Threat:
TICK

Notify:
when RiskLevel becomes HIGH
```

Архитектурно notification layer должен потреблять уже готовые:

```text
Assessment / RiskResult
```

а не самостоятельно повторять biological calculation.

---

## 16.13 Automatic scheduled Assessment

Уведомления могут потребовать автоматического запуска assessment без действия пользователя.

Conceptual flow:

```text
Schedule
        ↓
Location + UserProfile
        ↓
Assessment orchestration
        ↓
RiskResult[]
        ↓
Notification rule
```

Это новая application capability.

Она не должна изменять contracts:

```text
RiskCalculator

RiskPolicy

RiskEngine
```

---

## 16.14 Автоматическое обновление официальных сведений

В MVP предметные правила формируются вручную.

В будущем можно исследовать автоматизированное получение publications:

- Роспотребнадзора;
- Россельхозцентра;
- других официальных источников.

Но следует разделять:

```text
получение publication
```

и:

```text
автоматическое изменение calculation rule
```

Второе значительно рискованнее.

Автоматически найденная публикация не должна без review изменять:

```text
threshold

RiskCalculator

Recommendation
```

Минимально безопасный future flow:

```text
Source ingestion
        ↓
human review
        ↓
engineering interpretation
        ↓
approved rule change
```

---

## 16.15 Административный интерфейс

При росте проекта может появиться административная часть.

Она может управлять:

```text
Threat

Source

Recommendation
```

Управление calculation rules требует отдельного решения.

Если thresholds станут редактируемыми:

```text
admin change
        ↓
new rule version
```

а не:

```text
overwrite current value
and silently reinterpret history
```

Это ведет к необходимости versioned calculation model.

---

## 16.16 Versioned calculation model

После появления сохраненной истории изменение calculation rules становится отдельной архитектурной проблемой.

Например, могут измениться:

```text
Tick threshold

Colorado threshold

Cabbage Aphid range

Codling Moth threshold

Degree Days method

RiskPolicy
```

Новый расчет и исторический результат должны оставаться различимыми.

Возможное развитие:

```text
CalculationModelVersion
```

или иной mechanism, позволяющий зафиксировать:

```text
какой набор calculation semantics
использовался при конкретном Assessment
```

Точный технический контракт versioning не входит в MVP.

---

## 16.17 Controlled recalculation

В будущем пользователь может захотеть:

> Пересчитать старый Assessment по новой версии правил.

Это не должно быть side effect обычного открытия history.

Правильная semantics:

```text
Open historical Assessment
→ stored result
```

отдельно:

```text
Recalculate
→ explicit new operation
→ current calculation model
→ new result / new Assessment
```

Исходный historical result должен сохраняться.

---

## 16.18 Richer provenance

Current derived models уже сохраняют provenance, необходимый для собственного calculation.

В будущем Assessment может хранить более богатую provenance:

```text
provider identity

calculation model version

source rule version

provider observation timestamps

derived calculation method version
```

Но richer provenance должна добавляться только при наличии реальной потребности:

```text
auditability

research reproducibility

rule evolution
```

Не следует превращать каждый domain object в полный audit log.

---

## 16.19 Research dataset

После накопления:

```text
Assessment

RiskResult

User Observations
```

может появиться собственный исследовательский dataset.

Например:

```text
Date

Location

calculation inputs

RiskResult

actual observation
```

Это позволит исследовать вопрос:

> Насколько рассчитанный уровень environmental risk связан с фактическими observations?

Такой dataset является отдельным исследовательским artifact и не должен автоматически становиться runtime storage model основного приложения.

---

## 16.20 Машинное обучение

ML не требуется для MVP.

Его использование имеет смысл только после появления качественного dataset.

Возможная future architecture:

```text
environmental observations
+
location
+
historical context
+
verified observations
        ↓
Dataset
        ↓
ML Model
        ↓
prediction
```

До этого rule-based architecture имеет преимущества:

- понятность;
- детерминированность;
- воспроизводимость;
- explainability;
- traceability;
- соответствие масштабу проекта.

Исходный документ также прямо исходит из того, что до появления собственного набора данных rule-based модель более уместна. :contentReference[oaicite:2]{index=2}

---

## 16.21 ML не заменяет текущую модель автоматически

Если ML появится, необходимо отдельно решить:

```text
ML заменяет RiskCalculator?
```

или:

```text
ML является дополнительным signal?
```

или:

```text
ML используется только для research comparison?
```

Нельзя автоматически смешивать:

```text
rule-based RiskLevel
```

и:

```text
probabilistic ML output
```

под одним полем без явной semantics.

## 16.22 Миграция на другую СУБД

При росте объема данных SQLite может перестать быть достаточной.

Возможное развитие:

```text
SQLite
→ PostgreSQL
```

При правильной Repository boundary такая миграция не должна требовать изменения calculation core.

Не должны изменяться только по причине DB migration:

```text
RiskContext

RiskCalculator

RiskPolicy

RiskEngine
```

## 16.23 Замена Weather Provider

В будущем может измениться provider:

```text
Current Weather

Historical Weather

Forecast Weather
```

Provider replacement должен происходить внутри:

```text
Client
+
Adapter
```

при сохранении normalized domain contracts.

То есть:

```text
provider change
```

не должен автоматически означать:

```text
RiskCalculator rewrite
```

## 16.24 Расширение Assessment

После MVP Assessment может включать дополнительные capabilities:

```text
comparison

manual recalculation

calculation version display

provenance display

export

sharing

annotations
```

Но базовый invariant должен сохраняться:

```text
Assessment
→ snapshot конкретного calculation event
```

Исторический Assessment не должен становиться «живой ссылкой» на текущие external data.

## 16.25 Export Assessment

В дальнейшем возможно добавить export:

```text
PDF

JSON

CSV
```

Экспорт должен использовать сохраненное состояние Assessment.

Он не должен запускать новый calculation.

При export желательно сохранять:

```text
Location

Profile

Threat results

factor evidence

timestamp

calculation provenance
```

в объеме, утвержденном Assessment contract.

## 16.26 Расширение explainability

Можно развить explanation layer:

```text
structured factor evidence
        ↓
human-readable composition
```

Например, показывать:

```text
что совпало

что не совпало

чего не хватило

какой derived indicator использован

как он был рассчитан
```

Но explanation не должен становиться новым источником calculation truth.

Canonical source остается:

```text
RiskFactorResult[]
+
RiskResult
+
derived provenance
```

---

## 16.27 Отдельный Explanation Composer

Если пользовательская explainability станет значительно сложнее, можно выделить отдельный component:

```text
ExplanationComposer
```

Но он должен работать после calculation:

```text
RiskResult
+
RiskFactorResult[]
+
presentation metadata
        ↓
ExplanationComposer
```

Он не должен:

- изменять factor states;
- определять RiskLevel;
- применять thresholds.

Для MVP отдельный компонент не требуется.

---

## 16.28 Возможное развитие RiskPolicy

Текущая RiskPolicy использует generic ratio-based semantics.

В будущем могут появиться требования:

```text
weighted factors

different severity models

threat-specific aggregation policy
```

Такое изменение является существенным Architecture Decision.

Нельзя просто добавлять threat-specific `if` внутри текущего generic `RiskPolicy`, не проверив:

```text
остается ли policy действительно generic
```

Возможно, потребуется:

```text
RiskPolicy strategy
```

или другой explicit contract.

Это находится за пределами MVP.

---

## 16.29 Optional factors

Текущая RiskPolicy уже поддерживает:

```text
LIMITED
```

для отсутствующего optional factor.

В текущих четырех calculators все factors required.

Будущая threat model может впервые использовать:

```text
required = false
```

Тогда необходимо отдельно протестировать:

```text
optional MISSING
→ LIMITED

known factors
→ RiskLevel
```

То есть capability уже существует на уровне generic policy, но должна получить реальный domain use case прежде, чем станет частью пользовательских сценариев.

---

## 16.30 Основной принцип развития

Развитие системы должно происходить через добавление новых четко определенных capabilities, а не через постепенное размывание существующих responsibilities.

Для нового требования используется последовательность:

```text
Product / Research Need
        ↓
Architecture Question
        ↓
Domain Contract
        ↓
Component Responsibility
        ↓
Implementation
        ↓
Tests
```

Не следует использовать подход:

```text
добавим поле куда удобнее
        ↓
потом разберемся
```

---

## 16.31 Что должно оставаться стабильным

При развитии проекта желательно сохранять следующие foundational boundaries:

```text
Provider Payload
→ Adapter
→ Normalized Domain Data
```

```text
Normalized Data
→ Derived Calculation
→ Derived Domain Fact
```

```text
Prepared Inputs
→ RiskContext
```

```text
RiskContext
→ RiskCalculator
→ RiskFactorResult[]
```

```text
RiskFactorResult[]
→ RiskPolicy
→ RiskEngine
→ RiskResult
```

```text
RiskResult[]
→ Assessment Boundary
```

Если новое требование требует нарушения одной из этих границ, это должно быть отдельным Architecture Decision, а не локальным refactoring.

## 16.32 Итог возможностей развития

PestWatch может развиваться по нескольким независимым направлениям:

```text
больше Threats

больше Regions

новые environmental inputs

новые derived indicators

forecast assessments

richer history

user observations

maps

notifications

versioned rules

controlled recalculation

richer provenance

research datasets

ML
```

Но расширение должно сохранять ключевой принцип:

> Новая функциональность должна добавляться поверх объяснимой, детерминированной и тестируемой calculation architecture, а не разрушать ее.

MVP остается rule-based системой оценки environmental conditions.

Более сложные probabilistic, predictive или ML capabilities рассматриваются только после появления достаточного предметного и фактического основания.

# 17. Итог системного анализа

## 17.1 Итоговая архитектура

«Сезонный дозор» представляет собой клиент-серверное веб-приложение для объяснимой оценки соответствия environmental conditions условиям активности исследованных биологических угроз.

Актуальная архитектура системы:

```text
                         Пользователь
                              │
                              ▼
                         Web Browser
                              │
                              ▼
                        Flask Backend
                              │
                              ▼
                    Application Layer
                              │
              ┌───────────────┴───────────────┐
              │                               │
              ▼                               ▼
       Threat Selection               Environmental Data
              │                               │
              │                  ┌────────────┴────────────┐
              │                  ▼                         ▼
              │          Current Weather           Historical Weather
              │                  │                         │
              │                  ▼                         ▼
              │             WeatherData            DailyTemperature[]
              │                  │                         │
              │                  ▼                         ▼
              │       SoilTemperatureEstimator     DegreeDaysCalculator
              │                  │                         │
              │                  ▼                         ▼
              │       SoilTemperatureEstimate      DegreeDaysResult
              │                  │                         │
              │                  └──────────┬──────────────┘
              │                             ▼
              │                        RiskContext
              │                             │
              └───────────────┬─────────────┘
                              ▼
                    selected RiskCalculator
                              │
                              ▼
                     RiskFactorResult[]
                              │
                              ▼
                         RiskPolicy
                              │
                              ▼
                         RiskEngine
                              │
                              ▼
                        RiskResult[]
                              │
                              ▼
                     ASSESSMENT BOUNDARY
```

После этой границы начинается следующий application layer:

```text
RiskResult[]
        ↓
Assessment
        ↓
Persistence
        ↓
History
```

Точный contract этой части определяется Assessment Architecture.

---

## 17.2 Центральная архитектурная идея

В актуальной архитектуре нет одного класса, который является владельцем всей предметной логики.

Основная инженерная ценность создается последовательностью независимых stages:

```text
External Environmental Data
        ↓
Normalization
        ↓
Derived Environmental Facts
        ↓
RiskContext
        ↓
Threat-specific Interpretation
        ↓
RiskFactorResult[]
        ↓
Generic Risk Policy
        ↓
RiskResult
```

Поэтому нельзя считать:

```text
RiskEngine
```

монолитным центральным вычислительным компонентом.

Responsibilities разделены следующим образом.

```text
WeatherClient / HistoricalWeatherClient
→ external communication
```

```text
WeatherAdapter / HistoricalWeatherAdapter
→ provider normalization
```

```text
SoilTemperatureEstimator / DegreeDaysCalculator
→ derived environmental calculations
```

```text
RiskContext
→ canonical calculator input boundary
```

```text
RiskCalculator
→ threat-specific rules
```

```text
RiskPolicy
→ generic RiskStatus / RiskLevel semantics
```

```text
RiskEngine
→ composition of RiskResult
```

Таким образом, центральным архитектурным объектом является не отдельный класс, а **calculation pipeline с четко разделенной ответственностью**.

---

## 17.3 Внешние данные

Система использует две разные weather capabilities.

### Current Weather

```text
Location
        ↓
Current Weather Integration
        ↓
WeatherData
```

`WeatherData` представляет normalized provider observations.

Он не является контейнером:

```text
SoilTemperatureEstimate

DegreeDaysResult
```

---

### Historical Weather

```text
Location + period
        ↓
Historical Weather Integration
        ↓
DailyTemperature[]
```

Historical data имеет собственный domain output и не преобразуется в `WeatherData`.

---

## 17.4 Derived environmental calculations

Часть необходимых calculator inputs отсутствует в готовом виде у provider и рассчитывается внутри приложения.

### Soil Temperature at 10 cm

```text
T6
+
T18
        ↓
SoilTemperatureEstimator
        ↓
SoilTemperatureEstimate
```

### Degree Days

```text
DailyTemperature[]
        ↓
DegreeDaysCalculator
        ↓
DegreeDaysResult
```

Ключевой принцип:

```text
derived environmental fact
≠
risk evidence
```

Например:

```text
T10 = 14.2 °C
```

само по себе не означает:

```text
Colorado Beetle risk = HIGH
```

А:

```text
DegreeDaysResult.total = 137.4
```

само по себе не означает:

```text
Codling Moth factor = MATCHED
```

Risk interpretation выполняется только соответствующим Risk Calculator.

---

## 17.5 RiskContext

После подготовки environmental inputs формируется:

```text
RiskContext
```

Он является canonical input contract для всех Risk Calculators.

Текущая модель объединяет:

```text
WeatherData

SoilTemperatureEstimate | None

DegreeDaysResult | None
```

`RiskContext` не содержит:

```text
Location

UserProfile

Threat

Recommendation

RiskLevel

RiskResult

provider clients

Repository
```

Его задача — передать calculators уже подготовленные domain inputs, не связывая их с integration или application layers.

---

## 17.6 Четыре независимые модели угроз

Для MVP используются четыре специализированных calculator.

### Иксодовые клещи

```text
AIR_TEMPERATURE
```

Rule:

```text
temperature >= 10 °C
```

---

### Колорадский жук

```text
SOIL_TEMPERATURE_10CM
```

Rule:

```text
T10 >= 13 °C
```

---

### Капустная тля

```text
AIR_TEMPERATURE
+
HUMIDITY
```

Rules:

```text
25 °C <= temperature <= 26 °C
```

```text
60 % <= humidity <= 70 %
```

---

### Яблонная плодожорка

```text
DEGREE_DAYS_ABOVE_10C
```

Rule:

```text
Degree Days >= 130
```

---

Поле:

```text
Threat.activeSeason
```

остается справочной характеристикой угрозы.

Оно не означает наличие runtime-factor:

```text
SEASON
```

в текущих четырех calculators.

Это исправляет первоначальную модель документа, где все четыре угрозы описывались через `season + ...`. :contentReference[oaicite:3]{index=3}

---

## 17.7 Risk Calculator contract

Все calculators используют единый contract:

```python
evaluate(
    context: RiskContext,
) -> tuple[RiskFactorResult, ...]
```

Risk Calculator:

- выбирает необходимые ему значения из `RiskContext`;
- применяет threat-specific rule;
- формирует factor evidence.

Он не определяет:

```text
итоговый RiskStatus

итоговый RiskLevel
```

и не создает окончательный `RiskResult`.

Canonical output calculator:

```text
RiskFactorResult[]
```

---

## 17.8 RiskFactorResult

Каждый factor имеет структурированный результат:

```text
factor

state

actualValue

expected

explanation

required
```

Поддерживаемые состояния:

```text
MATCHED

NOT_MATCHED

MISSING
```

Главный invariant:

```text
MISSING
≠
NOT_MATCHED
```

То есть отсутствие данных не интерпретируется как отрицательный результат проверки.

---

## 17.9 RiskPolicy

`RiskPolicy` выполняет generic interpretation factor evidence.

Status semantics:

```text
нет factors
→ INSUFFICIENT_DATA
```

```text
required factor = MISSING
→ INSUFFICIENT_DATA
```

```text
optional factor = MISSING
→ LIMITED
```

```text
missing factors отсутствуют
→ CALCULATED
```

Для известных factors определяется доля:

```text
MATCHED / known factors
```

и `RiskLevel`:

```text
< 0.25
→ LOW

0.25–<0.50
→ MODERATE

0.50–<0.75
→ ELEVATED

>= 0.75
→ HIGH
```

`RiskPolicy` не содержит biological thresholds конкретных угроз.

---

## 17.10 RiskEngine

`RiskEngine` получает:

```text
threatCode
+
RiskFactorResult[]
```

вызывает:

```text
RiskPolicy
```

и формирует:

```text
RiskResult
```

Canonical flow:

```text
RiskFactorResult[]
        ↓
RiskPolicy
        ↓
RiskEngine
        ↓
RiskResult
```

RiskEngine не:

- получает погоду;
- рассчитывает T10;
- рассчитывает Degree Days;
- применяет thresholds угроз;
- выполняет persistence;
- знает Weather API.

Таким образом, старая формулировка:

```text
погодные данные
+
дата
+
правила
        ↓
RiskEngine
        ↓
оценка
```

больше не является актуальной архитектурой. Именно такая модель была зафиксирована в исходном итоговом разделе. :contentReference[oaicite:4]{index=4}

---

## 17.11 RiskStatus semantics

Поддерживаются:

```text
CALCULATED

LIMITED

INSUFFICIENT_DATA

ERROR
```

### CALCULATED

Все необходимые factor data доступны.

### LIMITED

Все required factors доступны, но отсутствует optional factor.

При этом:

```text
RiskLevel
```

может существовать.

### INSUFFICIENT_DATA

Отсутствует required factor либо factors отсутствуют.

```text
RiskLevel = None
```

### ERROR

Представляет technical inability to complete calculation.

`ERROR` не выводится `RiskPolicy` из:

```text
MATCHED

NOT_MATCHED

MISSING
```

Точный production contract `ERROR` относится к Assessment/application orchestration.

---

## 17.12 Независимость threat evaluations

Каждая threat model оценивается независимо.

Например:

```text
CABBAGE_APHID
→ CALCULATED
```

может существовать одновременно с:

```text
COLORADO_BEETLE
→ INSUFFICIENT_DATA
```

если отсутствует только T10 input.

А failure Historical Weather не должен автоматически мешать расчету threat, которой historical data не требуется.

Canonical principle:

```text
data sufficiency
→ per threat
```

а не:

```text
one missing indicator
→ whole Assessment unavailable
```

---

## 17.13 Принцип достоверности

Система не скрывает отсутствие необходимых данных.

Используется явное различие:

```text
MATCHED

NOT_MATCHED

MISSING
```

и:

```text
CALCULATED

LIMITED

INSUFFICIENT_DATA

ERROR
```

Это позволяет отказаться от:

- искусственного заполнения отсутствующих значений;
- подмены `None` нулем;
- подмены soil temperature температурой воздуха;
- вымышленного Degree Days result;
- необоснованно точного пользовательского результата.

Этот принцип исходного системного анализа сохраняется полностью. :contentReference[oaicite:5]{index=5}

---

## 17.14 Принцип объяснимости

Пользователь получает не только:

```text
HIGH
```

но и структурированное factor evidence.

Например:

```text
AIR_TEMPERATURE

actualValue = 12.3

expected = >= 10 °C

state = MATCHED
```

или:

```text
HUMIDITY

actualValue = 50 %

expected = 60–70 %

state = NOT_MATCHED
```

В случае отсутствия данных:

```text
state = MISSING
```

Derived inputs имеют отдельную provenance.

Например:

```text
T6 + T18
→ LINEAR_INTERPOLATION
→ T10
```

или:

```text
DailyTemperature[]
+
base 10 °C
→ DegreeDaysResult
```

То есть объяснимость строится на двух уровнях:

```text
derived provenance
```

и:

```text
risk factor evidence
```

Старый пример с:

```text
✓ сезон соответствует
```

больше не используется, поскольку `SEASON` не является текущим runtime-factor. В первоначальном итоговом разделе именно такой пример еще присутствовал. :contentReference[oaicite:6]{index=6}

---

## 17.15 Принцип детерминированности

При одинаковом:

```text
RiskContext

RiskCalculator implementation
```

calculator возвращает одинаковые:

```text
RiskFactorResult[]
```

При одинаковых:

```text
RiskFactorResult[]

RiskPolicy
```

формируются одинаковые:

```text
RiskStatus

RiskLevel
```

Derived calculations также детерминированы:

```text
same observations
+
same method
→ same derived result
```

Runtime calculation не использует:

- случайные значения;
- generative AI;
- недокументированные корректировки;
- скрытые fallback values.

---

## 17.16 Принцип воспроизводимости истории

Исторический Assessment должен открываться:

```text
без нового Weather API request
```

и:

```text
без автоматического recalculation
```

После сохранения изменение:

```text
погоды

historical provider data

thresholds

RiskPolicy

derived calculation method
```

не должно автоматически менять исторический результат.

При этом точный состав:

```text
assessment input snapshot
```

пока не утвержден.

Следовательно, старая формулировка:

```text
Assessment хранит WeatherSnapshot
```

не является окончательным canonical contract.

Исходный раздел напрямую фиксировал `погодный snapshot` как уже утвержденную часть Assessment. :contentReference[oaicite:7]{index=7} После Historical Weather и derived indicators этот вопрос должен решаться отдельно.

## 17.25 Итог проекта

Проект «Сезонный дозор» демонстрирует инженерный цикл:

```text
Реальная проблема
        ↓
Исследование
        ↓
Анализ источников
        ↓
Формулировка ограничений
        ↓
Проектирование domain model
        ↓
Интеграция реальных данных
        ↓
Derived calculations
        ↓
Rule-based risk modeling
        ↓
Automated tests
        ↓
Assessment
        ↓
Работающий MVP
```

Итоговая задача приложения формулируется следующим образом:

> **«Сезонный дозор» получает реальные текущие и, когда это необходимо, исторические environmental data для выбранной территории, преобразует их в нормализованные и вычисляемые domain indicators, применяет отдельные объяснимые модели исследованных биологических угроз и помогает пользователю определить, насколько доступные условия соответствуют зафиксированным условиям повышенного сезонного риска.**

Приложение:

```text
не подтверждает фактическое присутствие вредителя

не является медицинской системой диагностики

не заменяет профессиональный фитосанитарный мониторинг

не рассчитывает научную вероятность появления угрозы
```

Его задача — превратить исследование, внешние environmental data и проверяемые инженерные правила в понятный и объяснимый пользовательский инструмент.
