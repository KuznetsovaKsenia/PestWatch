# Техническое задание и пользовательские сценарии

## Проект

# Сезонный дозор

### Оценка сезонного риска клещей и вредителей растений

Версия документа: 1.0

---

# 1. Назначение проекта

## 1.1 Общая информация

Проект «Сезонный дозор» представляет собой образовательное веб-приложение для оценки сезонного риска активности клещей и вредителей растений на территории Центральной России.

Приложение получает актуальные погодные данные для выбранной пользователем территории и сопоставляет их с правилами сезонной активности конкретных биологических угроз.

На основании полученных данных система определяет один из четырех уровней сезонного риска:

- низкий;
- умеренный;
- повышенный;
- высокий.

Для каждой оценки система показывает:

- название угрозы;
- текущий уровень риска;
- факторы, повлиявшие на результат;
- краткое объяснение;
- профилактические рекомендации;
- источник, на основании которого сформированы правила оценки.

Проект не предназначен для точного прогнозирования фактического появления вредителя в конкретной точке.

Результат работы системы показывает, насколько текущие сезонные и погодные условия соответствуют известным условиям активности рассматриваемой угрозы.

---

## 1.2 Основание для разработки

Проект является результатом предварительного исследования сезонных биологических угроз в Центральной России.

В ходе исследования установлено, что активность различных видов зависит от разных факторов.

Например:

- для иксодовых клещей значимы сезон и температура;
- для колорадского жука — температура почвы;
- для капустной тли — температура и влажность;
- для яблонной плодожорки — накопленная сумма эффективных температур.

Исследование также показало, что погодные условия позволяют оценивать период повышенного риска, но не позволяют достоверно утверждать о фактическом наличии конкретного вредителя.

Поэтому в проекте используется модель **оценки сезонного риска**, а не модель точного прогнозирования появления вредителей.

---

## 1.3 Выявленная проблема

Обычному жителю Центральной России, владельцу дачного, садового или огородного участка сложно своевременно определить, какие сезонные биологические угрозы актуальны в данный момент для его региона и объекта интереса. Официальная информация существует, но распределена между различными санитарными и аграрными источниками, публикуется в разных форматах и требует самостоятельного поиска и интерпретации.

Обычному пользователю сложно самостоятельно определить, какие сезонные биологические угрозы актуальны в данный момент для его территории.

Информация существует в официальных источниках, однако:

- относится к различным областям;
- публикуется разными организациями;
- распределена по региональным ресурсам;
- представлена в разных форматах;
- требует самостоятельного поиска;
- требует специальных знаний для интерпретации погодных и сезонных факторов.

Пользователь может видеть текущую температуру, влажность и прогноз погоды, но без дополнительных знаний не может определить, что эти показатели означают с точки зрения активности конкретного вредителя.

---

## 1.4 Предлагаемое решение

Автоматически оценивать соответствие текущих погодных и сезонных условий известным условиям активности конкретных биологических угроз и заранее информировать пользователя о повышенном риске.

Приложение должно автоматически выполнять следующую последовательность:

```text
Выбор территории
        ↓
Получение погодных данных
        ↓
Определение актуальных угроз
        ↓
Применение правил для каждой угрозы
        ↓
Определение уровня риска
        ↓
Объяснение результата
        ↓
Профилактические рекомендации
```

Таким образом, приложение преобразует профессиональные сведения о сезонных условиях активности вредителей и текущие погодные данные в понятный обычному пользователю индикатор риска.

# 2. Цели проекта

## 2.1 Основная цель

Разработать веб-приложение, позволяющее пользователю на основании текущих погодных и сезонных условий получить понятную оценку уровня риска активности клещей и вредителей растений.

---

## 2.2 Пользовательские цели

Приложение должно помочь пользователю:

- определить актуальные для него сезонные угрозы;
- увидеть текущий уровень риска;
- понять причины полученной оценки;
- узнать, какие профилактические действия рекомендуется выполнить;
- получить ссылку на официальный источник информации.

---

## 2.3 Исследовательская цель

Продемонстрировать практическое применение результатов предварительного исследования.

Программный продукт должен использовать выявленные в исследовании зависимости между:

- сезоном;
- температурой;
- влажностью;
- температурой почвы;
- накопленной температурой;
- другими погодными факторами;
- активностью конкретных биологических угроз.

---

## 2.4 Инженерные цели

В рамках проекта необходимо:

- разработать клиент-серверное веб-приложение;
- реализовать получение актуальных погодных данных через внешний API;
- реализовать собственный модуль оценки риска;
- использовать отдельные правила для различных угроз;
- обеспечить объяснимость результата;
- реализовать хранение данных приложения;
- обеспечить независимость расчетной логики от пользовательского интерфейса.

---

## 2.5 Образовательные цели

Проект должен продемонстрировать применение:

- Python;
- веб-разработки;
- REST API;
- работы с внешними данными;
- базы данных;
- алгоритмов принятия решений;
- результатов предметного исследования при разработке программного продукта.

---

## 2.6 Практические цели

В результате разработки должен быть создан законченный программный продукт, который:

- запускается на персональном компьютере;
- получает реальные погодные данные;
- выполняет оценку риска;
- объясняет полученный результат;
- готов к демонстрации и защите.

# 5. Архитектура решения

## 5.1 Общая архитектура

Проект реализуется как клиент-серверное веб-приложение.

```text
                  Пользователь
                       │
                       ▼
                 Web Browser
            HTML / CSS / JavaScript
                       │
                  HTTP / JSON
                       │
                       ▼
                Flask Backend
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Weather       Risk        History
      Service       Service     Service
          │            │            │
          ▼            ▼            ▼
     Weather API   Risk Engine   Repository
                       │            │
                       ▼            ▼
                  Risk Profiles    SQLite
```

---

## 5.2 Weather Service

Отвечает за получение внешних погодных данных.

Weather Service:

- получает территорию;
- обращается к Weather API;
- получает погодные показатели;
- преобразует внешний ответ во внутреннюю модель приложения.

Остальные компоненты системы не должны зависеть от формата конкретного Weather API.

---

## 5.3 Risk Engine

Risk Engine является центральным вычислительным компонентом приложения.

Он получает:

- текущую дату;
- погодные данные;
- выбранную территорию;
- профиль угрозы;
- правила оценки.

На выходе формируется результат:

```text
RiskResult

threat
riskLevel
factors
explanation
recommendations
sources
```

---

## 5.4 Правила оценки

Каждая угроза имеет собственный набор правил.

Не допускается использование одной универсальной формулы для всех видов.

Пример:

```text
Иксодовые клещи
    ↓
сезон + температура + территория

Колорадский жук
    ↓
сезон + температура почвы

Капустная тля
    ↓
сезон + температура + влажность

Яблонная плодожорка
    ↓
сезон + сумма эффективных температур
```

---

## 5.5 Уровни риска

Система использует четыре качественных уровня:

```text
LOW       → Низкий
MODERATE  → Умеренный
ELEVATED  → Повышенный
HIGH      → Высокий
```

Уровень риска не является вероятностью появления вредителя.

В интерфейсе запрещается представлять результат в форме:

```text
Вероятность появления клеща — 87%
```

если такая вероятность не подтверждена отдельной научной моделью.

---

## 5.6 Объяснимость результата

Каждая оценка должна содержать объяснение.

Например:

```text
Уровень риска: ПОВЫШЕННЫЙ

На оценку повлияли:

✓ текущий месяц входит в сезон активности;
✓ температура соответствует условиям активности;
✓ влажность находится в благоприятном диапазоне.
```

Пользователь должен иметь возможность понять, почему система получила конкретный результат.

---

## 5.7 Источники правил

Каждое правило должно быть связано с источником, на основании которого оно сформировано.

Основные источники проекта:

- Роспотребнадзор;
- Россельхозцентр.

Это позволяет отделить:

```text
официальные сведения
```

от

```text
инженерной логики приложения
```

# 6. Пользовательские роли

## 6.1 Основной пользователь

Основной пользователь — человек без специальных профессиональных знаний.

Он использует приложение для получения информации о текущем сезонном риске.

---

## 6.2 Пользователь профиля «Человек»

Основная задача:

оценить сезонный риск контакта с опасными для человека членистоногими.

В MVP:

- иксодовые клещи.

Типичный сценарий:

> Пользователь собирается на прогулку в лес или на дачу и хочет понять, актуален ли сейчас сезонный риск клещей.

---

## 6.3 Пользователь профиля «Сад»

Основная задача:

оценить актуальность сезонных вредителей садовых культур.

В MVP:

- яблонная плодожорка.

Типичный сценарий:

> Пользователь хочет понять, соответствуют ли текущие условия периоду повышенной активности вредителя яблони.

---

## 6.4 Пользователь профиля «Огород»

Основная задача:

оценить актуальность вредителей овощных культур.

В MVP:

- колорадский жук;
- капустная тля.

Типичный сценарий:

> Пользователь выращивает картофель и капусту и хочет увидеть, для каких вредителей текущие погодные условия являются благоприятными.

---

## 6.5 Системные участники

### Weather API

Предоставляет актуальные погодные данные.

Weather API не принимает решений об уровне риска.

---

### Risk Engine

Выполняет расчет.

Risk Engine не является пользовательской ролью, но выступает основным системным участником пользовательского сценария оценки.

---

### База данных

Хранит:

- угрозы;
- правила;
- рекомендации;
- источники;
- историю оценок.

# Итог разделов 1–6

Проект представляет собой веб-приложение, которое преобразует текущие погодные и сезонные данные в объяснимую оценку уровня сезонного риска для конкретных биологических угроз.

Ключевой принцип проекта:

> **Система не предсказывает наличие вредителя — она определяет, насколько текущие условия соответствуют известному периоду повышенного риска.**

Именно это ограничение обеспечивает соответствие программного решения результатам проведенного исследования.

Пользовательские истории описывают функциональность приложения с точки зрения конечного пользователя.

Каждая история отражает конкретную потребность пользователя и ожидаемый результат взаимодействия с системой.

User Stories используются как основа для:

- разработки пользовательских сценариев (Use Cases);
- формирования функциональных требований;
- проектирования пользовательского интерфейса;
- декомпозиции задач разработки;
- подготовки тестовых сценариев.

---

## US-001 Выбор территории

**Как пользователь**

я хочу выбрать населенный пункт или территорию,

**чтобы**

получить оценку сезонного риска с учетом погодных условий выбранного места.

### Ценность

Оценка выполняется не для абстрактной территории Центральной России, а с использованием актуальных погодных данных выбранного пользователем места.

---

## US-002 Получение актуальных погодных данных

**Как пользователь**

я хочу, чтобы приложение автоматически получало актуальные погодные данные,

**чтобы**

мне не приходилось самостоятельно вводить температуру, влажность и другие показатели.

### Ценность

Уменьшается количество ручных действий и исключаются ошибки при переносе погодных данных.

---

## US-003 Просмотр погодных условий

**Как пользователь**

я хочу видеть погодные показатели, использованные системой,

**чтобы**

понимать, на основании каких исходных данных выполняется оценка риска.

### Ценность

Расчет становится прозрачным и проверяемым.

---

## US-004 Выбор профиля «Человек»

**Как пользователь**

я хочу выбрать профиль «Человек»,

**чтобы**

увидеть сезонные угрозы, представляющие риск непосредственно для меня.

### Ценность

Пользователь получает только релевантную ему информацию.

В MVP для данного профиля оценивается риск активности иксодовых клещей.

## US-005 Выбор профиля «Сад»

**Как пользователь**

я хочу выбрать профиль «Сад»,

**чтобы**

получить информацию об актуальных сезонных вредителях садовых растений.

### Ценность

Пользователь может отдельно оценивать угрозы для плодовых культур.

В MVP для данного профиля оценивается риск активности яблонной плодожорки.

---

## US-006 Выбор профиля «Огород»

**Как пользователь**

я хочу выбрать профиль «Огород»,

**чтобы**

получить информацию об актуальных вредителях овощных культур.

### Ценность

Пользователь получает оценку угроз, относящихся непосредственно к выращиваемым огородным культурам.

В MVP оцениваются:

- колорадский жук;
- капустная тля.

---

## US-007 Запуск оценки сезонного риска

**Как пользователь**

я хочу запустить оценку сезонного риска,

**чтобы**

узнать, насколько текущие условия соответствуют периоду активности выбранных угроз.

### Ценность

Пользователь получает результат на основании текущей погоды, сезона и правил конкретной угрозы.

---

## US-008 Просмотр уровня риска

**Как пользователь**

я хочу видеть понятный уровень риска для каждой актуальной угрозы,

**чтобы**

быстро оценить текущую ситуацию.

### Ценность

Пользователю не требуется самостоятельно интерпретировать исходные погодные показатели.

Система использует четыре уровня:

- низкий;
- умеренный;
- повышенный;
- высокий.

---

## US-009 Просмотр причин оценки

**Как пользователь**

я хочу видеть, какие факторы повлияли на уровень риска,

**чтобы**

понимать, почему система получила именно такой результат.

### Ценность

Оценка является объяснимой, а не представляет собой неизвестным образом рассчитанное значение.

Например:

```text
Уровень риска: ПОВЫШЕННЫЙ

На оценку повлияли:

✓ текущий месяц входит в сезон активности;
✓ температура соответствует условиям активности;
✓ влажность находится в благоприятном диапазоне.
```

---

## US-010 Просмотр факторов, не повышающих риск

**Как пользователь**

я хочу видеть не только совпавшие, но и не совпавшие условия,

**чтобы**

получить полную картину расчета.

### Ценность

Пользователь может понять, почему уровень риска оказался, например, умеренным, а не высоким.

Пример:

```text
✓ сезон активности начался;
✓ температура соответствует условиям активности;
✗ влажность ниже благоприятного диапазона.
```

---

## US-011 Просмотр информации об угрозе

**Как пользователь**

я хочу открыть подробную карточку конкретной угрозы,

**чтобы**

узнать, что это за организм и какой вред он может причинить.

### Ценность

Результат оценки дополняется необходимой справочной информацией.

Карточка должна содержать:

- название;
- краткое описание;
- объект воздействия;
- характер возможного вреда;
- период сезонной активности.

---

## US-012 Получение профилактических рекомендаций

**Как пользователь**

я хочу получить рекомендации при повышенном сезонном риске,

**чтобы**

понимать, какие профилактические действия можно выполнить.

### Ценность

Приложение не только сообщает об условиях риска, но и помогает пользователю перейти к профилактическим действиям.

Рекомендации должны иметь информационный характер и основываться на официальных источниках.

---

## US-013 Просмотр официального источника

**Как пользователь**

я хочу видеть источник, на основании которого сформировано правило или рекомендация,

**чтобы**

при необходимости самостоятельно проверить информацию.

### Ценность

Повышается прозрачность и доверие к результатам приложения.

В MVP основными источниками являются:

- Роспотребнадзор;
- Россельхозцентр.

---

## US-014 Понимание ограничения оценки

**Как пользователь**

я хочу понимать, что высокий уровень риска не означает гарантированное наличие вредителя,

**чтобы**

правильно интерпретировать результат.

### Ценность

Приложение не создает ложного представления о точности оценки.

Пользователю должно быть явно сообщено:

> Оценка показывает соответствие текущих условий периоду активности и не подтверждает фактическое наличие вредителя в конкретном месте.

---

## US-015 Просмотр нескольких угроз

**Как пользователь**

я хочу получить результаты сразу для всех угроз выбранного профиля,

**чтобы**

не запускать отдельную оценку для каждого вредителя.

### Ценность

Например, для профиля «Огород» пользователь за один расчет получает результаты для:

- колорадского жука;
- капустной тли.

---

## US-016 Повторная оценка для другой территории

**Как пользователь**

я хочу изменить территорию и повторить расчет,

**чтобы**

сравнить сезонную ситуацию в разных местах.

### Ценность

Приложение можно использовать, например, перед поездкой на дачу или природу в другой район.

---

## US-017 Повторная оценка для другого профиля

**Как пользователь**

я хочу переключаться между профилями «Человек», «Сад» и «Огород»,

**чтобы**

получать разные группы актуальных угроз без повторного ввода территории.

### Ценность

Одни и те же погодные данные могут использоваться для нескольких видов оценки.

---

## US-018 Просмотр истории оценок

**Как пользователь**

я хочу видеть ранее выполненные оценки,

**чтобы**

посмотреть, как менялся уровень сезонного риска.

### Ценность

Пользователь может сравнить результаты, полученные в разные даты.

---

## US-019 Просмотр деталей исторической оценки

**Как пользователь**

я хочу открыть ранее выполненную оценку,

**чтобы**

увидеть погодные данные и результат, которые были актуальны на момент расчета.

### Ценность

Исторический результат не пересчитывается по текущей погоде и остается воспроизводимым.

---

## US-020 Обработка недоступности погодного сервиса

**Как пользователь**

я хочу получить понятное сообщение, если погодные данные временно недоступны,

**чтобы**

понимать, почему расчет невозможно выполнить.

### Ценность

Ошибка внешнего сервиса не выглядит как поломка всего приложения.

Система не должна выполнять оценку на вымышленных или отсутствующих погодных данных.

---

## US-021 Обработка неполных погодных данных

**Как пользователь**

я хочу знать, если для конкретной угрозы не хватает необходимого погодного показателя,

**чтобы**

не получить необоснованный уровень риска.

### Ценность

Система не подменяет отсутствующие данные произвольными значениями.

Например, если правило требует температуру почвы, а Weather API ее не предоставляет, приложение должно либо использовать заранее определенный допустимый альтернативный способ оценки, либо сообщить об ограничении расчета.

---

## US-022 Простое представление результата

**Как пользователь**

я хочу получить результат в понятной форме,

**чтобы**

мне не требовались знания биологии или метеорологии.

### Ценность

Профессиональные показатели преобразуются в понятную структуру:

```text
Что представляет угрозу?

↓

Какой сейчас уровень риска?

↓

Почему система так решила?

↓

Что можно сделать?

↓

Откуда взята информация?
```

---

# 7.2 Связь пользовательских историй с результатами исследования

Пользовательские истории сформированы на основании выявленной в исследовании проблемы.

Исследование показало, что существующая информация:

- распределена между различными источниками;
- требует самостоятельного поиска;
- требует интерпретации погодных показателей;
- относится к разным группам угроз.

Поэтому основной пользовательской ценностью приложения является не предоставление новых биологических данных, а автоматическое сопоставление:

```text
Территория
+
Текущая погода
+
Сезон
+
Правила конкретной угрозы
        ↓
Понятная оценка риска
        ↓
Объяснение
        ↓
Профилактическая информация
```

---

# 7.3 Границы пользовательских историй

В User Stories первой версии сознательно отсутствуют:

- распознавание вредителей по фотографии;
- пользовательская карта находок;
- регистрация и авторизация;
- push-уведомления;
- Telegram-бот;
- AI-консультант;
- медицинская диагностика;
- рекомендации по лечению;
- расчет дозировок средств защиты растений;
- автоматическое определение фактического присутствия вредителя.

Данные возможности не относятся к MVP.

# 7.4 Итог

Пользовательские истории описывают полный пользовательский путь первой версии приложения:

```text
Выбрать территорию
        ↓
Получить погоду
        ↓
Выбрать профиль
        ↓

        ↓

        ↓
```

Таким образом, каждая пользовательская история непосредственно поддерживает основную задачу продукта — сделать данные о сезонных биологических угрозах понятными и применимыми для обычного пользователя.

# UC-001 Выбор территории

## Цель

Выбрать территорию, для которой будет выполняться оценка сезонного риска.

## Участники

Основной пользователь.

## Предусловия

- приложение запущено;
- главная страница доступна.

## Основной сценарий

1. Пользователь открывает приложение.
2. Система отображает форму выбора территории.
3. Пользователь вводит название населенного пункта.
4. Система выполняет поиск территории.
5. Система отображает найденный вариант.
6. Пользователь подтверждает выбор.
7. Выбранная территория становится текущей.
8. Система получает возможность запросить для нее погодные данные.

## Альтернативный сценарий

### 4а. Найдено несколько населенных пунктов

1. Система отображает список подходящих вариантов.
2. Для каждого варианта отображается дополнительная информация о территории.
3. Пользователь выбирает нужный вариант.
4. Выполнение продолжается с шага 7 основного сценария.

## Исключительная ситуация

### 4б. Территория не найдена

Система отображает сообщение:

> Не удалось найти указанную территорию. Проверьте название и попробуйте снова.

Расчет риска не выполняется.

## Результат

В системе определена территория, для которой могут быть получены погодные данные.

---

# UC-002 Получение погодных данных

## Цель

Получить актуальные погодные показатели для выбранной территории.

## Участники

- основной пользователь;
- Weather API.

## Предусловия

- территория выбрана;
- доступно подключение к Weather API.

## Основной сценарий

1. Система формирует запрос к Weather API.
2. Weather API возвращает погодные данные.
3. Система проверяет полученный ответ.
4. Внешние данные преобразуются во внутренний формат приложения.
5. Система сохраняет данные для текущей оценки.
6. Пользователю отображаются основные погодные показатели.

Минимально отображаются:

- температура воздуха;
- относительная влажность;
- осадки;
- скорость ветра.

Дополнительные показатели отображаются при их наличии и необходимости.

## Исключительная ситуация

### 2а. Weather API недоступен

Система отображает сообщение:

> Не удалось получить актуальные погодные данные. Попробуйте выполнить оценку позже.

Расчет риска не выполняется.

### 2б. Weather API вернул некорректный ответ

Система не использует полученные данные и сообщает о невозможности выполнить расчет.

## Результат

Получен проверенный набор погодных данных для выбранной территории.

# UC-003 Выбор пользовательского профиля

## Соответствие профилей угрозам MVP

# UC-004 Выполнение оценки сезонного риска

## Цель

Получить уровень сезонного риска для угроз выбранного профиля.

## Участники

Основной пользователь.

## Предусловия

- выбрана территория;
- получены погодные данные;
- выбран профиль;
- доступны правила оценки.

## Основной сценарий

1. Пользователь запускает оценку.
2. Система определяет угрозы выбранного профиля.
3. Для каждой угрозы система загружает соответствующие правила.
4. Проверяется наличие необходимых исходных данных.
5. Система применяет правила к текущим сезонным и погодным условиям.
6. Для каждой угрозы определяется уровень риска.
7. Формируются факторы, объясняющие результат.
8. Формируются профилактические рекомендации.
9. Результаты сохраняются в истории.
10. Система открывает страницу результатов.

## Результат

Для каждой доступной угрозы сформирован объяснимый результат оценки.

---

# UC-005 Просмотр результатов оценки

## Цель

Быстро определить текущие уровни сезонного риска.

## Участники

Основной пользователь.

## Предусловия

Оценка успешно выполнена.

## Основной сценарий

1. Система отображает выбранную территорию.
2. Отображается дата и время расчета.
3. Отображаются погодные данные, использованные при расчете.
4. Для каждой угрозы отображается отдельная карточка.
5. В карточке отображаются:
   - название угрозы;
   - уровень риска;
   - краткое объяснение.
6. Пользователь сравнивает результаты.
7. При необходимости пользователь открывает подробную информацию.

## Пример

```text
Москва

Погодные условия:
+18 °C
Влажность 67%

--------------------------------

Иксодовые клещи

Уровень риска:
ПОВЫШЕННЫЙ

Текущие условия соответствуют
периоду повышенной активности.

[Подробнее]
```

## Результат

Пользователь получил сводную картину сезонных рисков.

---

# UC-006 Просмотр объяснения оценки

## Цель

Понять причины установленного уровня риска.

## Участники

Основной пользователь.

## Предусловия

Для угрозы существует рассчитанный результат.

## Основной сценарий

1. Пользователь открывает подробности результата.
2. Система отображает факторы оценки.
3. Для каждого фактора отображается его состояние.
4. Пользователь видит, какие условия повысили или не повысили уровень риска.

## Пример

```text
Иксодовые клещи

Уровень риска: ПОВЫШЕННЫЙ

Почему:

✓ текущая дата входит в сезон активности;

✓ температура соответствует
  условиям активности;

✗ дополнительный фактор риска
  отсутствует.
```

## Обязательное пояснение

На странице должно отображаться сообщение:

> Уровень риска показывает соответствие текущих условий периоду активности и не подтверждает фактическое наличие вредителя в конкретном месте.

## Результат

Пользователь понимает происхождение результата.

---

# UC-007 Просмотр карточки угрозы

## Цель

Получить справочную информацию о конкретной угрозе.

## Участники

Основной пользователь.

## Предусловия

Угроза присутствует в справочнике системы.

## Основной сценарий

1. Пользователь выбирает угрозу.

## 8.3 Основной успешный сценарий

Типичный успешный сценарий использования приложения выглядит следующим образом.

1. Пользователь открывает приложение.
2. Выбирает населенный пункт.
3. Система получает актуальные погодные данные для выбранной территории.
4. Пользователь видит основные погодные показатели.
5. Пользователь выбирает профиль:
   - «Человек»;
   - «Сад»;
   - «Огород».
6. Система определяет угрозы, относящиеся к выбранному профилю.
7. Пользователь запускает оценку.
8. Система проверяет наличие данных, необходимых для соответствующих правил.
9. Для каждой угрозы выполняется независимая оценка.
10. Система определяет уровень сезонного риска.
11. Пользователю отображаются результаты.
12. Пользователь открывает интересующую угрозу.
13. Система показывает факторы, повлиявшие на результат.
14. Пользователь получает профилактические рекомендации.
15. При необходимости пользователь открывает официальный источник.
16. Выполненная оценка сохраняется в истории.

### Результат

Пользователь получает понятную и объяснимую оценку актуальных сезонных рисков для выбранной территории и профиля.

## 8.4 Сценарий при повышенном или высоком риске

Если для угрозы определен уровень:

- «Повышенный»;
- «Высокий»,

система должна дополнительно обратить внимание пользователя на профилактические действия.

Последовательность:

```text
Получен повышенный / высокий риск
        ↓
Выделить результат в интерфейсе
        ↓
Показать причины оценки
        ↓
Показать профилактические рекомендации
        ↓
Показать ограничение модели
        ↓
Предоставить официальный источник
```

При этом система не должна использовать формулировки:

> «Вредитель точно появился».

> «Вероятность укуса составляет 80%».

> «На выбранной территории находятся клещи».

Допустимая формулировка:

> **Текущие погодные и сезонные условия соответствуют периоду повышенной активности. Рекомендуется обратить внимание на профилактические меры.**

## 8.5 Сценарий при низком риске

Низкий уровень риска также не должен интерпретироваться как отсутствие угрозы.

Последовательность:

1. Система определяет уровень «Низкий».
2. Отображает факторы оценки.
3. Объясняет, какие условия в настоящий момент не соответствуют периоду повышенной активности.
4. Отображает общее ограничение модели.

Недопустимая формулировка:

> «Вредителей нет».

Допустимая формулировка:

> **По используемым системой факторам текущие условия слабо соответствуют периоду повышенной активности. Это не подтверждает отсутствие вредителя на конкретной территории.**

## 8.7 Сценарий при недоступности внешнего сервиса

Weather API является внешней зависимостью приложения.

При его недоступности:

1. приложение продолжает работать;
2. пользователь может открыть справочную информацию;

4. новая оценка, требующая актуальной погоды, не выполняется;
5. пользователю отображается понятное сообщение об ошибке.

Система не должна использовать устаревшие погодные данные как актуальные без явного уведомления пользователя.

## 8.9 Общие правила выполнения пользовательских сценариев

Для всех Use Cases действуют следующие правила.

### Правило 1. Отсутствие данных не заменяется предположением

Если необходимого значения нет, система не должна создавать его самостоятельно.

---

### Правило 2. Каждая угроза оценивается независимо

Результат одной угрозы не влияет автоматически на другую.

---

### Правило 3. Результат должен быть объяснимым

Для каждого рассчитанного уровня пользователь должен иметь возможность увидеть факторы, повлиявшие на оценку.

---

### Правило 4. Результат не является вероятностью

Уровни:

- низкий;
- умеренный;
- повышенный;
- высокий

являются качественной оценкой соответствия текущих условий правилам сезонной активности.

Они не являются математической вероятностью фактического присутствия вредителя.

---

### Правило 5. Исторический результат неизменяем

Сохраненная оценка отражает состояние системы на момент ее выполнения.

Изменение текущей погоды или правил не должно автоматически изменять ранее сохраненный результат.

---

### Правило 6. Официальный источник отделяется от инженерного вывода

Пользователь должен иметь возможность различить:

- исходные сведения официального источника;
- результат, рассчитанный приложением на их основе.

---

### Правило 7. Профилактика не заменяет профессиональную помощь

Приложение предоставляет информационные рекомендации и не заменяет:

- медицинского специалиста;
- Роспотребнадзор;
- Россельхозцентр;
- профессионального агронома.

# 9. Функциональные требования

## 9.1 Общие положения

Функциональные требования определяют обязательные возможности первой версии приложения «Сезонный дозор».

Требования сформированы на основании:

- результатов предварительного исследования;
- пользовательских историй;
- пользовательских сценариев;
- утвержденных границ MVP.

Система должна обеспечивать полный пользовательский путь:

```text
Выбор территории
        ↓
Получение погодных данных
        ↓
Выбор профиля
        ↓
Оценка сезонного риска
        ↓
Объяснение результата
        ↓
Профилактические рекомендации
        ↓
Официальные источники
        ↓
Сохранение истории
```

---

# 9.2 Работа с территорией

### FR-001 Выбор территории

Система должна предоставлять пользователю возможность выбрать населенный пункт, для которого выполняется оценка сезонного риска.

---

### FR-002 Поиск территории

Пользователь должен иметь возможность выполнить поиск территории по названию.

---

### FR-003 Обработка нескольких результатов поиска

Если одному названию соответствует несколько территорий, система должна предоставить пользователю возможность выбрать нужный вариант.

---

### FR-004 Обработка неизвестной территории

Если территория не найдена, система должна:

- сообщить об этом пользователю;
- не выполнять запрос погодных данных;
- предоставить возможность изменить поисковый запрос.

---

### FR-005 Хранение выбранной территории

После выбора территория должна использоваться системой как текущая до момента:

- выбора другой территории;
- завершения пользовательской сессии.

---

# 9.3 Получение погодных данных

### FR-101 Запрос погодных данных

После выбора территории система должна получать актуальные погодные данные через Weather API.

---

### FR-102 Получаемые показатели

Система должна поддерживать получение следующих показателей:

- температура воздуха;
- относительная влажность;
- осадки;
- скорость ветра.

Дополнительно могут использоваться:

- прогноз температуры;
- температура почвы;
- исторические температурные данные.

Конкретный набор дополнительных данных зависит от возможностей выбранного Weather API и требований соответствующего правила оценки.

---

### FR-103 Отображение погодных данных

Пользователь должен видеть погодные показатели, использованные при выполнении оценки.

Минимально отображаются:

- территория;
- дата и время получения данных;
- температура воздуха;
- влажность;
- осадки;
- скорость ветра.

---

### FR-104 Проверка ответа Weather API

Перед использованием полученных данных система должна проверить:

- успешность HTTP-запроса;
- наличие обязательных полей;
- корректность типов данных;
- допустимость полученных значений.

---

### FR-105 Недоступность Weather API

При недоступности погодного сервиса система должна:

- обработать ошибку;
- сообщить пользователю о невозможности получить актуальные данные;
- не выполнять новую оценку риска;
- сохранить доступ к ранее созданной истории.

---

### FR-106 Запрет использования недостоверных данных

Система не должна автоматически заменять отсутствующие погодные показатели:

- нулевыми значениями;
- случайными значениями;
- заранее заданными «средними» значениями.

---

# 9.4 Пользовательские профили

### FR-201 Поддерживаемые профили

Система должна предоставлять три пользовательских профиля:

- Человек;
- Сад;
- Огород.

---

### FR-202 Профиль «Человек»

Для профиля «Человек» в MVP должна выполняться оценка:

- иксодовых клещей.

---

### FR-203 Профиль «Сад»

Для профиля «Сад» в MVP должна выполняться оценка:

- яблонной плодожорки.

---

### FR-204 Профиль «Огород»

Для профиля «Огород» в MVP должна выполняться оценка:

- колорадского жука;
- капустной тли.

---

### FR-205 Переключение профиля

Пользователь должен иметь возможность изменить профиль без повторного выбора территории.

Если ранее полученных погодных данных достаточно для нового профиля, система должна использовать их повторно.

---

# 9.5 Справочник угроз

### FR-301 Хранение угроз

Система должна содержать справочник поддерживаемых биологических угроз.

Для каждой угрозы должны храниться:

- название;
- краткое описание;
- объект воздействия;
- характер возможного вреда;
- период сезонной активности;
- принадлежность к пользовательскому профилю.

---

### FR-302 Карточка угрозы

Пользователь должен иметь возможность открыть подробную карточку угрозы.

---

### FR-303 Факторы оценки

Для каждой угрозы должен быть определен собственный набор факторов, используемых при оценке.

Не допускается предполагать, что один и тот же набор факторов подходит всем угрозам.

---

### FR-304 Связь с источником

Для сведений, используемых при формировании правил и рекомендаций, должен храниться источник.

---

# 9.6 Оценка сезонного риска

### FR-401 Запуск оценки

Пользователь должен иметь возможность запустить оценку после:

- выбора территории;
- получения погодных данных;
- выбора профиля.

---

### FR-402 Определение списка угроз

После запуска система должна автоматически определить угрозы, относящиеся к выбранному профилю.

---

### FR-403 Независимая оценка

Каждая угроза должна оцениваться независимо.

Результат одной угрозы не должен автоматически изменять результат другой.

---

### FR-404 Использование отдельных правил

Для каждой угрозы должен применяться собственный набор правил.

В MVP должны поддерживаться правила для:

- иксодовых клещей;
- колорадского жука;
- капустной тли;
- яблонной плодожорки.

---

### FR-405 Учет сезона

При выполнении оценки система должна учитывать дату и период сезонной активности соответствующей угрозы.

---

### FR-406 Учет погодных факторов

Система должна учитывать только те погодные показатели, которые определены правилами конкретной угрозы.

---

### FR-407 Проверка достаточности данных

До выполнения оценки система должна определить наличие всех обязательных входных данных.

---

### FR-408 Недостаточность данных

Если обязательных данных недостаточно, система должна:

- не подставлять вымышленные значения;
- определить возможность ограниченной оценки;
- при невозможности корректного расчета вернуть состояние «Недостаточно данных».

---

### FR-409 Уровни риска

Система должна поддерживать четыре уровня:

```text
LOW       — Низкий
MODERATE  — Умеренный
ELEVATED  — Повышенный
HIGH      — Высокий
```

---

### FR-410 Запрет представления результата как вероятности

Система не должна отображать качественный уровень риска как математическую вероятность.

Недопустимо:

```text
Вероятность появления клеща: 87%
```

если такая вероятность не рассчитана валидированной научной моделью.

---

# 9.7 Объяснение результата

### FR-501 Формирование объяснения

Для каждого результата система должна формировать объяснение полученного уровня.

---

### FR-502 Положительные факторы

Система должна показывать факторы, которые соответствуют условиям повышенной активности.

Пример:

```text
✓ текущий месяц входит в сезон активности;
✓ температура соответствует условиям активности.
```

---

### FR-503 Факторы, не повышающие риск

Система должна иметь возможность отображать условия, которые не соответствуют повышенному риску.

Пример:

```text
✗ влажность ниже благоприятного диапазона.
```

---

### FR-504 Использованные данные

Пользователь должен иметь возможность увидеть погодные данные, использованные при расчете.

---

### FR-505 Ограничение интерпретации

Для результата должно отображаться пояснение о границах модели.

Обязательный смысл:

> Оценка показывает соответствие текущих погодных и сезонных условий периоду активности и не подтверждает фактическое наличие вредителя в конкретном месте.

---

# 9.8 Профилактические рекомендации

### FR-601 Отображение рекомендаций

Для каждой угрозы система должна предоставлять профилактические рекомендации.

---

### FR-602 Связь рекомендации с угрозой

Рекомендации должны определяться отдельно для каждой угрозы.

---

### FR-603 Источник рекомендации

Для профилактической информации должен быть указан официальный источник.

---

### FR-604 Ограничение медицинских рекомендаций

Для угроз человеку приложение не должно:

- ставить диагноз;
- назначать лечение;
- оценивать вероятность заражения;
- заменять обращение к медицинскому специалисту.

---

### FR-605 Ограничение агротехнических рекомендаций

Для вредителей растений приложение не должно:

- назначать конкретные химические препараты как обязательное решение;
- рассчитывать дозировки средств защиты;
- заменять профессиональный фитосанитарный мониторинг.

---

# 9.9 Работа с источниками

### FR-701 Отображение источника

Пользователь должен иметь возможность увидеть источник, использованный для формирования правил и рекомендаций.

---

### FR-702 Тип источника

Для MVP основными источниками являются:

- Роспотребнадзор;
- Россельхозцентр.

---

### FR-703 Переход к источнику

При наличии ссылки пользователь должен иметь возможность открыть официальный материал в браузере.

---

### FR-704 Разделение источника и результата приложения

Интерфейс должен позволять отличить:

- сведения официального источника;
- вывод, сформированный Risk Engine.

Система не должна представлять собственный рассчитанный уровень риска как официальный прогноз Роспотребнадзора или Россельхозцентра.

---

# 9.10 История оценок

### FR-801 Автоматическое сохранение

После успешного выполнения оценки результат должен автоматически сохраняться.

---

### FR-802 Состав исторической записи

Историческая запись должна содержать:

- дату и время;
- территорию;
- выбранный профиль;
- погодные данные;
- список оцененных угроз;
- уровень каждой угрозы;
- факторы результата.

---

### FR-803 Просмотр истории

Пользователь должен иметь возможность открыть список ранее выполненных оценок.

---

### FR-804 Порядок отображения

История должна отображаться в обратном хронологическом порядке.

---

### FR-805 Просмотр исторического результата

Пользователь должен иметь возможность открыть отдельную сохраненную оценку.

---

### FR-806 Неизменность исторического результата

Просмотр исторической записи не должен автоматически запускать новый расчет.

Историческая оценка должна отображать:

- исходные погодные данные;
- результаты;

которые были сохранены на момент выполнения оценки.

---

# 9.11 Повторная оценка

### FR-901 Обновление погодных данных

При повторной оценке система должна получить актуальные погодные данные.

---

### FR-902 Новый результат

Повторный расчет должен создавать новую запись истории.

---

### FR-903 Сохранение предыдущего результата

Предыдущая оценка не должна изменяться после выполнения новой.

---

### FR-904 Изменение территории

При выборе другой территории система должна получить новый набор погодных данных.

Данные предыдущей территории не должны использоваться как текущие.

---

# 9.12 Обработка ошибок

### FR-1001 Ошибка внешнего сервиса

Ошибки Weather API должны обрабатываться без аварийного завершения приложения.

---

### FR-1002 Понятное сообщение

Пользователь не должен видеть:

- stack trace;
- текст Python exception;
- технический ответ внешнего API.

Вместо этого отображается понятное пользовательское сообщение.

---

### FR-1003 Ошибка входных данных

Некорректный пользовательский ввод должен быть обнаружен до выполнения операции.

---

### FR-1004 Ошибка расчета отдельной угрозы

Ошибка при оценке одной угрозы не должна приводить к потере уже корректно рассчитанных результатов других угроз, если дальнейшая работа системы безопасна и результат явно помечен как неполный.

---

### FR-1005 Отсутствие правил

Если для угрозы отсутствуют необходимые правила оценки, система не должна формировать уровень риска.

Пользователю отображается состояние:

> Оценка временно недоступна.

---

# 9.13 Требования к воспроизводимости

### FR-1101 Детерминированность

При одинаковых:

- погодных данных;
- дате;
- территории;
- наборе правил

Risk Engine должен возвращать одинаковый результат.

---

### FR-1102 Независимость от AI

Для выполнения оценки не должны использоваться ответы генеративной AI-модели.

---

### FR-1103 Трассируемость результата

Для каждого результата должна существовать возможность определить:

```text
какая угроза оценивалась
        ↓
какие данные использовались
        ↓
какие правила применялись
        ↓
какие факторы сработали
        ↓
какой уровень был получен
```

---

# 9.14 Итог функциональных требований

Функциональность первой версии образует следующую цепочку:

```text
Территория
        ↓
Weather API
        ↓
Проверенные погодные данные
        ↓
Пользовательский профиль
        ↓
Список угроз
        ↓
Risk Engine
        ↓
Отдельные правила каждой угрозы
        ↓
Risk Result
        │
        ├── уровень риска
        ├── факторы
        ├── объяснение
        ├── рекомендации
        └── источники
        ↓
История
```

Главное функциональное ограничение системы:

> **Приложение оценивает соответствие текущих условий известным условиям сезонной активности и не определяет фактическое присутствие вредителя.**

# 10. Нефункциональные требования

## 10.1 Общие положения

Нефункциональные требования определяют качественные характеристики приложения «Сезонный дозор».

Они устанавливают требования к:

- производительности;
- надежности;
- удобству использования;
- корректности и объяснимости результатов;
- работе с внешними сервисами;
- безопасности;
- сопровождаемости;
- совместимости.

---

# 10.2 Производительность

### NFR-001 Время запуска приложения

После запуска backend приложение должно быть готово к работе не более чем через 5 секунд на типовом персональном компьютере.

---

### NFR-002 Время загрузки страниц

Переход между локальными страницами приложения не должен сопровождаться заметными задержками.

При отсутствии обращения к внешнему API целевое время формирования ответа составляет не более 2 секунд.

---

### NFR-003 Получение погодных данных

Время ожидания ответа Weather API зависит от внешнего сервиса.

Во время выполнения запроса пользователь должен видеть состояние загрузки.

Интерфейс не должен создавать впечатление зависания приложения.

---

### NFR-004 Время расчета риска

После получения необходимых погодных данных расчет уровней риска должен выполняться практически мгновенно.

Целевое время выполнения Risk Engine для всех угроз одного профиля — не более 1 секунды.

---

### NFR-005 Повторная отправка запроса

Во время уже выполняющегося запроса погодных данных система должна предотвращать случайный многократный запуск одной и той же операции пользователем.

---

# 10.3 Надежность

### NFR-101 Устойчивость к ошибкам Weather API

Недоступность внешнего погодного сервиса не должна приводить к аварийному завершению приложения.

---

### NFR-102 Сохранность истории

После успешного сохранения результат оценки не должен теряться после:

- обновления страницы;
- перезапуска браузера;
- перезапуска приложения.

---

### NFR-103 Целостность расчета

Система не должна формировать обычный уровень риска, если для конкретной модели отсутствуют данные, обязательные для такого расчета.

---

### NFR-104 Запрет скрытых значений по умолчанию

Отсутствующий погодный показатель не должен незаметно заменяться:

- нулем;
- средним значением;
- предыдущим значением;
- искусственно заданной константой.

Если предусмотрен допустимый альтернативный алгоритм, его использование должно быть явно определено правилами конкретной угрозы.

---

### NFR-105 Независимость результатов

Ошибка расчета одной угрозы не должна повреждать:

- справочник угроз;
- историю;
- погодные данные;
- корректно рассчитанные результаты других угроз.

---

### NFR-106 Атомарность сохранения

Историческая оценка должна сохраняться только после формирования согласованного результата.

Не допускается создание записи истории, выглядящей как успешно завершенный расчет, если операция завершилась ошибкой.

---

# 10.4 Корректность и воспроизводимость

### NFR-201 Детерминированность

При одинаковых:

- дате;
- территории;
- погодных данных;
- наборе правил

система должна возвращать одинаковый результат.

---

### NFR-202 Отсутствие случайности

Risk Engine не должен использовать случайные значения при определении уровня риска.

---

### NFR-203 Объяснимость

Для каждого рассчитанного результата система должна позволять определить:

- какие данные использовались;
- какие факторы анализировались;
- какие условия выполнились;
- какой уровень риска был получен.

---

### NFR-204 Отсутствие ложной точности

Система не должна представлять качественную оценку как научно установленную вероятность.

В интерфейсе используются:

```text
Низкий
Умеренный
Повышенный
Высокий
```

а не искусственно рассчитанные проценты вероятности.

---

### NFR-205 Корректная терминология

Пользовательский интерфейс должен различать понятия:

- «уровень сезонного риска»;
- «условия активности»;
- «фактическое присутствие вредителя».

Высокий риск не должен описываться как доказательство наличия вредителя.

---

### NFR-206 Трассируемость правил

Правила, основанные на предметных сведениях, должны быть связаны с соответствующим источником.

Должна существовать возможность определить, какие сведения использованы при формировании правила.

---

# 10.5 Удобство использования

### NFR-301 Простота интерфейса

Приложение должно быть понятно пользователю без предварительного обучения.

Основной пользователь не обязан знать:

- устройство Weather API;
- биологические термины расчетной модели;
- принципы работы Risk Engine;
- устройство базы данных.

---

### NFR-302 Минимальное количество действий

Основной сценарий должен требовать минимального количества шагов:

```text
Выбрать территорию
↓
Выбрать профиль
↓
Получить оценку
```

---

### NFR-303 Понятность уровней риска

Каждый уровень риска должен визуально и текстово отличаться от других.

Пользователь не должен определять уровень только по цвету.

Рядом с визуальным обозначением всегда отображается текст:

- «Низкий»;
- «Умеренный»;
- «Повышенный»;
- «Высокий».

---

### NFR-304 Понятные ошибки

Сообщения об ошибках должны объяснять:

- что произошло;
- влияет ли проблема на выполнение оценки;
- что пользователь может сделать.

Недопустимы сообщения вида:

```text
500 Internal Server Error

KeyError: humidity

NoneType has no attribute...
```

---

### NFR-305 Понятность профессиональных терминов

Если в интерфейсе используется специальный термин, например:

> сумма эффективных температур,

пользователь должен иметь возможность получить краткое понятное объяснение.

---

### NFR-306 Единый стиль

Все страницы должны использовать единый визуальный стиль:

- одинаковую типографику;
- единые элементы управления;
- единое оформление карточек;
- единые обозначения уровней риска.

---

# 10.6 Доступность информации

### NFR-401 Не использовать только цвет

Уровень риска нельзя передавать исключительно цветовой индикацией.

Например, карточка должна содержать:

```text
ПОВЫШЕННЫЙ
```

а цвет используется только как дополнительный визуальный сигнал.

---

### NFR-402 Читаемость

Основной текст должен иметь достаточный размер и контраст для комфортного чтения на обычном ноутбуке.

---

### NFR-403 Адаптация под экран

Основная версия должна корректно отображаться на стандартном ноутбуке с разрешением Full HD.

Интерфейс не должен требовать горизонтальной прокрутки при обычной ширине окна браузера.

---

# 10.7 Работа с внешним API

### NFR-501 Изоляция Weather API

Остальные компоненты приложения не должны зависеть от структуры ответа конкретного поставщика погодных данных.

Внешний ответ должен преобразовываться во внутреннюю модель WeatherData.

---

### NFR-502 Тайм-аут

Запросы к внешнему погодному сервису должны иметь ограниченное время ожидания.

Приложение не должно бесконечно ждать ответ.

---

### NFR-503 Обработка некорректного ответа

Если внешний сервис возвращает:

- некорректный JSON;
- отсутствующие обязательные поля;
- недопустимые значения,

такие данные не должны передаваться в Risk Engine как корректные.

---

### NFR-504 Замена поставщика

Архитектура должна позволять в дальнейшем заменить Weather API без переработки Risk Engine.

---

# 10.8 Безопасность

### NFR-601 Хранение API Key

Если используемый Weather API требует ключ, он не должен храниться непосредственно в исходном коде.

Ключ должен передаваться через:

- переменные окружения;
- `.env`-файл, исключенный из Git.

---

### NFR-602 Публикация репозитория

В публичный Git-репозиторий запрещается добавлять:

- действующие API-ключи;
- пароли;
- секретные токены.

---

### NFR-603 Проверка пользовательского ввода

Название территории и другие пользовательские значения должны проходить проверку перед обработкой.

---

### NFR-604 Работа с базой данных

Операции с SQLite должны выполняться через предусмотренный слой доступа к данным.

Пользовательский ввод не должен преобразовываться в выполняемый SQL.

---

# 10.9 Работа с информацией о здоровье

### NFR-701 Информационный характер

Информация о клещах должна иметь исключительно профилактический и справочный характер.

---

### NFR-702 Отсутствие диагностики

Приложение не должно:

- диагностировать заболевание;
- определять наличие инфекции;
- оценивать состояние человека после укуса;
- назначать медицинские препараты.

---

### NFR-703 Официальные рекомендации

Информация о действиях человека должна основываться на официальных материалах Роспотребнадзора или других явно указанных официальных источниках.

---

# 10.10 Информация о защите растений

### NFR-801 Ограничение рекомендаций

Приложение не должно самостоятельно рассчитывать:

- дозировку пестицида;
- концентрацию раствора;
- периодичность химической обработки.

---

### NFR-802 Безопасный формат

Допустимыми рекомендациями являются, например:

- обратить внимание на растения;
- провести визуальный осмотр;
- усилить мониторинг;
- ознакомиться с актуальным сообщением Россельхозцентра.

---

# 10.11 Сопровождаемость

### NFR-901 Модульность

Приложение должно быть разделено как минимум на следующие области ответственности:

- пользовательский интерфейс;
- получение погодных данных;
- расчет риска;
- работа со справочником;
- работа с историей;
- доступ к базе данных.

---

### NFR-902 Независимость Risk Engine

Расчетная логика не должна зависеть от HTML-интерфейса.

---

### NFR-903 Добавление новой угрозы

Архитектура должна позволять добавить новый вид угрозы без полной переработки существующей системы.

Добавление угрозы может потребовать:

- нового профиля правил;
- справочной информации;
- рекомендаций;
- источников;

но не должно требовать изменения базового пользовательского процесса.

---

### NFR-904 Читаемость кода

Исходный код должен:

- иметь понятную структуру;
- использовать осмысленные имена;
- избегать дублирования расчетной логики;
- соответствовать принятому разделению по слоям.

---

### NFR-905 Конфигурируемость правил

Численные пороги и параметры предметных правил не должны быть хаотично распределены по контроллерам и пользовательскому интерфейсу.

Они должны находиться в специально определенном месте системы.

Конкретный способ хранения будет определен в Документе №2.

---

# 10.12 Тестируемость

### NFR-1001 Изолированное тестирование Risk Engine

Расчет риска должен быть возможен без реального обращения к Weather API.

Для теста системе можно передать заранее подготовленный объект WeatherData.

---

### NFR-1002 Проверяемость правил

Для каждого поддерживаемого вредителя должны существовать тестовые наборы входных данных, позволяющие проверить разные уровни риска.

---

### NFR-1003 Тестирование ошибок API

Должна существовать возможность проверить поведение системы при:

- timeout;
- HTTP-ошибке;
- некорректном ответе;
- отсутствии нужного погодного показателя.

---

### NFR-1004 Проверяемость истории

Сохраненный результат должен позволять проверить соответствие:

```text
входные данные
→
расчет
→
сохраненный результат
```

---

# 10.13 Совместимость и переносимость

### NFR-1101 Операционная система

Разработка и демонстрация должны быть возможны на Windows.

Архитектура не должна намеренно использовать функции, делающие приложение несовместимым с Linux или macOS.

---

### NFR-1102 Браузеры

Приложение должно корректно работать в актуальных настольных версиях основных браузеров, как минимум:

- Google Chrome;
- Microsoft Edge;
- Mozilla Firefox.

---

### NFR-1103 Локальный запуск

MVP должен поддерживать локальный запуск без развертывания на внешнем сервере.

Интернет требуется только для получения актуальных погодных данных и открытия внешних источников.

---

# 10.14 Ограничения первой версии

MVP не предъявляет требований к:

- высокой серверной нагрузке;
- тысячам одновременных пользователей;
- отказоустойчивому кластеру;
- облачному развертыванию;
- горизонтальному масштабированию;
- мобильному приложению;
- полноценному адаптивному дизайну для всех размеров смартфонов.

Эти характеристики не соответствуют масштабу первой версии проекта.

---

# 10.15 Итог

Нефункциональные требования первой версии основаны на четырех ключевых свойствах системы:

```text
НАДЕЖНОСТЬ
система не придумывает отсутствующие данные

        +

ОБЪЯСНИМОСТЬ
пользователь понимает причины результата

        +

ВОСПРОИЗВОДИМОСТЬ
одинаковые данные дают одинаковый результат
```

# 11. Требования к пользовательскому интерфейсу

## 11.1 Общие требования

Интерфейс приложения «Сезонный дозор» должен быть минималистичным, понятным и ориентированным на пользователя без специальных знаний в области биологии, метеорологии или защиты растений.

Основные принципы интерфейса:

- простота;
- понятная последовательность действий;
- отсутствие перегруженных экранов;
- единый визуальный стиль;
- объяснимое представление результата;
- четкое различие между исходными данными и выводом системы.

Пользователь должен понимать назначение приложения и основной сценарий работы без предварительного изучения инструкции.

---

## 11.2 Основная навигация

В первой версии должны быть доступны следующие основные разделы:

```text
Главная
Оценка риска
История
Справочник угроз
```

Допускается объединение «Главной» и «Оценки риска» на одном экране, если это упрощает пользовательский путь.

Основная навигация должна быть постоянно доступна пользователю.

---

## 11.3 Главная страница

Главная страница должна сразу объяснять назначение приложения.

Рекомендуемая структура:

```text
Сезонный дозор

Оценка сезонного риска
клещей и вредителей растений

[ Выберите город ]

Что вас интересует?

[ Человек ] [ Сад ] [ Огород ]

[ Оценить риск ]
```

На странице также должно присутствовать краткое пояснение:

> Приложение оценивает, насколько текущие погодные и сезонные условия соответствуют периоду активности выбранных угроз.

---

## 11.4 Выбор территории

Интерфейс выбора территории должен содержать:

- поле ввода;
- кнопку поиска либо автоматический поиск;
- список найденных вариантов при необходимости;
- отображение выбранной территории.

Пользователь должен явно видеть, для какого населенного пункта выполняется оценка.

Пример:

```text
Территория

[ Тула                         ]

Выбрано:
Тула, Тульская область
```

---

## 11.5 Выбор пользовательского профиля

Профили:

- Человек;
- Сад;
- Огород

должны быть представлены как крупные понятные элементы выбора.

Например:

```text
┌──────────────────┐
│      Человек     │
│                  │
│ Клещи            │
└──────────────────┘

┌──────────────────┐
│       Сад        │
│                  │
│ Вредители сада   │
└──────────────────┘

┌──────────────────┐
│      Огород      │
│                  │
│ Вредители овощей │
└──────────────────┘
```

Одновременно активным является один профиль.

Активный профиль должен визуально отличаться от остальных.

---

## 11.6 Отображение погодных данных

Перед или после выполнения оценки пользователь должен видеть погодные данные, использованные системой.

Рекомендуемый формат:

```text
Тула

Погода сейчас

Температура     +18 °C
Влажность       67%
Осадки          нет
Ветер           3,2 м/с

Данные получены:
07.08.2026 18:30
```

Погодная информация является входными данными расчета и должна визуально отделяться от результата Risk Engine.

---

## 11.7 Состояние загрузки

При обращении к Weather API интерфейс должен показывать состояние обработки.

Например:

```text
Получаем актуальные погодные данные...
```

или индикатор загрузки.

На время запроса повторный запуск той же операции должен быть недоступен.

---

# 11.8 Страница результатов

Результаты должны отображаться после успешного выполнения оценки.

В верхней части страницы показываются:

- территория;
- выбранный профиль;
- дата и время;
- погодные условия.

Ниже располагаются карточки угроз.

---

## 11.9 Карточка результата

Для каждой угрозы должна отображаться отдельная карточка.

Минимальное содержимое:

```text
Название угрозы

Уровень риска

Краткое объяснение

[ Подробнее ]
```

Пример:

```text
┌─────────────────────────────────┐
│ Иксодовые клещи                 │
│                                 │
│ ПОВЫШЕННЫЙ                      │
│                                 │
│ Текущие условия соответствуют   │
│ периоду повышенной активности.  │
│                                 │
│ [ Подробнее ]                   │
└─────────────────────────────────┘
```

# 11.10 Представление уровней риска

Используются четыре уровня:

```text
Низкий
Умеренный
Повышенный
Высокий
```

Каждый уровень должен иметь:

- текстовое название;
- визуальное обозначение;
- краткое пояснение.

Цвет может использоваться как дополнительный визуальный сигнал, но не должен быть единственным способом различения уровней.

Недопустимо отображать только:

```text
●
```

без текстового названия уровня.

---

# 11.11 Страница подробного результата

При выборе «Подробнее» пользователь должен видеть:

- название угрозы;
- текущий уровень риска;
- описание угрозы;
- факторы расчета;
- использованные погодные показатели;
- профилактические рекомендации;
- ограничение интерпретации;
- официальный источник.

Рекомендуемая структура:

```text
Иксодовые клещи

ПОВЫШЕННЫЙ РИСК

Почему:

✓ сезон активности начался

✓ температура соответствует
  условиям активности

✗ один из дополнительных факторов
  не соответствует

--------------------------------

Что это значит?

Текущие условия соответствуют периоду
повышенной активности клещей.

--------------------------------

Что можно сделать?

• соблюдать профилактические меры;
• использовать подходящую одежду;
• проводить осмотр после прогулки.

--------------------------------

Важно

Оценка не подтверждает фактическое
наличие клещей в конкретном месте.

--------------------------------

Источник

Роспотребнадзор

[ Открыть источник ]
```

---

# 11.12 Отображение факторов

Каждый фактор должен быть представлен понятным пользователю способом.

Например:

```text
✓ условие выполняется

✗ условие не выполняется

— данные отсутствуют
```

Не рекомендуется показывать только внутренние названия:

```text
temperature_rule_01 = true
humidity_factor = false
```

Вместо этого:

```text
✓ Температура соответствует условиям активности

✗ Влажность ниже благоприятного диапазона
```

---

# 11.13 Недостаточно данных

Если оценка невозможна из-за отсутствия обязательного параметра, карточка не должна выглядеть как обычный рассчитанный результат.

Необходимо отдельное состояние:

```text
Яблонная плодожорка

НЕДОСТАТОЧНО ДАННЫХ

Для полноценной оценки не хватает
исторических температурных данных.

[ Подробнее ]
```

Пользователь должен понимать отличие между:

```text
Низкий риск
```

и

```text
Недостаточно данных
```

---

# 11.14 Профилактические рекомендации

Рекомендации должны отображаться отдельным смысловым блоком.

Они не должны смешиваться с объяснением расчета.

Структура:

```text
Почему такой риск?
        ↓
Что рекомендуется?
```

Для угроз человеку рекомендации должны быть сформулированы особенно осторожно и иметь справочный характер.

---

# 11.15 Официальные источники

Источник должен отображаться непосредственно в карточке подробного результата либо в отдельном блоке.

Минимально указываются:

- организация;
- название или краткое описание материала;
- ссылка.

Например:

```text
Источник

Роспотребнадзор
«О начале сезона активности клещей»

[ Открыть официальный материал ]
```

Результат Risk Engine визуально не должен выглядеть как официальный прогноз указанной организации.

---

# 11.16 Справочник угроз

Приложение должно содержать отдельную страницу со всеми поддерживаемыми угрозами.

В MVP:

```text
Человек

• Иксодовые клещи

Сад

• Яблонная плодожорка

Огород

• Колорадский жук
• Капустная тля
```

## 11.17 Карточка справочника

Карточка угрозы в справочнике должна содержать:

- название;
- профиль;
- краткое описание;
- объект воздействия;
- возможный вред;
- сезон активности;
- основные факторы;
- официальный источник.

Карточка справочника не должна показывать текущий уровень риска, если оценка для территории не выполнялась.

# 11.18 История оценок

Страница истории должна отображать ранее выполненные оценки.

Рекомендуемый формат:

```text
07.08.2026 18:30

Огород
```

Записи отображаются от новых к старым.

# 11.19 Исторический результат

При открытии исторической записи пользователь должен видеть сохраненные на момент расчета:

- территорию;
- дату;
- профиль;
- погодные данные;
- уровни риска;
- факторы.

Необходимо явно показывать, что это исторический результат.

Например:

> **Архивная оценка от 07.08.2026, 18:30**

Интерфейс не должен создавать впечатление, что отображаемая погода является текущей.

# 11.23 Ограничение интерпретации

На странице результата должно присутствовать заметное, но не агрессивное предупреждение:

> **Важно:** уровень риска показывает соответствие текущих условий периоду активности и не подтверждает фактическое наличие вредителя.

Для профиля «Человек» дополнительно:

> Приложение носит информационный характер и не заменяет медицинскую консультацию.

# 11.24 Требования к языку интерфейса

Основной язык интерфейса — русский.

Пользовательские тексты должны быть:

- короткими;
- понятными;
- без избыточной профессиональной терминологии.

Например, предпочтительно:

> «Условия подходят для активности вредителя»

вместо:

> «Зафиксировано соответствие комплексу абиотических факторов оптимальной экологической ниши».

# 11.25 Термины

Например:

> **Сумма эффективных температур**

рядом должна иметь краткое пояснение:

> Показатель накопленного тепла за определенный период, который используется для оценки стадий развития некоторых вредителей.

# 11.26 Визуальный стиль

Интерфейс должен быть выполнен в современном минималистичном стиле.

Рекомендуются:

- светлый фон;
- четкие карточки;
- достаточные отступы;
- минимум декоративных элементов;
- простые иконки;
- крупные основные действия;
- визуальная иерархия информации.

Главный акцент должен быть не на декоративности, а на понятности результата.

# 12. Минимально жизнеспособный продукт (MVP)

## 12.1 Назначение MVP

MVP определяет минимальный законченный объем приложения «Сезонный дозор», достаточный для:

- проверки основной идеи проекта;
- демонстрации практического применения результатов исследования;
- прохождения полного пользовательского сценария;
- тестирования;
- представления проекта на защите.

MVP должен представлять собой работоспособное веб-приложение, а не набор отдельных демонстрационных функций.

---

## 12.2 Основная гипотеза продукта

MVP должен проверить следующую гипотезу:

> **Если автоматически сопоставить текущие погодные и сезонные условия с известными условиями активности конкретных биологических угроз, обычный пользователь сможет быстрее понять актуальный уровень сезонного риска и получить своевременную профилактическую информацию.**

При этом приложение не проверяет гипотезу о возможности точного прогнозирования появления вредителя.

Такой подход сознательно исключен на основании результатов предварительного исследования.

---

## 12.3 Основной пользовательский результат

После работы с приложением пользователь должен получить ответ на четыре вопроса:

```text
1. Какие угрозы актуальны для меня?

2. Какой сейчас уровень сезонного риска?

3. Почему система получила такой результат?

4. Что рекомендуется сделать?
```

Дополнительно пользователь должен иметь возможность проверить официальный источник информации.

---

# 12.4 Обязательные пользовательские профили

В MVP реализуются три профиля.

## Человек

Назначение:

оценка сезонных угроз непосредственно для человека.

Поддерживаемая угроза:

- иксодовые клещи.

---

## Сад

Назначение:

оценка сезонных угроз для садовых культур.

Поддерживаемая угроза:

- яблонная плодожорка.

---

## Огород

Назначение:

оценка сезонных угроз для овощных культур.

Поддерживаемые угрозы:

- колорадский жук;
- капустная тля.

---

# 12.5 Обязательные угрозы MVP

Первая версия должна поддерживать ровно четыре исследованные угрозы:

| Угроза | Профиль | Основные факторы |
|---|---|---|
| Иксодовые клещи | Человек | сезон, температура, территориальные условия |
| Колорадский жук | Огород | сезон, температура почвы / доступные температурные показатели |
| Капустная тля | Огород | сезон, температура, влажность |
| Яблонная плодожорка | Сад | сезон, накопленные температурные показатели |

Добавление других вредителей не является условием завершения MVP.

---

# 12.6 Выбор территории

Пользователь должен иметь возможность выбрать населенный пункт, для которого выполняется оценка.

MVP должен обеспечивать:

- поиск территории;
- выбор найденного варианта;
- отображение выбранной территории;
- изменение территории;
- получение погодных данных для выбранного места.

---

# 12.7 Получение реальных погодных данных

MVP должен быть интегрирован с внешним Weather API.

Минимально система должна получать:

- температуру воздуха;
- относительную влажность;
- осадки;
- скорость ветра.

При необходимости конкретной модели используются дополнительные доступные показатели.

Приложение должно показывать пользователю данные, которые были использованы при расчете.

---

# 12.8 Risk Engine

MVP должен содержать собственный детерминированный модуль оценки сезонного риска.

Risk Engine должен:

1. получить погодные данные;
2. получить текущую дату;
3. определить выбранную угрозу;
4. загрузить соответствующие ей правила;
5. проверить наличие необходимых данных;
6. применить правила;
7. сформировать результат.

Общая схема:

```text
WeatherData
+
Date
+
Threat
+
RiskRules
        ↓
    Risk Engine
        ↓
    RiskResult
```

---

# 12.9 Независимые модели оценки

Каждая угроза должна иметь собственную расчетную логику.

Недопустим вариант:

```text
Одна универсальная формула
        ↓
Все вредители
```

Используется подход:

```text
Иксодовые клещи
        ↓
собственные правила

Колорадский жук
        ↓
собственные правила

Капустная тля
        ↓
собственные правила

Яблонная плодожорка
        ↓
собственные правила
```

---

# 12.10 Уровни риска

MVP использует четыре качественных уровня:

```text
LOW       → Низкий

MODERATE  → Умеренный

ELEVATED  → Повышенный

HIGH      → Высокий
```

Система не должна преобразовывать их в неподтвержденную процентную вероятность.

---

# 12.11 Объяснение результата

Для каждого рассчитанного результата пользователь должен видеть:

- уровень риска;
- краткое объяснение;
- факторы, повысившие риск;
- факторы, не повысившие риск;
- использованные погодные данные.

Пример:

```text
Капустная тля

Уровень риска:
ПОВЫШЕННЫЙ

Почему:

✓ текущий период входит в сезон активности;

✓ температура находится в благоприятном диапазоне;

✓ влажность находится в благоприятном диапазоне.
```

---

# 12.12 Ограничение интерпретации

Для каждой оценки должно быть доступно пояснение:

> **Уровень риска показывает соответствие текущих погодных и сезонных условий известным условиям активности и не подтверждает фактическое наличие вредителя в конкретном месте.**

Это является обязательной частью MVP.

---

# 12.13 Профилактические рекомендации

Для каждой из четырех угроз должен существовать набор профилактических рекомендаций.

Рекомендации:

- имеют информационный характер;
- связаны с конкретной угрозой;
- основываются на официальных источниках;
- не содержат медицинской диагностики;
- не содержат самостоятельно рассчитанных дозировок химических препаратов.

---

# 12.14 Официальные источники

Для каждой угрозы должны быть доступны источники, использованные при подготовке:

- правил;
- описания;
- профилактических рекомендаций.

Основными источниками являются:

- Роспотребнадзор;
- Россельхозцентр.

Пользователь должен иметь возможность перейти к официальному материалу.

---

# 12.15 Справочник угроз

MVP должен содержать справочник четырех поддерживаемых угроз.

Для каждой угрозы отображаются:

- название;
- профиль;
- краткое описание;
- объект воздействия;
- возможный вред;
- сезон активности;
- основные факторы;
- источник.

---

# 12.16 История оценок

После успешного расчета результат должен сохраняться в SQLite.

Историческая запись должна содержать:

- дату и время;
- территорию;
- профиль;
- погодные данные;
- рассчитанные угрозы;
- уровни риска;
- факторы результата.

---

# 12.17 Просмотр истории

Пользователь должен иметь возможность:

- открыть список предыдущих оценок;
- выбрать конкретную запись;
- посмотреть сохраненный результат.

Исторический результат не должен автоматически пересчитываться по текущей погоде.

---

# 12.18 Обработка недостатка данных

Если для конкретной модели отсутствует обязательный показатель, MVP должен корректно обработать ситуацию.

Допустимые результаты:

```text
Оценка выполнена с ограничением
```

если правила допускают частичную оценку,

или:

```text
Недостаточно данных
```

если корректная оценка невозможна.

Приложение не должно создавать отсутствующие данные самостоятельно.

---

# 12.19 Обработка недоступности Weather API

При недоступности внешнего сервиса:

- приложение не завершается аварийно;
- пользователю показывается понятное сообщение;
- новая оценка не выполняется на вымышленных данных;
- справочник остается доступен;
- ранее сохраненная история остается доступна.

---

# 12.20 Обязательные страницы MVP

В первой версии достаточно следующих экранов:

```text
1. Главная / Оценка риска

2. Подробный результат

3. Справочник угроз

4. Карточка угрозы

5. История

6. Исторический результат
```

Главная страница и страница оценки риска могут быть объединены.

---

# 12.21 Основной демонстрационный сценарий MVP

На защите должен полностью выполняться следующий сценарий:

```text
Запуск приложения
        ↓
Выбор города
        ↓
Получение реальной погоды
        ↓
Выбор профиля «Огород»
        ↓
Запуск оценки
        ↓
Расчет двух угроз
        ↓
Колорадский жук
+
Капустная тля
        ↓
Разные уровни риска
        ↓
Просмотр факторов
        ↓
Просмотр рекомендаций
        ↓
Открытие официального источника
        ↓

        ↓
Просмотр записи в истории
```

Данный сценарий демонстрирует практически все ключевые возможности продукта.

---

# 12.22 Дополнительный демонстрационный сценарий

Для демонстрации исследовательской составляющей проекта рекомендуется использовать две угрозы с различной расчетной логикой.

Например:

```text
Капустная тля
        ↓
температура + влажность

и

Яблонная плодожорка
        ↓
накопленные температурные показатели
```

Это позволяет показать, что приложение не использует одну произвольную формулу для всех вредителей.

---

# 12.23 Функции, не входящие в MVP

В первую версию сознательно не входят:

- регистрация;
- авторизация;
- пользовательские аккаунты;
- роли пользователей;
- карта распространения вредителей;
- GPS;
- автоматическая геолокация;
- пользовательские сообщения о находках;
- фотографии;
- распознавание вредителей по изображению;
- машинное обучение;
- генеративный AI;
- чат;
- Telegram-бот;
- мобильное приложение;
- push-уведомления;
- электронная почта;
- прогноз на длительный период;
- автоматический сбор публикаций Роспотребнадзора;
- автоматический сбор публикаций Россельхозцентра;
- социальные функции.

Эти возможности не являются необходимыми для проверки основной гипотезы продукта.

---

# 12.24 Функции, которые не должны добавляться во время разработки MVP

Во время реализации первой версии новые функции не должны добавляться только потому, что:

- осталось свободное место в интерфейсе;
- найден интересный API;
- появилась идея использовать AI;
- функция выглядит эффектно на демонстрации.

Любое расширение должно оцениваться относительно основного вопроса:

> **Нужно ли это для проверки основной идеи «Сезонного дозора»?**

Если нет — функция остается за пределами MVP.

# 12.26 Критерий успешности MVP

Первая версия считается успешной, если пользователь без специальных знаний способен самостоятельно:

```text
выбрать место
        ↓
получить актуальную погоду
        ↓
выбрать интересующую область
        ↓
получить оценку риска
        ↓
понять причины результата
        ↓
увидеть профилактические действия
        ↓
проверить официальный источник
```

и при этом правильно понимает, что полученный уровень является **оценкой условий сезонного риска, а не прогнозом фактического присутствия вредителя**.

---

# 12.27 Итог MVP

MVP «Сезонного дозора» представляет собой законченное веб-приложение, объединяющее:

```text
Результаты исследования
        +
Актуальные погодные данные
        +
Rule-based Risk Engine
        +
Объяснение результата
        +
Профилактические рекомендации
        +
Официальные источники
        ↓
Понятная пользователю
оценка сезонного риска
```

Главная особенность проекта состоит не в количестве поддерживаемых вредителей, а в том, что программное решение непосредственно следует из результатов исследования.

Приложение превращает выявленные в исследовании зависимости между погодными условиями и сезонной активностью отдельных угроз в работающий, объяснимый и проверяемый программный продукт.
